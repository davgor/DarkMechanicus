# Forge performance investigation · DM-904

**GO** for a project-scoped utility owner, after splitting the work into separate contention, typed transport, and native cutover tickets. **NO-GO** for a pre-parse-only path or a production cutover that leaves synchronous Workspace lifecycle or attachment, mail, grant and migration calls on Electron main. Treat the limits below as downstream acceptance targets. The original investigation preceded production implementation. Local production evidence appears at the end of this report, with second-PC measurements still outstanding.

- The runner creates a private Electron profile, a private Dark Mechanicus home and synthetic repositories. It uses the normal desktop folder picker IPC with a fixture path substituted for the native dialog result. Every large project in the final matrix had no machine-local database before its first renderer command. The first matrix seeded them as already tracked, and startup chat recovery opened them before that command. Exclude its `desktop-cold` rows from cold-open comparisons.

The separate writer announces its acquired SQLite transaction and committed release over process IPC with timestamps. The probe tests check process identities and both timing sinks.

## Results

- Desktop cold open from its native renderer command took **151 ms / 344 ms / 16.437 s** across the three sizes. Main timer gaps were **161 ms / 357 ms / 16.343 s**. At 10,000 tickets the renderer max gap was 11.3 ms and it dispatched 411 synthetic clicks, while the only unrelated-project IPC reply waited 16.408 s. A live renderer timer does not establish an interactive desktop when its backend is stalled.
- Warm reconciliation of already-open desktop workspaces took **14 / 17 / 74 ms**. The automatic desktop timer advanced its 10,000-ticket session timestamp by 15.013 s. Within that observation window Electron main had a **96 ms** timer gap while renderer max was 11.4 ms. The current timer runs `heartbeatAll()` at 15-second intervals.
- Opening an existing database in the candidate utility owner took **66 / 54 / 553 ms** inside the child. Its warm `heartbeat()` took **9 / 12 / 58 ms**, with **7 / 7 / 34** text-read calls, **34 / 34 / 322** file-stamp calls and zero binary-read calls. The field `reads.bytes` is a count of binary reads. It does not count text bytes or parsed bytes. The deterministic I/O check separately counts UTF-8 bytes from warm `run.json` reads and binary payload size. It verifies one full history body is read each heartbeat and an already-restored image is not read again in this fixture.
- Applying one changed 10,000-ticket project's portable epic state took **2.083 s** in the unopposed utility-owner operation. Behind a 1.2 s competing writer, the same shape took **3.619 s** inside the owner. The unrelated project in a separate utility owner completed its card read in **2.4 ms** before writer release. The renderer received 39 small-project IPC replies before release and main's maximum gap was 21.2 ms. Real built CLI card creation was visible through the already-open owner, and the explicit changed epic appeared in the import result.
- On the disputed `getKanbanCard` operation, all baseline desktop shapes got **zero unrelated IPC replies before writer release**, with 1.314–1.322 s main gaps. In the final matrix moving the same command and its database connection to the utility owner allowed **38 / 38 / 39** unrelated IPC replies before release, with 19.7–20.6 ms main gaps. Both sets of calls preserved the writer commits. The first matrix still recorded a **926 ms** main gap during the 10,000-ticket owner contention case and **1.127 s** at 100 tickets. Main also owned those workspaces during the experiment, so background work could still contend on main. The automatic heartbeat is a plausible source, and the final matrix measured it independently. The adverse runs show why moving a single command is insufficient.
- The pre-parse-only experiment validated all 20 large-project snapshots in **287 ms** within the owner. That removes the sampled parsing from main, while the exact desktop lock wait remains. Any real pre-parse path would also need containment, branch and source revalidation before transaction apply. Utility ownership addresses both parsing and SQLite waiting.
- A real built `dm call heartbeat_kanban_card` extended a synthetic 60 s lease behind a 1.2 s writer, came back in **1.655 s**, and changed the attempt to running. Under the final 24 s writer, real built `dm call get_kanban_card` failed after **22.317 s** with `internal: database is locked`. The same error was reported remotely by the v0.69.0 MCP `get_kanban_card` call. The native fixture reproduces the exact command and error, and does not isolate whether that particular CLI failure occurred during workspace open or inside the command's own sweep.
- On the largest fixture the utility was about **143 MiB RSS** after opening the existing database and **209 MiB RSS** at the changed record sample. Sampled heap usage was about **59 MiB** at the latter point. Closing the candidate workspace dropped its owned map to zero and sampled **105 MiB RSS / 9 MiB heap** after subsequent work. The Electron process retains a runtime footprint after close. These are point samples across three open/change/close cases, with natural collection. They do not prove a production eviction policy or retained-memory ceiling.

The harness measures the repository reconcile portion of Forge Sync directly through built desktop IPC and uses local fixture transactions for the backend. It does not exercise GitHub fetch/push, the second PC, Remote Desktop input, or a production store switch during a held transaction. It confirmed the small-project IPC and separate owner remained usable during a held import, then untracked the large project after close. Full renderer interactions and untrack-during-import behavior remain downstream checks.

## Attribution

- [ForgeOpen](../../src/renderer/src/folder/ForgeOpen.tsx) gates child rendering on sync and [App](../../src/renderer/src/App.tsx) applies the gate when viewing Forge projects. [ForgeService](../../src/main/desktop/forgeService.ts) uses async Git, then invokes Workspace reconciliation inside its member validation callback. Awaiting that call still executes synchronous work before yielding.
- [Desktop bootstrap](../../src/main/desktop/bootstrap.ts), its [workspace pool](../../src/main/desktop/workspacePool.ts), and [Workspace](../../src/core/workspace.ts) own open, close, session touch, portable import and post-command flush. Startup chat recovery can touch every tracked folder. The [importer](../../src/core/repo/importer.ts) runs scan, planning and apply under a write transaction. It reads whole run-history text before recognizing an unchanged hash. The [attachment registrar](../../src/core/repo/attachmentImport.ts) examines stored evidence and saved bundles during apply. Previously restored run images incurred no warm binary reads in this fixture. The [orphan/recovered attachment path](../../src/core/repo/recoveredAttachments.ts) reads and hashes images independently and was outside this fixture. [File hash caching](../../src/core/repo/fileHashes.ts) currently remembers file stamps for comments and profiles without a size cap for a live workspace.
- [Kanban command routing](../../src/core/commands/kanban.ts) marks `getKanbanCard` and `listKanbanCards` as reads yet eagerly calls the [lease sweep](../../src/core/services/kanban/attempts.ts). It takes `BEGIN IMMEDIATE` before deciding whether any lease is overdue. Opening a fresh [CLI](../../src/cli/main.ts) workspace also migrates/binds the database, registers a session, reconciles and may flush before it serves even a read. [DatabaseSync](../../src/core/db/database.ts) uses a 5-second per-attempt busy timeout and up to four begin attempts. Keep WAL, FULL durability and transaction fencing in remediation.

## Ownership and delivery

1. **DM-912 · remove avoidable read contention.** On the warm Kanban read path, make the common no-overdue case read-only. If a read-side existence check finds a potentially expired lease, reacquire current time and run the authoritative expiry check inside the write transaction. Keep machine ownership, tooling holds, fencing and transition event atomicity. Test the exact built CLI entry separately because it has independent open-time writes. A fast CLI path must preserve the grant, project, schema, branch, session and storage checks for the particular allowed command. Use the current scoped authenticated CLI/MCP path for mutations. An external lease heartbeat still writes through SQLite and must remain viable while routine reconcile work is queued.
2. **DM-908 · implement typed asynchronous ownership and prove lifecycle.** Electron main retains window lifecycle, authenticated IPC validation, folder registry, UI state and asynchronous Git orchestration. The utility owns the entire project's Workspace and SQLite handle. Its narrow request set is open, typed allow-listed command, reconcile, heartbeat and close, correlated by request ID and owner generation. Evaluate one active project per process while scheduled refresh and unrelated IPC continue. Make workspace registration and startup chat recovery lazy. Do not expose Ctx, Db, paths supplied by the renderer or arbitrary SQL. Hold this transport behind internal integration until the native callers migrate.
3. **DM-913 · migrate native callers and complete the cutover.** Replace direct Workspace/Ctx access with narrow typed operations for [attachment streaming](../../src/main/desktop/attachmentProtocol.ts), [chat grants](../../src/main/agents/chatGrants.ts), [mailbox lifecycle](../../src/main/agents/chatMailboxes.ts), [agent mail](../../src/main/agents/agentMailDesktop.ts), [tooling recovery](../../src/main/agents/toolingRecoveryDesktop.ts), [cross-repository corrections](../../src/main/desktop/crossRepoCorrections.ts) and [Forge conversion/restore](../../src/main/desktop/forgeService.ts). The finished sprint has one desktop owner per canonical database, including cold open, automatic touch, import, outbox flush, session close and all native paths. Coordinate two-project operations by an explicit stable resource order. External CLI/MCP processes retain independent connections and use SQLite to serialize transactions. The completed cutover precedes cache-invalidation and renderer responsiveness acceptance.

## Cache, concurrency and failure contract

- **Identity.** Resolve the registered project path canonically before admission. Fence the owner by project ID, storage mode and Forge binding epoch in addition to the canonical project path. A changed workspace key prevents stale completion from overwriting a new selection, track operation or storage bind. Branch, checkout identity and tracked-record generation scope file-level hints. Cache immutable content hashes and lightweight validation metadata keyed by validated relative path, file stamp and format version. Keep authoritative ticket, evidence and run-history bodies in their existing persistent stores.
- **Invalidation.** After successful Git pull/merge or checkout, explicit local edits and external CLI/MCP writes, invalidate the affected generation or entries and revalidate against current SQLite revisions and sync-state hash. File watchers can schedule checks. They cannot certify that a write was seen, a file stayed within the repository, or content is unchanged. Recheck containment, identity and freshness at the application boundary. If an owner reads or parses outside a SQLite transaction, publish only after rechecking branch, file generation and external-writer fencing inside the transaction. A missing or changed token falls back to the original validated import path.
- **Ordering and leases.** One project serializes accepted mutations, storage transitions and flush. Coalesce duplicate scheduled reconciliation into one running and at most one pending job. Allow an ordinary session touch or authenticated lease heartbeat to advance ahead of another background import when no transaction is in progress. Once a transaction starts, preserve its atomicity. Keep desktop cached views usable during all project-local waits, and route unrelated project commands separately. Lease heartbeats from existing CLI/MCP sessions retain their current grant, machine and claim checks across desktop owner eviction. Pin any desktop owner that owns an unfinished local operation or indispensable active session, and transfer lifecycle responsibilities explicitly before retiring it.
- **Close and recovery.** Untrack stops admitting work for that owner generation, drains admitted operations in order and rejects any stale late response. Close ends the session and releases handles. Desktop shutdown starts this sequence before closing shared app state. On utility failure, resolve outstanding request outcomes explicitly where the durable state can confirm them. Report uncertain write completion and re-read durable SQLite/outbox/portable state through normal validation on restart. Replay mutations only through existing idempotency contracts. Exercise restart after commit-before-response, stop while import is held, and source move/untrack while stale messages are outstanding before enabling production cutover.

## Downstream budgets

- **Liveness.** In CI, hold an external SQLite writer at an explicit barrier and require an unrelated-project IPC response and both timer sinks before releasing it. Assert a same-project command cannot overtake an earlier admitted mutation. On this class of Windows hardware, target a main 10 ms timer max gap of 100 ms and unrelated IPC p95 of 50 ms during both large cold import and lock waits. These are native regression targets with a documented host, while barrier order and committed-state assertions are deterministic in CI. The clean candidate windows passed those liveness measures and the mixed-owner cases failed the main-gap target.
- **Operations.** After a successful cold reconcile, an unchanged warm reconcile should read **zero completed run-history bodies, zero saved-snapshot bodies and zero verified attachment images**. File enumeration and cheap metadata checks may remain. Verify counters and UTF-8/binary bytes independently. A single changed record should re-open its changed body and the validation dependencies required by the record. Verify an unchanged completed epic still exposes its attempts and evidence while a changed record and a real external CLI write appear after reconcile. Assert no duplicate semantic events or lost writes.
- **Resources.** Admit owners lazily. Use at most two active utility processes initially, with one interactive slot reserved from background-only jobs and at most one background import. Evict an idle unpinned owner on pressure or after 60 seconds. Bound each validation cache to 4,096 entries and 8 MiB of retained metadata, whichever is reached first. Test eviction, re-open, one unrelated foreground operation during a held import, and a second background project being queued rather than spawning more owners. Use **256 MiB RSS per active owner / 512 MiB aggregate** as local native regression budgets under the 10,000-ticket fixtures. Count live owners and cache entries deterministically in CI and sample OS memory separately. If both allowed slots are occupied, preserve the current cached board and surface queued work while an owner drains.
- **Durability.** Keep the existing SQLite busy settings and verify full commit, current lease fencing, storage mismatch rejection, project invalidation and durable recovery. The 60 s synthetic lease behind a 1.2 s writer must extend before its original deadline. A blocked writer still produces a genuine contention result under the existing extreme-lock limit. It may not be turned into success with retry or an increased timeout.

## Production utility ownership

The production-mode harness launched the compiled desktop, renderer, preload, and project utility from `aba66454c7ac690583585a787eb5ae5d1f616f3d` on the same Windows x64 host. It used the generated 10,000-ticket portable fixture and a separate five-ticket project. The folder picker selected the fixture through the ordinary desktop IPC. The utility hook observed posted requests and stopped one exact utility during the crash scenario. All ticket and mailbox requests used production IPC.

- Main PID 37612, renderer PID 20340, and project utility PIDs 21060 and 23180 were separate. The large project's desktop SQLite session recorded utility PID 21060. The application main PID held no session in that database.
- Cold opening the 10,000-ticket project took **20.402 s**. Main's longest sampled gap was **23.4 ms**, the renderer's was **25.3 ms**, and the unrelated project's IPC p95 was **8.3 ms** across 495 samples. Baseline cold opening took 16.437 s with a 16.343 s main gap. The gain in this run was responsiveness during the import. Cold completion time increased by about four seconds.
- The external writer held its transaction for **1.258 s** while the production utility processed a card mutation. Small-project IPC p95 was **9.2 ms** and the main gap stayed near **20 ms**. The writer committed before the card mutation completed. A second barrier test stopped the selected utility before releasing the writer. The mutation returned unknown completion, a new utility read the original card and the earlier committed mutation, and the interrupted mutation was absent. The pool test separately injects a lost post-commit reply and verifies a durable reread without replay.
- A real built CLI `get_kanban_card` completed in **3.813 s** while the desktop reconciled a changed portable record. The built CLI heartbeat completed in **3.226 s**, moved the synthetic attempt to running, and extended its 60-second lease. The renderer's ordinary grant issue and revoke and native mailbox provision and snapshot also passed.
- At the cold sample, the large and small utility working sets were approximately **196 MiB** and **114 MiB**, below the two-owner per-process and aggregate targets. These readings are point samples. Pool tests exercise the two-slot cap, idle retirement, preserved grant and hold identity, and cancellation of queued work on untrack.

The startup sample recorded a **3.284 s** main gap before the renderer finished loading. The timer began before the wrapper loaded the compiled app. This run did not isolate startup contributors. The cold command and contention measurements started after the renderer and preload were ready. This is local synthetic Windows evidence. It does not measure installed-app startup, macOS, or the second PC over Remote Desktop.

### Final production build

The same harness ran on `f96d429a19657360c1649e51d565e822e1422535` with the durable local-cache check and the final renderer build. The 10,000-ticket fixture again had no machine-local database when the cold request began. The separate five-ticket fixture supplied unrelated-project IPC.

- With a writer holding its transaction for **1.260 s**, an unrelated IPC reply and both timer sinks ran before release. The pre-release main and renderer max gaps were **16.6 ms** and **25.1 ms**, and unrelated IPC p95 over the operation was **8.6 ms**. The admitted card mutation committed once. The crash case stopped that project's utility while the writer held its transaction. The caller got unknown completion, and durable reread through a new utility found the earlier commit and no interrupted card.
- During production reconciliation of a changed portable record, the built CLI card read completed in **3.317 s** and the CLI lease heartbeat in **2.856 s**. The 60-second lease extended, and the main max gap was **20.9 ms**. Desktop mailbox provision and read and grant issue and revoke passed.
- Main PID 21152, renderer PID 40000, and project owner PIDs 37400 and 20276 were separate. The large project's desktop SQLite session recorded PID 37400. The large and small owner working sets at the cold sample were approximately **221.4 MiB** and **125.3 MiB**, within both local budgets.

The final run sampled a **454.4 ms** startup main gap across nine intervals. Its bounded CPU profile began before the wrapper required the compiled app and ended when the renderer loaded, before the command measurements. The app require took **373.2 ms**, and the renderer finished loading **714.5 ms** after the wrapper began.

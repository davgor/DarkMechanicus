# Dark Mechanicus — implementation architecture

This is the build contract for the product described in [`product-plan.md`](product-plan.md). Where the plan says "proposed", this document records the choice that was implemented. Exact types live in code; this file explains the rules those types carry.

## Processes and modules

```text
External agent host ──stdio──> out/main/mcp.js  (src/mcp)   ─┐
                                                             ├─> src/core  (Workspace: command layer) ─> SQLite + .darkmechanicus/ files
Electron renderer ─> preload (window.dm) ─> main IPC (src/main/desktop) ─┘

Electron renderer ─> preload (window.git, window.github) ─> main IPC (src/main/git, src/main/github) ─> git, gh, api.github.com
```

No renderer database access and no duplicated business rules: MCP handlers and IPC handlers are adapters only.

## Storage decision

SQLite through the built-in **`node:sqlite`** module (`DatabaseSync`). It ships inside Electron 42's Node 24 runtime and in system Node ≥ 22.13, so the desktop and the headless MCP process open the same database with no native `.node` binary to rebuild per ABI. See [`docs/decisions/0001-sqlite-driver.md`](decisions/0001-sqlite-driver.md).

- Database: `<repo>/.darkmechanicus/local/state.sqlite` (Git-ignored). WAL, `foreign_keys=ON`, `busy_timeout=5000`, `synchronous=FULL`.
- Every write runs in `db.tx()` = `BEGIN IMMEDIATE` (nested calls use savepoints). Concurrent processes serialize on the write lock.
- **Write-lock holds are short by design.** A read snapshot is a deferred `BEGIN` (`db.tx(fn, 'read')`), which leaves the WAL writer free; only writes take `BEGIN IMMEDIATE`. Reconcile and the finalizer read and verify tracked files, hash images and stage temp files before they take the lock. Each of their write transactions writes one record, one outbox entry or the closing bookkeeping (see [Repository-owned persistence](#repository-owned-persistence)), and a reconcile that would change nothing takes none. The epic's target is that no reconcile or finalizer write transaction is held longer than 250 ms on the 10,000-ticket fixture; the measurements are in [`reports/performance-revamp.md`](reports/performance-revamp.md). On the desktop, reconcile runs on its own connection and thread (the sync lane), so the screen's reads never queue behind it.
- **Observing holds.** `openDatabase(path, { onTransaction })` reports each depth-0 write transaction (acquire and hold time, commit or rollback) with the innermost `tagTransactions(tag, fn)` scope: `reconcile`, `flush` or `command` (`src/core/workspace.ts`, `src/main/desktop/syncLaneCore.ts`); a write outside them is untagged. Without an observer nothing is measured. The desktop pool logs one warning per operation whose queue wait plus run time exceeds 1 s (`SLOW_OPERATION_MS`).
- `guardTransactions` (the storage-epoch and Forge binding fence) checks once per depth-0 transaction, not on each savepoint, so a mailbox poll checks the fence once.
- Storage stays SQLite: [decision 0007](decisions/0007-targeted-reconcile.md) records the measurements and why a Postgres port, and an asynchronous reconcile on the owner's own thread, were rejected.
- Granted CLI startup redeems the grant and registers its session audit in one write transaction, before dispatching even read-only discovery such as `get_capabilities`. A competing writer cannot interleave grant use and session registration; capability discovery and native grant verification then read the committed authority. `src/cli/capabilities.concurrent.test.ts` exercises three separate CLI processes with a deterministic writer-intervention barrier, checking their JSON responses, exits, mailbox identities and completed grant-bound session audits.
- The one-shot CLI waits for competing SQLite writers during connection setup and before entering a write transaction. While SQLite reports contention, the CLI sends progress over private IPC to renew the native client watchdog. Abort and session shutdown can still terminate a waiting child. Transaction bodies execute once.
- **DM-919:** Windows workers reported `internal: database is locked` for `get_capabilities` and `list_comments`. In an isolated Windows reproduction, a writer held `BEGIN IMMEDIATE` on the project's SQLite store. The two real CLI processes completed WAL setup, then each exhausted four `BEGIN IMMEDIATE` attempts (`SQLITE_BUSY`, code 5) at grant redemption/session registration before reaching the read. Both exited 1 with `{"ok":false,"error":{"code":"internal","message":"database is locked"}}` (`get_capabilities`: 22,371 ms; `list_comments` with both IDs: 22,365 ms). This reproduces the startup path and failure, not the identity of the historical writer. The earlier read-only peer-discovery fix (#83) handles a different, unaudited lifecycle.
- `src/cli/projectContention.concurrent.test.ts` exercises audited concurrent reads, a writer held beyond the old CLI deadline, contested audit closure, idempotent reports and claim fencing.
- `PRAGMA user_version` is the schema version. `migrate()` runs under the write lock; a database newer than the build is refused with `incompatible_schema`, never downgraded.
- Backups use `VACUUM INTO` (a consistent snapshot), never a raw file copy. A backup copies the whole private database, local agent mail included, so `backupDatabase` is desktop-only (`repo.backup` is human-only): no agent role, grant or MCP tool can export every mailbox through it.
- Local agent mail (schema v15, `src/core/services/agentMailStore.ts`) lives only in this database, in both storage modes: no portable record, outbox entry, event body or history index carries it. A project-mismatch error therefore never advises deleting `local/`; move it aside or back it up first.

## The command layer (`src/core`)

A **Workspace** is opened per project root (one repository, or a folder of repositories) and implements `CommandApi` (`src/shared/domain/api.ts`). Each public command follows the same sequence:

1. **Validate** the untrusted input with the zod schemas in `src/core/schemas.ts` (`parseInput`). Limits (`LIMITS`) bound string sizes, list lengths, and graph sizes.
2. **Authorize** with `requireCapability(ctx.session, capability)`. Capabilities come from the session's role, fixed when the session registered (desktop launch, or the MCP process's launch flags). A caller-supplied name is never authority. The capability each command requires is declared once in `COMMAND_CAPABILITIES` (`src/core/commands/capabilities.ts`, exhaustive over `CommandName`); a test proves the services enforce exactly that table for every role.
3. **Branch guard** — commands that save, export, or dispatch work call `ctx.assertBranch()`; it throws `branch_changed` if the coordinating checkout's branch differs from the one recorded at the last reconcile. Flushing portable records is guarded the same way (pending exports belong to the recorded branch), and a Workspace opened after a branch switch does not reconcile automatically: the person (or agent) reconciles explicitly, which pauses active runs and records the new branch.
4. **Transact** — the whole mutation runs in one transaction, optionally wrapped by `withIdempotency` (same key + same request ⇒ original response; same key + different request ⇒ `idempotency_mismatch`). The stored response never holds a secret: `withIdempotency` is the only place a response is stored, and it stores what `storableJson` (`src/core/storedSecrets.ts`) makes of the response (the v10 migration rewrites stored rows through the same redaction, and deleting an epic deletes its rows). A listed secret field (`claimToken`, `token`, `claimSecret`) and any other field whose name ends in a secret word (`…Token(s)`, `…Secret`, `…Password`, `…Credentials`, `…ApiKey`; `fencingToken` and the token counts are listed as public) are stored as null, and whole claim tokens (attempt id, `.`, 16 or more secret characters) and grant tokens in any string or key are masked; stored text is never cut, so a bare attempt id at the end of a text is kept. The keys of `refMap` are a planner's refs, data rather than field names, so they are masked but not judged by name. A replay passes the stored row through the same redaction again, so a plaintext row written by an older build still running against the database is never handed out. So a replay returns a secret as null; the first caller alone receives it. Schema v10 put the responses stored before this through the same redaction.
5. **Record** — append an event (`appendEvent`) and enqueue portable-record work (`enqueueOutbox`) inside that same transaction.
6. **Flush** — after commit, the Workspace runs the finalizer to write portable records (see **Finalizer** under [Repository-owned persistence](#repository-owned-persistence): in `repo` mode files are staged outside the write lock and committed in one short transaction). Flush failure never rolls back the command; it leaves the outbox entry `pending/failed` with its retry time, and storage status shows it. The flush after a mutation is `scheduled` and honors the entry's backoff; `flush_portable_state` and the desktop Flush are `explicit` and retry every waiting entry at once.

Service functions take a `Ctx` (`src/core/context.ts`: db, clock, ids, session, machineId, projectId, assertBranch) and never read globals, so tests drive time and ids deterministically.

Errors are `DomainError(code, message, details)` with codes from `src/shared/domain/errors.ts`; adapters convert them with `toErrorShape`.

## Domain rules

### Statuses

Epics and tickets have exactly three statuses: `backlog`, `in_progress`, `completed`. Paused/failed/awaiting review are run or attempt conditions, never statuses.

- Starting work (a claim, or a run starting) moves the ticket and its epic to `in_progress`.
- A ticket becomes `completed` only through an accepted attempt (or explicit carry-forward) — `setTicketStatus(completed)` succeeds only if that evidence exists in the epic's active or latest run.
- An epic becomes `completed` when its final sprint checkpoint advances (all required tickets accepted, the final sprint report carries an epic outcome whose success criteria are all met, and the checkpoint policy's authorization is present), or when a verified Linear transfer completes it: the read-back of the transfer the person authorized matches its stored packet, and the epic's outcome records the transfer. `setEpicStatus(completed)` never completes an epic.
- `completed` is terminal for epics: no status change, no draft, no save, no new run. Tickets of a completed epic are read-only.
- `in_progress` → `backlog` is allowed for an epic without an active run, and for a ticket without an open attempt.

### Drafts and saved revisions

- An epic has at most one draft (`drafts` table) with a `draft_revision` counter for optimistic concurrency and a `base_revision_id`.
- `createEpic` creates the epic (`backlog`) plus an initial draft (one empty sprint). Until the first Save the epic has no saved revision.
- `openDraft` creates a draft from the current saved bundle if none exists. `updatePlanDraft` also creates it implicitly.
- `updatePlanDraft(ops, expectedDraftRevision)` applies `DraftOp`s through `applyDraftOps` (`src/core/plan/draftOps.ts`): all-or-nothing, and every rejected op returns a concrete reason (e.g. "Dependency not added. DM-203 is in Sprint 2 and can't require DM-301 in Sprint 3…"). A stale `expectedDraftRevision` fails with `conflict`. Client-local refs map to stable ids in `refMap`.
- `savePlan(expectedDraftRevision)` validates the whole bundle (`validatePlan`; errors ⇒ `invalid_plan`), rejects a draft whose base is no longer current (`stale_draft`), then records a **pending** revision + outbox entry in one transaction. The finalizer writes the snapshot and pointer; only then is the revision `saved`, the epic's `current_revision_id` advanced, `ticket_status` rows created for new tickets, the draft removed, and the result `saved`. If the finalizer fails the result is `pending`, the draft stays, and the next flush retries. Saving a draft identical to the current revision returns `unchanged`.
- Execution reads only saved revisions. A pending revision is never executable.
- `discardPlanDraft` deletes the draft (for a never-saved epic it resets to the initial bundle).
- Revision ids are collision-resistant stable ids; `number` is display-only (max + 1 per epic).

### Plan validity (`src/core/plan/graph.ts`)

Errors (block Save): duplicate ids, empty titles, no sprints, non-contiguous sprint ordinals, a ticket in zero or several sprints, unknown ticket in a sprint, edges to unknown tickets, self-edges, duplicate edges, **a prerequisite in a later sprint**, cycles (reported as a path), bad relations, duplicate criterion ids, invalid policies, and the acceptance-node errors below. Warnings: isolated tickets, empty sprints, missing acceptance/success criteria, required ticket depending on an optional one, a work-ticket criterion whose wording asks for a person (`criterion_needs_person`, from `src/core/plan/criterionWording.ts`; acceptance nodes are exempt, since a person verifies only at the sprint checkpoint), the acceptance-node warnings below, and, **while a run is active** (it has started a sprint), the run-aware warnings: `edits_passed_sprint` (the draft, or a newer saved revision, changes a sprint the run has already passed: a ticket edited, added, removed, moved out or given other prerequisites, or the sprint's own settings; one warning per sprint, measured against the revision the run is pinned to, ignoring the automatic title an acceptance node takes from its sprint's number) and `sprint_before_active` (a sprint the run's plan did not have sits before the active one, so the run never reaches it). They come from `src/core/plan/runWarnings.ts`, are added by `validatePlan` and by every draft edit's result, and never change `valid`.

An edge `{from: A, to: B}` means **B requires A's accepted result**. Relations (`related_to`, `duplicate_of`) are never execution edges. Layout is not stored; the desktop derives positions.

### Sprint acceptance nodes

- Every sprint ends in one ticket of `kind: 'acceptance'` (`src/core/plan/acceptance.ts`; `work` is the default and is never stored, so plans saved before the kind existed keep their content hash). The draft creates it with the sprint (`createEpic`, `add_sprint`): titled `Sprint N acceptance`, a testing ticket with no criteria yet, always last in its sprint. It cannot move to another sprint, its automatic title follows a renumbered sprint, and it goes with its sprint when the sprint is otherwise empty.
- It **implicitly requires every required (non-optional) work ticket of its sprint**. No edge is stored, so tickets move between sprints without rewiring, and `get_run` and `get_ready_tickets` list them as its prerequisites (`get_ticket` shows stored edges only). Until they are all accepted, and while the latest check of any row of its sprint has not passed, it is not ready.
- Its criteria may carry `covers`, the id of the work ticket the criterion verifies (draft operations accept an id, a display key or a client ref; `null` clears it). The plan puts one specific screenshot, measurement or end-to-end check per ticket there, so the combined sprint is verified item by item. A `covers` on a work ticket is ignored.
- Errors: a second acceptance node in a sprint (`duplicate_acceptance`); a ticket of its sprint requiring the node (`acceptance_runs_last`); a criterion covering an unknown ticket (`unknown_covered_ticket`). Warnings: a sprint with work but no node (`missing_acceptance_node`); a required work ticket no criterion covers (`ticket_not_covered`); a criterion covering a ticket outside its sprint (`covers_outside_sprint`); an explicit edge into the node that it already implies (`redundant_acceptance_edge`); `covers` on a work ticket (`covers_on_work_ticket`).
- The checkpoint gates on it (see Sprint checkpoints): its own accepted attempt even when it is optional (`acceptance_accepted`), a verified increment (`increment_merged`), and the project's Definition of Done reported as passed (`definition_of_done`).

### Runs, readiness, and attempts

- One active run per epic (`queued|running|awaiting_checkpoint|paused`), enforced by a partial unique index.
- `queueRun` (desktop) creates a `queued` run pinned to the current saved revision; `startRun` (orchestrator) picks up the queued run or creates one, binds the epic branch (explicit input, else the current checkout branch + HEAD), sets the first sprint active, and moves the epic to `in_progress`.
- A run is pinned to `revision_id`. Saving a new revision never changes an active run; `adoptRevision` switches it while it is running, awaiting its checkpoint or paused, and only with no open attempts (adoption invalidates grants bound to the old revision, so in-flight workers finish or are reconciled first; no pause is needed). Every session but the desktop's must give a `reason` (trimmed, 20 to `LIMITS.shortText` characters: what failed and what the revision changes); it is stored with claim and grant tokens masked in the `run.revision_adopted` payload, with the adopted `revisionNumber` and `adoptedBy` (the session's role), and the run's activity shows "Plan revision n adopted by the orchestrator: why". It is information only: nothing waits on it. An orchestrator without `allowSave` may `savePlan` an epic whose active run this machine owns (`requireSaveAuthority`, `src/core/services/plans.ts`: a per-epic check, not a role capability, so the MCP server lists `save_plan` to every orchestrator and the service refuses the rest; inside the save's transaction it rechecks the run and refuses a draft whose `policies` differ from the epic's current saved revision's (the person's latest, so it cannot revert stricter limits the run has not adopted yet), or that removes a ticket with spent, unsuperseded attempts in the run or moves one to a later sprint, since each would grant retries, which only the person does; `adoptRevision` repeats the spent-ticket check inside its transaction for every session but the desktop's that lacks `plan.save`, because a ticket can be moved or removed while unspent and fail before the adoption), so it fixes the plan mid-sprint and adopts it without the person; checkpoint approval stays human-only. Accepted tickets whose content hash is unchanged keep their acceptance; changed tickets need explicit `carryForward` or new work (old attempts get `superseded_at`). A changed ticket in a sprint the run already passed can never be redone in that run, so adoption refuses it unless it is carried forward. **A ticket that moves to a later sprint starts it with a fresh retry budget:** its failed, rejected and abandoned (reconciled `lease_expired`) attempts get `superseded_at`, so readiness no longer counts them and a leftover does not arrive at its retry limit. Sprints are matched by id (a renumbered sprint is the same sprint), accepted and canceled attempts are never touched, the superseded attempts stay in history (and in the tier facts), the next attempt continues the numbering, and the tickets so treated are listed as `freshBudget` in the adoption result and in the `run.revision_adopted` event. The desktop's Saved view shows the revision an active run executes.
- Runs carry `owner_machine_id`. A run imported from another machine rejects execution commands with `run_not_owned` until `takeoverRun`, which marks its leased attempts `lease_expired` (uncertain, needs reconciliation) and pauses the run.
- **Readiness** is computed server-side for the active sprint: a ticket is `ready` when every prerequisite is accepted in this run (or carried forward), it has no open attempt, its last attempt does not need reconciliation, it is under the retry limit, and capacity (sprint cap, plan `maxConcurrency`) allows. Tickets of later sprints are `later_sprint`. Blockers explain why (`prerequisite`, `row_check_failed`, `delivery_pending`, `concurrency`, `retry_limit`, `lease_expired`, `run_state`). Readiness stays per ticket: there are no waves inside a sprint, and rows are not a barrier. Beyond its own prerequisites a ticket is held only by a failed row check on a row it depends on and by an earlier sprint's unverified delivery (Delivery hold below), and a sprint's acceptance node waits for every required work ticket of its sprint (see Sprint acceptance nodes, Rows and Row checks below).
- **Rows** (`groupIntoRows` and `planRows` in `src/core/plan/graph.ts`; the graph view uses the same function and only wraps a wide row at six columns) are the server's layer concept: within a sprint, a ticket's row is one below its deepest same-sprint prerequisite, so row 1 has no same-sprint prerequisites and prerequisites in other sprints do not count. A sprint's acceptance node is in no row (its `row` is null). `get_run` reports each ticket's `row` and, for every row of every sprint, its tickets and latest row check; `get_ready_tickets` reports the same for the active sprint.
- **Delivery hold** (`deliverySatisfied` and the `delivery_pending` blockers in `src/core/plan/readiness.ts`): while a sprint before the active one declares `delivery` and has neither a waiver nor a passing highest-numbered delivery check (`delivery_checks`, read with the run context), every pending ticket of the active sprint carries a `delivery_pending` blocker `{ sprintId, ordinal }`, once per such sprint: a ticket that would be `ready` is `waiting`, and a `blocked` one stays `blocked`. A later failed check puts the hold back; a waiver releases it for good. Plans without `delivery`, and the active (or final) sprint's own delivery, hold nothing. A refused claim's message names `record_delivery` and the person's waiver, and `get_run` lists every check and waiver as `deliveries` in number order. `adoptRevision` (and so `approveWithRedraft`) refuses with `conflict` a revision that removes or changes the `delivery` of a sprint before the active one while it is unsatisfied, so only the person's waiver lifts the hold.
- **Row checks** (`recordRowCheck`, MCP `record_row_check`, capability `run.row_check`, orchestrator only; table `row_checks`, schema v5, ids with the `rk` prefix) record `{ runId, sprintId, row, commit, checks[] }` as a run event (`run.row_check_recorded`) and in the run history. `checks` has at least one entry and the check **passes only when every entry has status `passed`**: a failed or skipped entry fails it. A run's checks are numbered in the order they were recorded and the highest number of a row is its latest. While a row's latest check has not passed, every ticket that requires a ticket of that row is `waiting` with a `row_check_failed` blocker (once per row, whichever of its tickets it requires), and a later passing check clears the hold. A sprint's acceptance node is held the same way while the latest check of **any** row of its sprint has not passed (one blocker per failed row). Nothing else is held: readiness stays per ticket, with no barrier between rows, and a ticket already accepted stays accepted.
- **Claim** (`claimTicket`) is transactional: re-computes readiness, creates an attempt (`claimed`) with `fencing_token` = previous claims + 1, a lease, and a secret; returns a claim token (`<attemptId>.<secret>`) and a bounded execution packet (pinned ticket content, acceptance criteria, predecessor outputs, constraints, reporting contract). The partial unique index on open attempts makes duplicate concurrent claims impossible. The token is shown once: a replay of the claim's idempotency key returns the same attempt and packet with `claimToken: null`, and nothing rotates the secret. A caller that lost the token, with no worker holding it, fails the attempt without a token (orchestrator only; it uses a try) and claims again; if a worker may hold it, the lease runs out and the attempt is reconciled. Either way the new claim needs a new idempotency key: the old key keeps replaying the lost claim.
- Heartbeat extends the lease (first heartbeat moves `claimed → running`). Late writes with a superseded or expired token fail with `stale_claim` / `expired_claim`. A heartbeat may carry `progress` `{ note (at most 280 characters), step? (at most 64) }`: it is stored as an `attempt.progress` event (time, sending session, `{ attemptId, note, step }`) in the local events table after any claim token in it is masked, the last 200 per attempt are kept, and it queues no outbox work and is not part of run history, so exports and their hashes do not change. A refused heartbeat stores no note.
- **Activity timelines** (`getAttemptTimeline`, `getRunTimeline`; `src/core/services/activity.ts`, entry shapes in `src/shared/domain/activity.ts`; capability `read`, desktop commands only, no MCP tool) are read models over the events table and the attempt as it stands now; they store nothing. An attempt timeline lists, in time order, the claim (worker label, model, host, effort, rationale), one `alive` span, progress notes, comments on the ticket made while the attempt was open (after its claim, until it closed), the submission, the decision, a failure, a lease expiry (or takeover) and its reconciliation, and the run ending under it. Plain heartbeats write no event, so they are collapsed into the `alive` span: first heartbeat (the `attempt.running` event) to `attempts.heartbeat_at`, with `active` true while the attempt holds a lease. A run timeline lists the run's starts, pauses, resumes and ends, claims, submissions, decisions, failures and lease events, sprint reports and checkpoint approvals and advances, grouped by the session that logged each (groups in order of first activity); notes and heartbeats stay in the attempt timeline. `isLive` is true while the attempt is open (`claimed`, `running`, `submitted`) or the run is active. **Cursor**: `cursor` is an event `seq`; pass it back as `sinceSeq` and a page holds only entries whose event came later (`limit` 1 to 500, default 200; when more remain the cursor stops at the last entry returned). The alive span is the one entry that grows without an event, so it is sent again, same id and a later `until`, on every poll while the attempt holds a lease and on any page that carries another entry (the attempt may have closed since the last poll); the client replaces an entry by id. Each read first expires overdue leases and runs in one transaction, so `isLive` and the entries agree. Every text in an entry is masked for claim-token lookalikes again on the way out, and attempt facts come from `attemptView`, which has no claim secret. The renderer polls with `src/renderer/src/app/activityPoller.ts`.
- Leases expire lazily: commands that read or write execution state first mark overdue `claimed/running` attempts `lease_expired`. Lease expiry is uncertainty, not failure: the ticket needs `reconcileAttempt` (`abandon`, or `resubmit` with outputs) before another claim.
- `submitAttempt` (worker/orchestrator with the claim token) → `submitted`. Submission never unlocks dependents.
- **Sprint increments** (`increment` on `submitAttempt` / MCP `submit_attempt`, acceptance nodes only; column `attempts.increment_json`, schema v6; `incrementVerify.ts`, `increments.ts` in `src/core/services`) check that a sprint reached the epic branch as **one squashed commit**. The acceptance node's submission names `{ branch, commit }`; the command layer asks the Git adapter read-only questions (`isAncestor`, `commitParents`: `git merge-base --is-ancestor`, `git rev-parse --verify`, `git rev-list --parents`, nothing that writes) and `submitAttempt` stores the verdict with the attempt, so gate evaluation stays synchronous SQL and never asks git. The checks, in order: the named branch is the epic's own `branch.name` (the epic's, never the caller's, is what everything else is measured against) · the commit exists · it has exactly one parent · it is reachable from `refs/heads/<epic branch>` · it comes after its base · no commit recorded (`outputs.commits`) by the sprint's accepted, current `work` attempts is reachable from the epic branch (that proves the sprint was squashed and not merged; carry-forward attempts and rejected or superseded ones are not counted). The base is the nearest earlier sprint's verified increment in the run (the new commit must not be reachable from it), else the epic's start commit (the new commit must come strictly after it). **An epic branch without a start commit** (`startCommit: null`) and no earlier increment has no base: the base check is recorded as `skipped` with that reason and the verdict can still pass; likewise the squash check is `skipped` when the sprint's accepted work recorded no commit hash. A skipped check never counts against an increment, a failed one does, and every verdict lists each check with its detail.
  - **A failed verdict is stored, not rejected.** `submit_attempt` still returns the attempt (state `submitted`) with `increment: { passed: false, reasons, checks, ... }`, so the orchestrator reads the reasons straight away, rejects the attempt with them, and the node is resubmitted as a new attempt. Accepting a node whose verdict failed does not help, because the gate reads that accepted attempt, and an accepted ticket cannot be claimed again in the run. A work ticket that names an increment is refused (`invalid_input`); a malformed branch or commit is refused by the input schema; a commit or branch git does not know is a failed check with a reason, never an error. Verification happens once, on submit: `reconcile_attempt` with `resubmit` stores no increment, so that node's gate stays unmet until a submission names one.
  - Read back: `get_run` lists `increments` (each sprint with an acceptance node whose standing attempt, or latest current attempt, named one: sprint, node, attempt and state, verdict), `get_sprint_report` and the checkpoint's `report` carry the sprint's `increment` beside the report (in a folder of repositories `increments` instead, one per repository in name order, and no `increment`; neither is in its content hash, so grants are unaffected), and the run history exports the verdict on the attempt record (`attempts[].increment`, absent when none was named, so history recorded before schema v6 keeps its bytes).
  - The integration target is the epic branch. Merging the epic into the default branch stays a person's step.
- **The sprint cadence** these pieces serve (the orchestrator's side is in `skills/orchestrator.md` and its built-in facts in `skills/knowledge/orchestrator/`; Dark Mechanicus records the commits and verdicts and asks Git read-only questions, but it never merges). Core and MCP never write to Git; only the desktop's Source control does, in `src/main/git`, when the person asks it to (see [Source control](#source-control)):
  1. Tickets are light. A worker branches from the sprint integration branch, runs only targeted checks (tests for the files it touched, typecheck when types changed, a screenshot only when a criterion needs one) and submits; the reviewer judges it against its own criteria and that evidence.
  2. The orchestrator merges each accepted ticket into a separate worktree on the sprint integration branch, which leaves the coordinating checkout on the epic branch (switching it raises `branch_changed`). When a row is fully accepted it runs the combined check (typecheck plus the tests touching that row's files) and records it as a row check.
  3. When the acceptance node is ready, the Definition of Done runs on the combined work (a slow check that has its own ticket is taken from that ticket's accepted result), each covered item is verified, and the sprint is squashed into one commit on the epic branch, which the node's submission names as its increment.
  4. The checkpoint gates on the node, the verified increment and the Definition of Done, and then on the person's approval. The full verification therefore runs once per sprint, on the combined work, and the epic branch gets one commit per sprint, never a merge per ticket.
- `acceptAttempt` / `rejectAttempt` (orchestrator/reviewer/desktop) decide a submission. Acceptance completes the ticket and unlocks dependents; rejection leaves the ticket retryable. Every acceptance also keeps the reviewer's own per-criterion results on the decision (`decision.criteria`, `[]` when none were passed; an acceptance recorded before has no key, which marks its criteria as not distinguishable), so reviewer-checked criteria stay apart from the worker's claims, and a sprint acceptance node's acceptance freezes the Definition of Done check names it was accepted against (`decision.requiredChecks`). Both are optional in the portable run history, so earlier records keep their bytes.
- `failAttempt` → `failed`. When a ticket exhausts `retryLimit` (+ user-granted retries), the plan's `onTicketFailure` applies: `continue_independent` (default; dependents stay blocked), `pause_run`, or `fail_run` (terminal; open attempts canceled). A failed dependency is never treated as complete.
- `carryForwardTicket` records a `carry_forward` attempt (state `accepted`) for a ticket already `completed` by an earlier run, with an explicit note.
- `cancelRun` cancels open attempts; `pauseRun` stops new claims (open attempts may still report).
- A run paused with the exact reason `signed_out` (the app's response to an orchestrator chat whose CLI login expired) keeps its open leases: `expireLeases` skips it whatever the lease time, and heartbeats still work. Only the desktop session holds `run.pause_signed_out` (human-only, like checkpoint approval), so `pause_run` with that reason from an MCP session fails with `unauthorized` and changes nothing. The desktop can also switch a run that is already paused for another reason (the ticket-failure policy, a person's pause) to `signed_out`: its overdue leases lapse first, `paused_at` becomes that moment, the open leases are kept, and a `run.paused` event records `from: paused` and the `previousReason`; a run already paused for sign-in is left as it is, so its `paused_at` is not lost. Resuming a run paused for `signed_out` needs the desktop-only `run.resume_signed_out` (human-only too): `resume_run` from an MCP session fails with `unauthorized` and a message that the person resumes it in the desktop app, and changes nothing; a run paused for any other reason is resumed as before. Every pause records `paused_at` (schema v8, local, not exported); `resumeRun` after a `signed_out` pause extends each open lease by the time the run spent paused and records a `run.leases_extended` run event (`pausedAt`, `extendedMs`, each attempt's old and new lease end). Other pause reasons, and `takeoverRun`, expire leases as usual.

### Sprint checkpoints

- `submitSprintReport` stores report revision n+1 (content hash recorded) and moves a `running` run to `awaiting_checkpoint`; no new claims while awaiting a checkpoint.
- Gate conditions (`getCheckpoint`), in this order: report submitted for the active sprint (`report_submitted`) · no open leases in the sprint (`no_active_leases`) · every required ticket accepted (`required_accepted`; the sprint's own acceptance node is left to the next condition) · (sprints with an acceptance node) the node accepted (`acceptance_accepted`) and its increment verified (`increment_merged`: the node's accepted submission, else the one awaiting review, carries a passing increment verdict; a rejected or superseded attempt never counts) · (and, when the project has a Definition of Done) `definition_of_done`: the node's accepted, current attempt reports every named check as passed in its evidence (see below) · (sprints with an acceptance node) the latest report includes a retro with something in it (`retro`; see Sprint retros) · every exit criterion reported met (`exit_criteria`) · (final sprint) epic outcome with all success criteria met (`epic_outcome`) · the run executes the epic's current plan (`plan_current`; see The retro and the redraft loop) · authorization (`approval`).
- Authorization: sprint `checkpoint.mode = human` (default) needs a one-use **approval grant** issued by the desktop (`approveCheckpoint`), bound to project, epic, run, pinned revision, sprint, report id, report hash, and action. `advanceSprint` consumes the exact grant in the same transaction as the transition. A new report revision, an adopted revision, or a consumed grant invalidates it (forged/replayed/stale grants fail). `auto` mode only takes effect when the person enabled `authorizeAutoContinue` on that run; plan edits cannot relax this, and imported runs never carry the authorization.
- `approveAndAdvance` is the desktop's single-click path (issue + consume atomically). `approveWithRedraft` is the desktop's one step for a checkpoint that has a redraft (see The retro and the redraft loop).
- Advancing the final sprint completes the run and the epic (records the outcome). The final gate checks every required ticket of the plan, not only the final sprint's.
- Checkpoint reads and advances first expire overdue leases, so the gate never shows an expired claim as still holding a lease.
- `grantRetry` (desktop) allows one more attempt for a ticket in this run and returns an `awaiting_checkpoint` run to `running`.
- `retryTicket` (MCP `retry_ticket`, capability `ticket.auto_retry`, the orchestrator only; `src/core/services/autoRetry.ts`) is the orchestrator's own extra attempt for a ticket its retry limit holds right now (`conflict` otherwise), in an active run this machine owns. It needs a `failureReason` and a `newApproach` of 20 to 2000 characters once trimmed, both stored with claim and grant tokens masked, and refuses (`conflict`) an approach any run of the epic already tried for the ticket, ignoring case, spacing and punctuation. It adds the attempt to `retry_grants` as `grantRetry` does, resumes an `awaiting_checkpoint` run, and logs `ticket.retry_granted` with `grantedBy: "orchestrator"`, both texts and `autoRetry: <n>`. The plan policy `autoRetryLimit` (default 3, never stored by default, so older plans keep their hash) bounds it per ticket over every run of the epic on this machine (the count is read from the machine-local event log, as `retry_grants` is, so a takeover or transfer to another machine starts it again; every `ticket.retry_granted` event with `grantedBy: "orchestrator"` for that ticket and epic counts, so canceling the run and starting a new one resets neither the count nor the tried approaches; the person's `grantRetry` stays per run); past it the call fails with `retry_escalation_required` and only the person's `grantRetry` adds attempts, which never use up the orchestrator's budget. The desktop ticket panel lists each orchestrator retry with an Acknowledge button (`acknowledgeAutoRetry`, human-only `ticket.retry_acknowledge`, a `ticket.auto_retry_acknowledged` event) that records only that the person read it; an unread retry is an info count and gates nothing. Timing labels the wait before an orchestrator retry `queue` / `awaiting_orchestrator_retry`, never `human_approval`.
- Idempotency keys make repeated advance calls return the original outcome.

### Sprint retros

- A sprint report may carry a `retro` (the sprint review and retrospective): `delivered` (`{ ticket, demo, evidence }`: what to look at and where), `wentWell`, `wentPoorly`, `actions` (process changes for the next sprint), `discoveries` (`{ title, body, ticket? }`: new work found), `leftovers` (`{ ticket, reason }`: required work not accepted) and `tierFit` (`{ ticket, verdict: right_sized | oversized | undersized, note }`). Every list is optional on input. A `ticket` is a ticket id or display key; the server resolves it against the run's pinned plan, stores the stable id, and refuses an unknown ticket with `invalid_input` naming the field (`retro.leftovers[0].ticket`). The retro is part of the report content, so it is in `contentHash`; types are in `src/shared/domain/retro.ts`, resolution and the search text in `src/core/plan/retro.ts`.
- The `retro` gate belongs to a sprint with an acceptance node (plans saved before nodes are unaffected). It is met when the sprint's latest report revision has a retro with at least one entry in some list, so a later revision that leaves the retro out puts it back to unmet and its earlier approval does not carry over. It sits after the node gates and before `exit_criteria`.
- A report read as `SprintReportView` adds `tierFacts`, one entry per ticket of the sprint, computed from the run's attempts on every read (never stored, never in the content hash; `src/core/plan/tierFacts.ts`): `size`, `plannedLevel`, `plannedEffort` (null when the ticket sets none), each work attempt's `modelId`, `effort`, `label` and `fallback`, `attemptCount`, `rejectionCount` (rejected attempts only) and `escalated`. Carry-forward attempts are not counted. `escalated` means some attempt used a higher model tier (cost tier, then highest reasoning level, as `compareTier` orders them, using the run's host catalog) or a higher effort than some earlier attempt. Models are compared only when the catalog lists both and efforts only when both were recorded, so an attempt with no model and no effort (an orchestrator fallback, labelled "Orchestrator (fallback)") is listed, flagged `fallback`, and counted, but never ranked.
- **Redrafting the next sprint** (`redraftNextSprint`, MCP `redraft_next_sprint`, capability `run.redraft`: the orchestrator and the desktop; `src/core/plan/redraft.ts`, `src/core/services/redraft.ts`) turns the retro into the epic draft while the run waits at its checkpoint. It reads the retro of the latest report revision for the run's active sprint (`not_found` without a report, `conflict` for a report with no or an empty retro, `run_not_active` unless the run is awaiting its checkpoint) and rewrites the draft, never the saved plan or the run. Each leftover moves from the active sprint to the sprint after it, ahead of that sprint's acceptance node, together with the tickets of the active sprint that require it (transitively, in sprint order, listed as `dependentsMoved`); a sprint with its own acceptance node is added after the active one only when it is the last and something has to go in it. An explicit dependency of the active sprint's acceptance node on a moved ticket is dropped (`droppedDependencies`), because a node requires every required ticket of its sprint without one; the node itself never moves. Each discovery becomes an unsized ticket in the next sprint, after the moved tickets and ahead of the node, whose `references` hold the source ticket's display key (`{ kind: 'ticket', label: key, location: key }`). A leftover that is an acceptance node, is not in the active sprint, is already in the next one, is not in the draft or was accepted since the report, and a discovery whose title a ticket of the draft already has (ignoring case and spacing) or that has no title, is skipped and listed in `skipped` with a code and a reason, never refused. A second call over the same retro changes nothing (`changed: false`, same draft revision, no event). A change writes one `draft.redrafted` event. The result holds the sprints, `moved`, `dependentsMoved`, `added`, `skipped`, `droppedDependencies`, `changed`, `draftRevision` and the draft's validation (with the run-aware warnings); the orchestrator then sizes and describes the new tickets with `update_plan_draft`, writes the next acceptance node's `covers` criteria and validates the draft, and the person saves and adopts it with the retro's approval (see The retro and the redraft loop).
- Compatibility: a report saved before retros has no `retro` key; it reads with `retro: null` and keeps the content hash it was stored with. A report submitted without a retro stores `retro: null` (as `effort: null` is stored on a worker), so run history that holds one is not readable by an older build, whose strict schema does not know the key. The portable report schema gives `retro` no default (`nullable().optional()`), because a default of null would add the key to every earlier run history and change its bytes and tracked hash; a report written without one parses and re-exports exactly as it was (`legacyRecords.test.ts`). Retro text, with ticket keys, is indexed for search both when a report is submitted and when a run history is imported.
- **Improvement experiments** (`retro.experiments`; types `src/shared/domain/experiments.ts`, normalization and import checks `src/core/plan/experiments.ts`, events and reads `src/core/services/experiments.ts`). Beside the prose `actions`, a retro may carry structured experiments, each with every planning field required: `source`, `issue` (`{ summary, evidence }`, at least one evidence reference, each id checked against its kind), `hypothesis` (labeled as one), `destination` (`source_repository`, naming one repository only in a folder of repositories, or `darkmechanicus_source`; no machine path), `proposedWork` (at least one `{ title, body }`), `baseline` (`{ measure, unit }`, one of `EXPERIMENT_MEASURES`: the grade or a component score in points, or a frozen input such as `T.actual_ms`, `K.actual_tokens`, `E.corrective_ms`, `C.failed_checks`), `expectedChange` (`{ direction, amount, unit }`, in the baseline's unit or percent, never past 0 or 100 points), `guardrails` (at least one `{ measure, unit, comparator, threshold }`) and `window` (`{ basis: sprints | runs | tickets, count }`). **Sources.** `{ subject: { level, id } }` names a grade of the scorecard frozen with the very revision being submitted, so one submission carries the experiments and their scorecard: `submitSprintReport` drafts the grades first (`draftScorecard`; grades never read the report text), resolves the retro against them, hashes the content and only then seals the scorecard (`sealScorecard`). That source is stored as `{ revision: 'own', … }` with the grade's identity (epic, run, sprint, this report id and revision, snapshot id, policy hash, assessment id, subject, input hash) but without the report content hash and snapshot seal, which would be circular; the holding report row binds it. `{ reportId, assessmentId }` names a grade of an earlier revision's sealed scorecard of the same epic and is stored as `{ revision: 'earlier', … }` with that scorecard's report content hash and snapshot hash too. The server reads the baseline's value and state from the cited grade and refuses a measure it did not measure. A unit that is not the measure's, an unknown report, assessment or subject, a report from before scorecards, an absent field, an id listed twice, a repository that does not fit the project, and an evidence detail that breaks the metric ledger's text rule (`textProblem`, `src/core/space/ledger.ts`: one line of at most 200 characters, no token, credential or machine-local path) are refused with `invalid_input` naming the field. The server mints each id (`xp_…`); a reporter gives one only to restate an experiment of an earlier revision of the same sprint's report, citing its original source by `{ reportId, assessmentId }`. An experiment that a later revision of its sprint's report leaves out is withdrawn. The `experiments` key is written only when there is one, so a prose-only retro (or one sent with `experiments: []`) stores exactly what it did before experiments and keeps its content hash, and `retroIsEmpty` counts experiments only when there is one; the portable schema refuses an empty list. **Later events** (`recordExperimentEvent`, capability `report.submit`, on the machine that owns the run) are a `status` (`selected`, `scheduled`, `in_progress`, then a final `completed` or `abandoned`, after which the status no longer changes) or a `result` in the baseline's unit: read from a cited sealed grade at the baseline's level (a stated value must agree), or stated (never negative, at most 100 points, with at least one evidence reference). Notes and evidence details follow the ledger's text rule. A withdrawn experiment and a status after a final one are refused with `conflict`. Events are rows of `experiment_events` (schema v19), numbered 1..n per experiment, never written into a report: a report's content, hash and scorecard stay exactly as approved. Each event cites the report revision holding the definition it is about and that definition's content hash, and is exported with the run history under `experimentEvents` (left out when a run has none, so earlier run history keeps its bytes). **Import** refuses a run history whose events do not cite a definition its reports hold, report a result in another unit, skip a number, or differ from an event stored here in anything but its number, or take the number of a stored event that arrives changed, or put an experiment's stored events in another order (an event arriving with only another number, as a resolved fork renumbers it, takes that number here: see the two-machine rules below); whose reports redefine an experiment under events stored here (a stored event must still match the incoming definition); or whose experiments do not follow from the scorecards they cite (arriving or stored): the source must be exactly the reference the cited grade gives, the baseline exactly the value and state read from it, and a result read from an assessment exactly what it holds. `getExperiment` reads an experiment's latest definition, where it is written, its status (`proposed` before any status event), whether it is withdrawn, and its events.
- **Experiment and report history across machines.** A report written by an earlier build without later keys (such as `followUps`, or a follow-up's `body`) keeps the content hash it was written with: the import checks that hash over the content as written in the file and stores exactly that content (`sprint_reports.content_json`), the export writes back what is stored (`buildRunHistoryRecord`), and readers fill the defaults when they read it (`filledReportContent`), so a report imported on one machine and exported again imports on the next. Two limits are inherent: a machine that never stored a run's experiment events cannot tell that the last events of an experiment were cut from its history (the numbers left still run 1..n); a machine that holds those events imports the shorter history, keeps them as its own (numbered after the tracked ones) and exports them again (`insertExperimentEvents`), so they come back to the tracked file; and a report revision with no scorecard whose content was edited and re-hashed reads on a fresh machine as a self-consistent revision (its hash is its own), while a machine that stored the original refuses it (`changedReport`). An experiment in such a report must still follow from the scorecard it cites (`forgedSource`).
- **Corrective work from experiments** (`previewCorrections` / `createCorrections`, MCP `preview_corrections` (read) / `create_corrections` (`draft.edit`, plus `epic.create` for a follow-up epic); types `src/shared/domain/corrections.ts`, pure part `src/core/plan/corrections.ts`, service `src/core/services/corrections.ts`). Selected experiments of the latest revision of a sprint report become DRAFT work in the same repository: for an unfinished epic, a sprint appended after the draft's last sprint (default; its own acceptance node, human checkpoint) or an existing sprint after the report's sprint and any sprint a run in progress has reached; for a completed epic, the earliest open follow-up epic holding corrective work of it (whichever experiments the earlier requests selected; its first sprint while it was never saved, else a sprint appended last, plus a success criterion per new experiment), else a new backlog epic linked by `provenance` (the completed epic gets no draft). Each proposed work item becomes a ticket with the experiment's size, its body plus the experiment (hypothesis labeled, baseline, change, guardrails) and concrete criteria (editable before creation, with prerequisites); a Fireguard ticket per repository the work targets (tag `fireguard`, naming its repository in a folder of repositories; none with `fireguard: false`) requires that repository's corrective tickets, and the sprint's acceptance node gains a criterion covering each. Blocked: unsized or vague work (`executionProblems`; `vagueness` asks for 40+ characters, 6+ words, no leading placeholder marker on its own such as `TODO:` (a body about `TODO comments` is fine), no body that opens with "To be decided" or "To be determined" (another "to be …" such as "To be defined in limits.ts: …", or "to be decided", "soon", "eventually" or "TBD" later in a body, is fine), 3+ distinct terms beyond filler and generic scope words such as "quality", "code" or "whole project", and something the title does not already say; the preview carries the restatement to resubmit by id and original `{ reportId, assessmentId }`, `restatementOf`), a finished experiment, a `darkmechanicus_source` destination (cross-repository), and new work aimed at a named sprint that is missing (`not_found` on creation) or passed or in progress (`conflict`). Every created ticket carries a correction marker, a `doc` reference whose location is `darkmechanicus:correction/<source report>/<experiment>/<target>#work/<n>` (or `#fireguard`, `#fireguard/<repository>`) and whose hash is the request's payload hash; the server owns it (`src/core/plan/correctionMarker.ts`: a new ticket never brings one, `applyCorrections` attaches them; a references edit keeps a ticket's markers and never adds one, and is refused when the kept markers and the edit together exceed the 100 references a saved plan allows). Work already created is looked up first, in any draft or saved revision, and the key never includes a title or a report revision, so a repeat, a rename, a references edit, a report resubmission or a run reaching the named sprint answers `created` (`changed: false`, `createdIn` naming every epic that holds it), and a different payload or target for the same experiment is `idempotency_mismatch`. `expectedDraftRevision` is the target draft's revision the preview read: null refuses a draft opened since, a number refuses a draft changed or gone since (`conflict`); a repeat that adds nothing is never refused. Creation is one transaction (a failure leaves no epic or draft change); the `draft.corrected` event names the source run only for work in the source epic. Nothing is saved, adopted, started, approved, granted or continued: the person reviews the draft and uses Save, adopt (or Approve with redraft), run and checkpoint controls as usual, and `plan_current` keeps the checkpoint honest meanwhile. `scheduled`, `in_progress` and `completed` statuses all need sized, specific work.
- **Cross-repository corrective work** (types `src/shared/domain/crossRepoCorrections.ts`, core `src/core/services/crossRepoCorrections.ts`, desktop broker `src/main/desktop/crossRepoCorrections.ts`). An experiment whose destination is `darkmechanicus_source` becomes a **target-owned** DRAFT epic in the Dark Mechanicus source project, never in the source's own plan: one backlog epic per experiment and target project (no branch, never saved, no run; its first sprint holds the corrective tickets with their markers, a Fireguard ticket and the acceptance node's covers, human checkpoint), validated against the target before it is written. It carries portable provenance on the epic (`EpicProvenance` of kind `cross_repo_correction`, exported in the epic-state record once the epic is saved): the key `<assessment report>/<experiment>/from:<source project>/to:<target project>`, the payload hash, and the source project, epic, run, sprint, report revision and content hash, assessment, snapshot, policy hash and experiment, and the target project; ids and hashes only, never a path. The source keeps a machine-local **receipt** per key (`correction_links`, schema v20, deleted with the source epic, not exported): written `pending` with the fully specified draft (checked against the packet schema first, so a draft that would not fit a plan is `blocked` and stores nothing) before the target is touched, `linked` with the target epic and tickets afterwards (stored with `created: false`: only the creating call reports `created: true`), and counting attempts with the last failed step and error code (never a message, which may name a path). When the target accepted the work but the link failed, the pending receipt keeps that epic, and later deliveries require exactly that epic (`expected`; without one the earliest epic under the key is taken). Only the desktop reaches it, under the human-only `correction.cross_repo` capability: no command, MCP tool or grant does, and `createEpic` accepts only an earlier epic of the same project as provenance. A repeat of the same key and payload returns the same epic (`created: false`) on both sides; another payload is `idempotency_mismatch` (from the receipt, or from the target when this machine has no receipt); another target project for an experiment already requested is `conflict`. An experiment that was withdrawn or reached a final status forbids **creating** a target epic (`conflict`, `problem: experiment_closed`, not retryable: withdraw the request), never **recording the link** to one the target already holds: a retry still links it. The source epic, its draft, runs, reports and scorecards are only read. **Residual (duplicate epics):** two checkouts of one project each keep their own local database, and only saved, synced records carry the key from one to the other. A second epic for the same key can appear in another checkout (or in this one, after its epic was lost) when (1) the target committed but no source write landed (the link and its failure record both failed, or the process died in between), so the receipt names no epic, and another checkout is chosen before retrying; (2) a machine without this receipt (another machine, a rebuilt database) requests the same payload while its chosen checkout lacks the first checkout's records; (3) the person withdrew a request with `confirmUnverified` while its checkout could not be read, and the target had in fact accepted it; (4) the person asked for `recreate`. Once the first checkout's saved records reach the other, the shared key on both epics shows the duplicate.
- **Assessing corrective work against its experiment** (`ExperimentView.outcome` from `getExperiment` / MCP `get_experiment`, and `SprintReportView.experimentOutcomes` added only by `getSprintReport`, in the retro's order; types `src/shared/domain/experiments.ts`, pure classifier `src/core/plan/experimentOutcome.ts`, reads `src/core/services/experimentOutcomes.ts`, holder check `correctionHolderProblem` in `src/core/plan/corrections.ts`). Derived on read, never stored, never part of a report's content or hash; no report, scorecard or event is written. **Where the work is.** The epics holding an experiment's corrective work are its own epic, any follow-up epic whose `provenance.sourceEpicId` names it, and this project's own cross-repository correction epic for it when the active repository is the Dark Mechanicus source and was chosen as its own target (provenance of kind `cross_repo_correction` naming this project on both sides, the experiment's epic, the experiment and the key `<source report>/<experiment>/from:<this project>/to:<this project>`); each counts only when its markers (the newest saved revision holding them, else its draft) all carry the experiment's key for that target (`epic:<id>`, `follow-up:<id>` or that request key) and one well-formed payload hash. Its tickets are listed with the epic holding them and the attempt and run that accepted each (not superseded by an adoption), so a follow-up created as draft work is shown (and linked) before Save; the work **lands** when its last work ticket is accepted (with no ticket: its `completed` status), where a ticket held only in a draft of another epic never counts (a draft is local and unreviewed, so it never holds the landing back, and such an epic holds no result). **Results** (`recordExperimentEvent`) are read from a frozen grade of the experiment's epic or of another epic of this project holding the work in a saved revision (the scorecard is seal-checked and regraded on that write), and are always stored as the next event of the run whose report defines the experiment, so its events stay one numbered, append-only sequence beside the definition they cite. This machine may append when it owns that run, or, for a result read from a follow-up's grade, when it owns the run that froze that grade (a completed source run cannot be taken over); statuses and source-epic results need the source run's machine. **Two machines appending** to one run's history never drop each other's events: the finalizer refuses (`conflict`, the entry waits) to write a run's history over a tracked file this machine has not imported when another machine owns the run, or, for a run it owns, when that file holds experiment events it does not store; the reconcile then takes them in (a run this machine owns with changes waiting merges only the arriving events, checked as on any import but against the reports stored here, which are the owner's and may hold a restatement not exported yet; on another's run, its own unexported events are kept) and numbers this machine's events that the tracked history lacks after the tracked ones, queuing the run history for export, so the next export writes both. A fork Git resolved by keeping one side recovers the same way, and any other machine that imported a renumbered event under its old number takes the new one when the resolved history arrives (an event arriving with nothing but another number; an experiment's stored events must arrive in the order they are stored, so a renumbering that moves one past another is refused). Statuses of one experiment recorded on two machines cannot be ordered and are refused; an event arriving with other content than stored, or taking the number of a stored event that arrives changed, is always refused. **Import** of a result citing another epic's grade checks that epic as above (arriving snapshots or saved revisions here). An epic or cited scorecard that is not here (deleted, or never shared) does not hold the run history back: the event is imported and its outcome reads the scorecard as not here, and once it arrives every read checks the result against the grade it cites (`resultProblem`), so a result that does not match is not read. **Comparison.** The baseline (value, state, the cited assessment, the scope's sample size, size mix and window), the target (the baseline moved by the expected change) and the guardrails are listed beside every `result` event. A result is **placed** when it cites a frozen grade here at the baseline's level, other than the baseline's own, whose window starts once the work landed and is among the next `count` sprints, runs or tickets (the window's basis) that started after it in the epic holding that grade. A guardrail breached on a placed result makes it **regressed** and decides the experiment's outcome, even when the result's own value is missing or estimated and even when a later result is clean (a lower token or time total with a failed quality guardrail never counts as improved); a breach on a result that is not placed does not count. Otherwise a result is **insufficient evidence** when it is not placed, has no value, either side is estimated, the units differ, a score was graded under another policy than the baseline, it is a stated value, or the task scope differs: a run, sprint or epic's additive measure (counts, milliseconds, tokens) is compared **per ticket in scope** and needs the same share of each planned size on both sides (3 medium matches 4 medium; unsized tickets count as one size, `unsized`), a ticket's total compares only with a ticket of the same planned size. Else a move of at least the expected change toward the target is **improved** (insufficient evidence while any guardrail cannot be read), at least that much the other way **regressed**, anything less **unchanged** (six-decimal comparison). The outcome is the latest result with a counted breach, else (unless the experiment was abandoned) the latest comparable result (`decidedBy`), except that it is never improved while any result cites a frozen grade that cannot be read here (not here, failing its seal, or not what the result states): that grade may hold a breach, so the outcome is insufficient evidence; a stated value cites no grade and holds nothing back. Every outcome is labeled `observational`, with a caveat: a before/after difference over different work is not proof of cause. **Cost.** Only `getSprintReport` and `getExperiment` compute outcomes (the checkpoint, run and gate reads built on `latestReport`, and corrective-work checks, which read `experimentStanding`, do not); a read parses each cited scorecard once and checks its seal, never regrades, and treats one that does not parse or match its seal as not here (insufficient evidence), so a report read never fails on it. Report views read through `getSprintReport` (the epic workspace's sprint reports) show each experiment's outcome, target, corrective tickets (by their key and title in a follow-up epic, which is named), landing and every result's before/after with sample sizes and size mix, change, guardrail verdicts, evidence and reasons (`retroView.ts`, `RetroSections.tsx`); the checkpoint's own report, read with its gate, leaves them out.
- **Results from a correction epic in another project** (the Dark Mechanicus source chosen as a separate checkout). The desktop brings the correction epic's sealed scorecards, scope starts, corrective tickets (with their accepted attempts) and planned sizes back onto the source's linked receipt (`recordCrossRepoResults`, `correction_links.evidence_json`, local; cleared whenever the receipt is linked to another epic); `getExperiment` lists them as `crossRepoResults`, except a receipt of this very project (its correction epic in another checkout of it): those grades are cited directly once that checkout's records arrive through Git, and `recordExperimentEvent` refuses them with that hint. A result may cite one of those grades only while the receipt links that very epic (`carriedEvidence`; otherwise an unknown report, with a hint to bring the grades back): the event then carries it as `ExperimentResult.crossRepo` (`CrossRepoResultEvidence`), bound to this project's request (its key is `crossRepoCorrectionKey(experiment, <this project>, <target project>)` with a target project other than this one, the scorecard, starts and tickets all of the cited epic, and the cited scorecard's own scope starts exactly those the scorecard holds) and sealed over every field (`crossRepoSealOf`). The seal is **tamper-evident only**: an edit that is not resealed is refused, one that is resealed is not caught. Only the scorecard is regraded; the accepted times, other scopes' starts and planned sizes are the target's word, which no machine of this project can verify, and the outcome's landing detail and the comparison's reasons label them as carried from the target. A self-targeted correction epic (above) is this project's own and is never carried. `crossRepoEvidenceProblem` (`src/core/plan/corrections.ts`) applies on the write (`recordExperimentEvent` stores nothing that reads or imports would refuse), on import (regrading the scorecard) and on every read (seals only); a result carrying `crossRepo` that cites no grade, or cites a grade of one of this project's epics, is refused, and the carried scorecard is read only after those checks pass. Evidence that fails a read's check is not here (insufficient evidence). A request for an experiment that cannot take new work (closed, aimed elsewhere, or its work not specific, recomputed on every create and retry) writes nothing to the source: its receipt is written, linked, only when the target already holds its epic.

### The retro and the redraft loop

The retro turns what a sprint left over and found into the next sprint's plan, and one approval by the person covers both the retro and the plan change. The pieces are above (the retro, `tierFacts`, the redraft) and below (the gates and the one-step approval); this is how they fit, in order.

1. **Report.** The reporter (`skills/sprint-reporter.md`) writes the retro from evidence: `delivered` with what to look at, an honest `wentWell` and `wentPoorly`, a `tierFit` verdict per ticket taken from the computed `tierFacts` (never from impression), `discoveries` lifted from the workers' structured notes (each has a title and a reason, `skills/worker.md`) and from review notes, `leftovers` with their reasons, and `actions` for the next sprint. The orchestrator submits it with `submit_sprint_report`, and the run waits at its checkpoint.
2. **Redraft.** The orchestrator calls `redraft_next_sprint`. Only the epic's draft changes: leftovers (with the tickets that require them) move into the next sprint, discoveries become unsized tickets there, and a sprint is added after a final one. The orchestrator then refines the draft with `update_plan_draft` or `update_ticket`: it sizes every new ticket, writes the `covers` criteria of the next acceptance node for the moved and the new items, and validates the draft (`validate_plan`). The run-aware warnings (`runAwareWarnings` in `src/core/plan/runWarnings.ts`) flag any change to a sprint the run has passed and any sprint inserted before the active one: the draft changes only future sprints, and a passed sprint is never edited (see the planner skill). This is the one place the orchestrator changes a plan that a run is executing, and it adds tickets only to later sprints. The orchestrator tells the person that the retro and the redraft are ready to approve in one step.
3. **Gate.** Two checks keep the approval honest:
   - `plan_current` (after `epic_outcome` and before `approval`; every sprint, with or without an acceptance node) is unmet while the epic's draft has changes the saved plan lacks (`changedDraftRevision`: a draft that equals the saved plan, as one just opened does, is no change) and while the epic's current saved revision is newer than the run's and not adopted. Its detail says which, and what to do: save the draft and adopt the new revision, discard the draft, or adopt the revision.
   - A report goes stale after an adoption. `report_submitted` is unmet again, with the reason, when the run's revision differs from the one the report was written for (`sprint_reports.revision_id`, a machine-local column) and the sprint's exit criteria changed, a required ticket was added, or a required ticket left by a route other than moving a retro leftover or a ticket that requires one (`sprintScopeChanges`, `src/core/plan/sprintScope.ts`). A new report revision is then due. A report that did not record its revision is never stale. Moving the retro's leftovers out, and adding tickets to later sprints, leave the report current.
4. **Approve retro & redraft.** `approveWithRedraft` (desktop only: capability `checkpoint.approve`, and it also requires `plan.save`, `run.adopt` and `checkpoint.advance`, which no agent role holds, so an agent is refused with `unauthorized` before anything is saved; there is no MCP tool for it, and agents can never approve) takes `{ runId, expectedDraftRevision, reportId? }`, where `reportId`, when given, must still be the sprint's latest report (`conflict` otherwise). In order: (1) **save** the draft (overdue leases are expired first; saving an unchanged draft is fine) and flush the outbox so the revision is saved and current (`save_pending` if it is still pending); (2) **adopt** the saved revision into the run, unless the run already executes it (moved leftovers get a fresh retry budget: `freshBudget`); (3) **recompute** every gate on the adopted revision, so the moved leftovers no longer count; (4) **approve** the report, issuing a grant bound to the adopted revision; (5) **advance**, consuming the grant. The save commits on its own, because a file write cannot be rolled back with a database transaction. Steps 2 to 5 run in one transaction: a refusal at any of them rolls all four back, so the run stays on its old revision with nothing approved or advanced, the saved revision stays saved, and the error names the step (`details.step`, `stepNumber`, `savedRevisionId`, `savedRevisionNumber`, `adoptionNeeded`). The result holds `save`, `adoption`, `approval`, `advance` and the `run`. On the final sprint with the redraft's added sprint, it advances into that sprint instead of completing the epic, because the gates are recomputed on the adopted plan where the active sprint is no longer the last. The desktop's button for it is "Approve retro & redraft"; "Approve & advance" stays for a checkpoint with no redraft.
5. **The acceptance-node limitation.** In a sprint with an acceptance node, a required ticket that is not accepted (a leftover) keeps the node from ever being ready, because the node requires every required work ticket of its sprint (`implicitPrerequisitesOf`, `src/core/plan/acceptance.ts`). The node can therefore never be accepted while the leftover is in the sprint, `acceptance_accepted` stays unmet, and `approveWithRedraft` stops at its recompute step and rolls the adoption back: the moved leftover no longer blocks on the adopted plan, but the node has not run and is not accepted there. The code allows this route instead (the orchestrator's side is in the built-in facts `skills/knowledge/orchestrator/required-leftover.md` and `required-leftover-finish.md`):
   1. Submit the report with the retro, listing the leftovers. `submitSprintReport` accepts it while the run is `running` or `awaiting_checkpoint` whether or not the gates are met.
   2. Redraft, refine and validate the draft as above.
   3. The person saves the draft and adopts the new revision in the desktop app. `adoptRevision` needs no open attempts. The leftovers and the tickets that require them leave the sprint, the unchanged accepted tickets keep their acceptance, and the run stays in `awaiting_checkpoint`; the sprint stays the active one because it survives under its id.
   4. The run takes no claims in `awaiting_checkpoint` (readiness reports a `run_state` blocker), so the orchestrator calls `pause_run` (allowed from `awaiting_checkpoint`) and `resume_run`, which returns a started run to `running`, and then runs the acceptance node over what remains like any other: it is ready once every remaining required ticket is accepted and no row check is failing.
   5. The orchestrator submits a new report revision (`submitSprintReport` moves the `running` run back to `awaiting_checkpoint`) with the retro carried again. The gates do not force it, since moving leftovers out does not make the first report stale, but the first report predates the node's acceptance and increment, and a grant is bound to one report's id and hash.
   6. The person approves. The draft was saved and adopted, so `plan_current` is met and no draft remains for `approveWithRedraft` to save: the plain "Approve & advance" applies.

   Where the leftover is in the final sprint, the redraft adds a sprint after it, and once the revision is adopted the active sprint is no longer the last, so `epic_outcome` is no longer asked of it.

### The project's Definition of Done

- A project's Definition of Done is the team's one standard of "done": ordered checks `{ name, command, description }`, stored once in `.darkmechanicus/project.json` (`definitionOfDone`, optional with no default, so a project record written earlier parses and re-serializes unchanged). It is written only by `setDefinitionOfDone` (tool `set_definition_of_done`, capability `project.definition_of_done`, held by the planner and the desktop; the orchestrator reads it through `getProject` but does not hold the capability, because it accepts work against the standard) and through the app's own writer (`src/core/repo/projectConfig.ts`: sorted keys, two-space indent, trailing newline, atomic replace; an empty list removes the key). It is read from the file on every use (`Ctx.definitionOfDone()`), so a change by another session or by hand applies at once; `getProject` returns it as `definitionOfDone`. Names must be unique ignoring case and surrounding spaces, at most 50 checks.
- The execution packet of a sprint acceptance node lists the checks (`definitionOfDone`) and adds a reporting instruction; no other ticket's packet carries them.
- The `definition_of_done` gate belongs to a sprint with an acceptance node, when the project has a Definition of Done (with none, the gate is left out and sprints are gated exactly as before). Dark Mechanicus runs no command: it reads the `evidence.checks` of the node's accepted, non-superseded attempt (not one awaiting review). A check passes when the evidence names it, matching trimmed and ignoring case (never by containment), at least once and every entry under that name has status `passed`; the gate's detail names each check that was not reported, failed, or was skipped.
- In a folder of repositories the project has no list of its own: each repository has its own `definitionOfDone` in its `repositories` entry (written by `setDefinitionOfDone` with `repo`). The acceptance node's packet lists each touched repository with its checks, the node reports them as `<repo>: <check>`, and the gate checks every touched repository's list by those names.

### SPACE grading contract

- Scorecards grade a ticket, run, sprint or epic on seven equally weighted components (S, P, A, C, E, execution time T, tokens K) under a versioned Dark Mechanicus policy informed by SPACE, not an official SPACE formula. The rubric, the direct-versus-proxy table, the status rules (ungraded without verification, F cap on a confirmed mandatory failure, provisional when incomplete) and the baseline rules are in [space-grading.md](space-grading.md).
- Who records, checks and reviews each input (the person, the planner, worker, reviewer, orchestrator and sprint reporter, and the server), the evidence hierarchy, which agent integrations emit usage, and the anti-gaming limits are in [space-grading.md](space-grading.md#who-records-checks-and-reviews); the role guides in `skills/` and the orchestrator's `orchestrator.space-*` knowledge facts (skills version 1.12.0) teach each role its part. The operator runbook for corrective work and its recovery is [runbooks/corrective-work.md](runbooks/corrective-work.md).
- Contract types live in `src/shared/domain/space.ts`, runtime validation in `src/core/space/contract.ts`, policies v1 and v2 (registered by content hash, `spacePolicyByHash`; `CURRENT_SPACE_POLICY` is v2, whose only change is C's rule `C.handoff-pass-rate.v2`) and the reference grader `gradeSpace` in `src/core/space/rubric.ts`, baseline selection in `src/core/space/baselines.ts`, and reference fixtures in `src/core/space/fixtures/` (`policy-v1.json`, `policy-v2.json`). Observations, baselines and frozen grade snapshots have stable ids with the `mo`, `bl` and `as` prefixes.
- **Ticket grade** (`getTicketGrade`, `read`; `src/core/services/spaceGrades.ts`, types in `src/shared/domain/spaceGrades.ts`): one ticket's grade in a run as of a cutoff, assembled only from the server's read models in one transaction at one cutoff (S, A and C from `getSpaceSignals`, P from the ticket's performance read, E, T and K from the run's efficiency) and graded by `gradeSpace`. It returns the input, the grade and the three source views. The dispatch time comes from those reads' lifecycle records, never a caller; when the two reads name different first dispatches the earlier is used (a baseline frozen between them is refused) and the disagreement is listed in `anomalies`.
- **Run, sprint and epic grades** (`getRunGrade`, `getSprintGrade`, `getEpicGrade`, `read`): every ticket of a run is graded once with the run's plans, attempts, observations and lifecycle log loaded once (`gradeRunTickets`, `SignalsCache`, `ticketPerformanceReader`), then each level is graded from its own raw measures: roles frozen at first dispatch (acceptance nodes and tickets tagged `administrative`, `fireguard` or `overhead` are integrated overhead), a confirmed failure of any counted outcome capping at F, outcomes kept by the sprint that incurred them and never erased by a later run without an attempt, E/T/K from the runs that executed work, and T/K against a roll-up of the ticket baselines counted once per scope (partial and provisional when a feature ticket has none). Rules: [space-grading.md](space-grading.md#run-sprint-and-epic-grades).
- **Scorecards** (`src/core/services/scorecards.ts`, schema in `src/core/space/snapshot.ts`): `submitSprintReport` freezes the revision's scorecard in its transaction into `sprint_reports.scorecard_json` (schema v18; null for earlier reports, which stay ungraded): grade inputs pooled by content hash and compact results, the policy hash, plan revision, report hash, frozen timing and efficiency inputs and source ids, sealed by `snapshotHash`. The report view lists it at a glance; `getReportScorecard` regrades every stored input under the stored policy (which must give the stored result back) to return the explanations; `reassessReportScorecard` is the dated reassessment. In `repo` mode the finalizer writes each scorecard once as `history/<runId>/scorecards/<reportId>.json` before the run history, which names it by id and seal; the importer refuses a missing, tampered or re-sealed scorecard that does not match its run, epic, sprint, report revision, plan revision or subjects.

### Metric observation ledger

- Table `metric_observations` (schema v17) holds one immutable row per SPACE observation: the contract record as stored (`observation_json`), its scope ids, metric, source kind and measurement state as lookup columns, and `payload_hash`, the observation without its `recordedAt`. Nothing updates or deletes a row; deleting an epic deletes its observations with it. A correction is a new observation. The v17 migration only adds this table and the `metric_observation` outbox and sync-state kind (rebuilding both tables the way v13 and v14 did); no plan, report or other record changes, so their content hashes and files stay byte for byte.
- `recordObservations(ctx, observations)` (`src/core/services/observations.ts`) records up to 500 observations atomically: all, or none on the first refusal. The server assigns `recordedAt` (a supplied one is refused) and, when none is given, an `mo_` id greater than every id recorded at the same instant and than the call's previous one, so a call reads back in call order (reads order by `recordedAt`, then id) here and after export and import; a caller-supplied id orders by its own value. `observedAt` is normalized to UTC (one instant, one form) and repeated evidence is listed once. A stored id with the same payload is returned unchanged with its original `recordedAt`; a different payload under that id is `conflict`. Each observation must parse against the contract, and every scope id must resolve: the epic exists with a saved plan and the run belongs to it; with an attempt, the attempt is that ticket's attempt in that run and the sprint and ticket are in the plan revision the attempt ran under (`attempts.revision_id`, which adopting a newer revision never rewrites); without one, they are in any saved plan of the epic, so work stays attributable after a ticket is moved or removed. Evidence references must name records this project holds, of the observation's epic when it has one, and never the observation itself; a baseline reference cannot resolve until baselines are stored. Unknown references are `not_found`, mismatched ownership `invalid_input`. Attempts in every state stay attributable (rejected, failed, canceled, expired, superseded), but execution metrics (tokens, active, elapsed and wait time, corrective effort, activity volume) on a carry-forward attempt are refused: it ran nothing, so its work's usage stays with the attempt that did it. Who may report what is the calling command's decision. `listObservations(db, filter)` reads them in recorded order.
- Storage rules (`src/core/space/ledger.ts`): a server observation names no actor and every other source names one; `observedAt` is in UTC; evidence never cites the observation itself or one record twice. Every free text (actor, estimate method, usage parent, evidence detail, attribute names and values) is one line of at most 200 characters, so no transcript fits, and may not hold a claim or grant token, a credential (provider and cloud keys, bearer and basic auth, JWTs, private key blocks, `password=…`-style pairs) or a machine-local path (any absolute POSIX path of two or more segments or a known system root, drive and UNC paths, `~/`, `$HOME`/`%USERPROFILE%`-style homes, `file://`). Attribute names containing a credential word or pair (`secretKey`, `pwd`, `apiKeyValue`) or ending in `token` are refused, as are string attributes named like chat text. Missing values are stored without a number, so unknown stays distinct from zero and from estimates.
- Export: one immutable file per observation, `epics/<epicId>/observations/<observationId>.json`, or `observations/<observationId>.json` at the top of `.darkmechanicus/` for a project-level one (format `darkmechanicus.metric-observation` v1, holding the observation as stored). A `metric_observation` outbox entry is queued with the row; the finalizer writes the file once (`writeOnce`): an existing file must hold the same observation (same payload; another machine's record of the same delivery differs only in `recordedAt` and is kept), so an export interrupted after its write completes on retry and a different file is a `conflict`, never overwritten. Entries stand alone like comments, and an epic's observation waits while the epic's records are not in the checkout. In `db` mode the entry completes without a file. Switching a database-only project to repository files writes every observation of a saved epic and every project-level one.
- Import: after epics and runs, the importer reads the project-level folder and each local epic's `observations/` as untrusted input (containment, regular files, at most 256 KiB and 50,000 files per folder, names from valid `mo_` ids, the strict schema with the storage rules, id and epic matching the path, a `formatVersion` this build knows). New observations are checked like recorded ones, evidence resolving only against observations already stored or inserted by this import (in passes, so file order does not matter and nothing imports citing a file that did not), and inserted with `sync_state` kind `metric_observation`. One already here with the same payload is only marked synced and the local row stays; a different payload, or one id in two folders, is rejected and reported, never overwritten. Each bad file is rejected on its own.
- Escaped defects (`escaped_defect`) follow a defect vocabulary enforced with the storage rules, on record and import (`defectProblem`, `src/core/space/defects.ts`): each record belongs to an epic and names its `defectEvent` (`report`, `duplicate`, `reassessment`, `fix`, `withdrawal`); a report names severity, attribution, discovery phase, its source build commit and an origin fitting its attribution, and every later record cites a report instead of changing it. An attributed origin attempt must be an accepted work attempt of the origin ticket (`invalid_input` otherwise). Records that change charging (an attributed report and every later record) need a `human` or `server` source or the server's review stamp (attribute `authority: review`), which `recordAttemptMetrics`/`recordRunMetrics` add only for a session holding `attempt.review` (orchestrator, reviewer) and refuse from callers; a worker's is `unauthorized`, and an unstamped agent or host one is refused on import and ignored on read. `getEscapedDefects` and `getTicketPerformance` (`src/core/services/performance.ts`, read-only, capability `read`; no command or MCP tool yet) build the P inputs as of a cutoff from times written once (decision and lifecycle columns, the event log's failure, cancel, takeover and retry-grant times, the frozen Definition of Done); the rules are in [space-grading.md](space-grading.md#verification-and-escaped-defects-p-inputs).

### Metric ingestion and planned budgets

- Agents and external MCP hosts report usage through `recordAttemptMetrics` (capability `metrics.report`: worker and orchestrator) and `recordRunMetrics` (`metrics.report_run`: orchestrator and reviewer), MCP tools `record_attempt_metrics` and `record_run_metrics` (`src/core/services/metricReports.ts`). Both capabilities are agent-only. A worker presents its live claim token and reports only that attempt; the claim is fenced exactly like a heartbeat (`stale_claim` for another attempt's token, a superseded or closed attempt, `expired_claim` after the lease), and a worker without a token is `unauthorized`. An orchestrator may report any attempt of a run this machine owns without a token, in any state, so a host with no built-in chat adapter can relay actual usage. Orchestration, review and verification overhead goes to the run's bucket (scope level `run`, optionally with a `sprintId`, attribute `overhead`), never to an attempt. Both commands check the coordinating branch like other writes.
- Only sources `agent` and `host` are accepted, and only metrics those sources may record; a human source, a human metric (`human_rating`, `rescue_minutes`, `human_review_minutes`) or a server-derived one (`verification`, `scope_*`, `handoff_check`, `elapsed_ms`) is `unauthorized`. Each report states its unit, which must be the metric's. Its delivery identity derives its `mo_` id (`derivedStableId`, `src/core/ids.ts`): scope, source kind and actor, metric, and the `sequence` of a cumulative report or the source `eventId` of a delta or event (stored as attribute `sourceEvent`). A resent delivery is listed as unchanged and counted once; the same identity with another payload is `conflict`. A stream (scope, source, metric) keeps one accumulation, and a cumulative value never falls below an earlier sequence's or rises above a later one's.
- `getRunMetrics` (`get_run_metrics`, `read`) answers each executing attempt's usage (every claimed work attempt, whatever its state; carry-forward attempts are listed apart) and the overhead bucket's, per token metric and `active_ms`: a cumulative stream counts its latest report, deltas add, and a stream whose actor is nested under an `inclusive` parent counts once. Each cell's coverage is `observed`, `estimated`, `unavailable` (only `host_unavailable` reports) or `unreported`, with a null value when nothing numeric came. A run total is `observed`/`estimated` only when every executing attempt reported a number; otherwise it is `missing` (`partial_coverage`, `host_unavailable` or `not_reported`) and `reportedValue` is a lower bound. `includeObservations` lists the stored observations (at most 2,000) with their provenance.
- A ticket's planned `budget` (`tokens`, `activeMs`; `src/shared/domain/bundle.ts`) is a draft field like any other (`update_ticket` with `budget`, `null` clears it) and appears in the plan diff. Saving freezes it: each saved revision that changes a ticket's budget for a metric is a new version, frozen at the revision's server save time, with a `bl_` id derived from revision, ticket and metric, so the versions are append-only, travel with the plan snapshots and are named alike on every machine (`src/core/services/plannedBaselines.ts`; nothing is stored separately). `getPlannedBaselines` (`get_planned_baselines`, `read`) pins them: a dispatched ticket uses the version in effect in the revision of its first claim in the run (frozen strictly before that claim), an undispatched one the run's revision; later versions are `prospective` and an unsaved draft edit shows against the epic's current saved revision. Adoption ignores the budget when it compares tickets, so re-budgeting never supersedes accepted work. Metric evidence may cite a budget version by its `bl_` id.
- A budget states where its numbers came from (`basis`: `person_estimate`, `planner_estimate` or `prior_tickets`; a label, never graded). Only the desktop session may introduce `person_estimate` or change the amounts of a budget while it keeps that label: `updatePlanDraft` (and so `setTicketBudget`, which goes through it) refuses any other session that would leave a ticket with a `person_estimate` budget different from the draft's, with `unauthorized`, and writes nothing (`assertPersonEstimates`, `src/core/services/drafts.ts`). An agent may still leave such a budget as it was, replace it with a `planner_estimate` or `prior_tickets` budget, or clear it; either change shows in the plan diff the person reviews before Save.
- Usage read details: the overhead kind is part of a run-level report's delivery identity and stream; a delivery that an agent and its host both report (same actor and `sourceEvent` or `sequence`) counts once, the host's; nesting under an `inclusive` report is resolved across the whole run for totals (a child attempt's `self` usage under a run-level inclusive parent counts once); a missing report beside numbers makes the cell `partial` (value a lower bound) and the total `missing`; each total carries `overheadCoverage`, and `unreported` overhead means none was counted, not that none was spent. Graders consume only a planned budget's `applied` baseline, never a saved but unadopted version.

### Human feedback, committed scope and handoff quality (S, A, C)

- **Human feedback** (`recordHumanFeedback`, `src/core/services/humanFeedback.ts`; input types in `src/shared/domain/spaceSignals.ts`) records a person's rating (1–5) of a ticket (optionally in one run) or of a sprint (a run named beside a sprint only places it: once per sprint), rescue minutes (`rescue_minutes`: an intervention and a cause, both required of every new entry; older imported entries without a cause stay readable) and planned review or playtesting minutes (`human_review_minutes`, with its `activity` `review` or `playtest`; never an intervention, never a rescue, never scored) on an epic, sprint, run, ticket or attempt. Minutes are optional (absent: stored `missing`/`not_reported`, never 0) and, when given, at least 1 (`MIN_FEEDBACK_MINUTES`) and at most 2,400. It needs capability `feedback.record`, which is human-only (only the desktop holds it, and the session must be the desktop's), and the branch guard; an idempotency key makes a retry record once. The source is `human`; the actor is the person the desktop names (else the desktop session's label), with attributes `desktopSession` and `machine`; `observedAt` is the server's clock; an attempt target takes its run, ticket and sprint from the attempt. A sprint rating must say whether it is shared with the sprint's tickets (`sharedWithTickets`); a ticket rating may not, and overrides a shared sprint rating for that ticket only. Corrections are new entries; the latest per scope counts. Agents cannot record any of them: the MCP metric tools refuse `human` sources and human-only metrics (above). The desktop calls it as a command on its IPC channel (see the score commands below); no MCP tool offers it.
- **Handoff checks** are server-derived when a submission is stored (`submitAttempt`, and `reconcileAttempt` with `resubmit`), in the same transaction (`recordHandoffChecks`, `src/core/services/spaceSignals.ts`; the rules are pure, `src/core/space/handoff.ts`): `criteria_evidence` (every acceptance criterion of the ticket, in the revision the attempt ran under, has an evidence entry with a note, met or not), `verification_checks` (at least one check, and every Definition of Done check of a single repository's acceptance node, matched by `checkNameKey` like the `definition_of_done` gate: trimmed, ignoring case) and `outputs_contract` (a summary; artifacts, commits or changed files; a branch for commits; an artifact when the ticket expects some). Each is one `handoff_check` observation (1 pass, 0 fail) scoped to the attempt, with attributes `missing` (a JSON list of the whole missing items that fit 200 characters) and `missingCount`, and the submission (and each missing criterion) as evidence. Ids derive from attempt, submission time and check; once stored they are that submission's record, so asking again (even after a review merged its criteria into the evidence) changes nothing. They never depend on the review, so a submission canceled or expired before review keeps its checks. Measurement never blocks the lifecycle: the checks are recorded in a savepoint, and when the ledger refuses them (a full ledger, a Definition of Done name its storage screens refuse) nothing is stored and the submission goes on unchecked, which C reads as not reported. Three outbox entries (one file each) per checked submission.
- **Coordination defects** (`coordination_defect`) must cite a run record (an attempt, run, check, report, comment or observation), and one that names itself a clarification (attribute `kind: clarification` or intervention `clarification`) is refused: a purposeful clarification is not a coordination failure (`src/core/space/ledger.ts`, so imports apply it too).
- **Reading** (`getSpaceSignals`, `read`): the S, A and C grader inputs of a ticket or sprint within a run, a run, or an epic (every run), from records stored by a cutoff (now when absent, never later), each with the records behind it (`SpaceSignalsView`). S takes the latest ticket rating and the latest rating of the sprint that held the ticket at its first dispatch (a run or epic: its only sprint's), with rescue entries listed. A freezes the scope of the revision the subject's first work claim ran under (`attempts.revision_id`); a ticket's scope is frozen with its sprint's (the sprint's first claim, when that plan already held the ticket there; else the ticket's own first claim). A ticket commits its acceptance criteria by id and text (compared ignoring case and runs of whitespace, so a casing or spacing edit is the same criterion and substantive rewording is not); a sprint, run or epic its tickets by id, without acceptance nodes, optional tickets and tickets carried forward before the first claim with no work attempt of the subject's own. A committed ticket is delivered only when its standing acceptance (accepted, not superseded, by the cutoff; for a carried-forward ticket, looked up across the epic's runs) verified every criterion the ticket held in the frozen revision, with the same text, so trimming or rewording a ticket cannot deliver it. Every undelivered committed item says why (`ScopeItem.undelivered`): `not_accepted`, or `criteria_unverified` with each criterion the acceptance did not verify, `not_met` (held but not verified met) or `changed` (the accepted revision holds no such criterion). The plan the run held at the cutoff (the local event log's adoptions, else the run's revision) gives `removed` (kept in the denominator) and `added` (listed apart). C counts the checks of the subject's submissions by the cutoff and the defects in its scope; any submission without checks makes the handoff count unavailable (`null`, so C is `not_reported`), none makes it zero (`no_handoffs`). Every deduction links to its check observation, the submission and its review decision, or to the defect and the records it cites. Sprint membership follows the revision each attempt ran under (a sprint an adoption renamed is matched by ordinal); a record naming a ticket but no sprint (or no run) counts for the sprint and run holding that ticket, and a sprint-level record without a run for the run whose plan holds the sprint.
- **Score read commands and desktop measurement controls** (`src/core/commands/scores.ts`, types in `src/shared/domain/scoreReads.ts`): `getTicketGrade`, `getSprintGrade`, `getRunGrade`, `getEpicGrade`, `getReportScorecard` (pinned to one report revision: `frozen` with its snapshot, or `legacy`; never live data), `reassessReportScorecard`, `getSpaceSignals`, `getTicketPerformance`, `getEscapedDefects`, `getRunEfficiency` and `getRunTiming` (`projectRunTiming` as of a validated, clamped cutoff; `ticketId` keeps only that ticket's entry) (`read`) return the core read models unchanged; the desktop allow-lists them with `getRunMetrics` and `getPlannedBaselines`, and every MCP role reads them, with `getMetricsSummary`, through the read-only tools of `src/mcp/tools/metrics.ts`. Desktop-only writes: `recordHumanFeedback` and `recordEscapedDefects` (a person's defect records, source `human`, server-ordered ids, all or none; both `feedback.record`), and `setTicketBudget` (a draft edit, `draft.edit`, stale `expectedDraftRevision` → `conflict`; `savePlan` freezes it as a prospective version). S entries carry their provenance (`recordedBy`: `this_machine`, `other_machine`, `unattested`) because portable records are not authenticated, and a handoff-check refusal at submission is logged (`attempt.handoff_checks_refused`) and listed in C's read (`CollaborationSignal.unchecked`). See `docs/space-grading.md`, "Reading scorecards and the desktop's measurement controls".

### Comments

- Comments are append-only Markdown notes on an epic (`ticketId` null) or one of its tickets, written by people (desktop) and agents (MCP). There is no edit or delete (deletion stays deferred product-wide). Table `comments` (schema v3), ids with the `cm` prefix.
- `addComment({ epicId, ticketId?, body, idempotencyKey? })` needs capability `comment.write`, which every role holds; `listComments({ epicId, ticketId? })` needs `read` and returns comments oldest first (`created_at`, then id): without `ticketId` every comment of the epic, epic-level and ticket-level; with it only that ticket's.
- The author is the calling session's role and label (the label cut to 200 characters), never input. The body is Markdown, not blank, at most 20,000 characters (`commentBody`). A `ticketId` must be in the epic's current saved plan or its draft (else `not_found`). Completed epics refuse new comments with `completed_epic`; their comments stay readable. The branch guard applies, and an epic holds at most 10,000 comments (`capacity_exceeded`), the most a reconcile reads back.
- Each comment appends a `comment.added` event (payload: comment id and author) and a search document of type `comment` (title "Comment by <label>", body the Markdown), so `search_history` finds comments and labels them.
- Export: one immutable file per comment, `epics/<epicId>/comments/<commentId>.json` (format `darkmechanicus.comment` v1), so writers on different machines never touch the same file. A `comment` outbox entry (epic id, entity id = comment id) is queued in the same transaction; the finalizer writes the file with `writeFileSafely`. An existing file must hold the same comment (else `conflict`, never rewritten). Comment entries never block, or wait for, their epic's plan records. A checkout whose tree lacks the epic's `current.json` (a branch without the epic) gets no comment file, since a folder holding only `comments/` would be rejected by every reconcile: the entry fails with a retryable message and is exported once the epic's records are back (for example, after checking out the epic's branch); the epic's records are never written there for it. Like the epic itself, comments of a never-saved epic stay local: completing the epic's first save queues every comment without an export record, and the finalizer runs up to three passes so entries queued while flushing are written by the same flush.
- Import: for every epic whose own records are not rejected, the importer reads `comments/` as untrusted input: containment and link checks, regular files only, at most 256 KiB per file and 10,000 files per epic, names `<commentId>.json` built from validated ids (dot entries and other names such as temp files are ignored), the strict schema, and an id and epic matching the path. Each bad file is rejected on its own. New comments are inserted, indexed, and recorded in `sync_state` (kind `comment`); an id that already exists with different content is a conflict (reported with its epic, never overwritten) that clears once the file matches again. A comment waiting for export does not count as an unexported epic change.
- Desktop: the ticket panel's Comments tab lists a ticket's comments (author, role, time, body through the safe Markdown renderer) and, for open epics, adds one.

### Named capability profiles

- A named profile is a reusable, provider-neutral `CapabilityProfile` preset (for example `ui-implementation` or `deep-review`) that tickets start from. It names no vendor or model; an exact model stays the `preferences.modelOverride` preference, as on tickets.
- **Names** double as file names (`profiles/<name>.json`), so they are portable on Windows, macOS, and Linux: 1-64 lowercase letters, digits, and hyphens, starting and ending with a letter or digit, and never a Windows device name (`con`, `prn`, `aux`, `nul`, `com0`-`com9`, `lpt0`-`lpt9`). `src/core/profileNames.ts` holds the rule; the owned-path builder, the command schemas, and the record schema all apply it.
- **Commands:** `listProfiles` (sorted by name) and `getProfile` (`not_found` when missing) need `read`. `saveProfile` needs `profile.write` (desktop, planner, orchestrator), honours the branch guard and idempotency keys, and replaces the whole profile: it creates at revision 1 when `expectedRevision` is absent or 0 and replaces only at the current revision; anything else is `conflict`. The description has at most 500 characters (omitted means empty); the capability is complete and validated with the ticket schema, and its skills are normalized like a ticket's. Each save appends `profile.saved` and queues a `profile` outbox entry keyed by name (`outbox.entity_id`).
- **Revision** is the local database's optimistic-concurrency counter and is not tracked: a clone starts at 1 and every import bumps it.
- **Tickets copy profiles.** Applying one (the desktop editor's "Start from profile", or an agent passing a profile's `capability` to `create_ticket`/`update_ticket`) copies the requirements into the ticket; later profile saves never change existing tickets or saved revisions. The desktop writes only on Apply, and "Save as profile…" stores the requirements shown under a name. Apply writes only the requirement groups the person changed since the editor loaded the ticket (through a field or a profile; `context` per field); the others keep the draft's latest values, so it never reverts an agent's concurrent `update_ticket`.
- Deleting profiles is deferred like every other deletion.

### Kanban cards

- A Kanban card is an isolated ticket on the folder's board: not an epic and not a plan ticket. Table `kanban_cards` (schema v13), ids with the `kc` prefix; its key comes from the project's ticket sequence (`nextProjectKey`, allocated inside the write transaction), so no card and plan ticket share a key. Lanes: Backlog, In progress, Ready for review, Done (`src/shared/domain/kanban.ts`).
- `createKanbanCard` (title, body, acceptanceCriteria, expectedArtifacts, references, priority, size) and `updateKanbanCard` (`cardId`, `expectedRevision`, the fields to change; `size: null` clears it) need `kanban.write` (desktop, planner, orchestrator), honour the branch guard and idempotency keys, and validate with the ticket field schemas. A new card goes to Backlog at revision 1, authored by the calling session's role and label. Criteria get `c<n>` ids like a ticket's. An edit is allowed only for a Backlog card that has no attempt (otherwise `invalid_state`), at its current revision (otherwise `conflict`).
- Each write appends a `kanban_events` row (`created` or `updated`, with the actor) and a workspace event `kanban.created` / `kanban.updated` whose payload carries `cardId` and `key` and no epic.
- `listKanbanCards({ doneLimit?, doneCursor? })` and `getKanbanCard({ cardId })` need `read`. The board holds slim summaries only (never a body, criteria or evidence): open lanes by priority (critical first), then creation time; Done by completion time, newest first, `doneLimit` 20 by default and 100 at most, paged with the opaque `doneNextCursor`. `getKanbanCard` returns the full card with its revision and every attempt, oldest first; no view carries the claim secret.
- **Play and claim** (`src/core/services/kanban/attempts.ts`). `playKanbanCard({ cardId })` needs `kanban.play` (human-only). It marks a pending play (`play_requested_at`, `play_requested_by`) on a card in Backlog, or In progress with no open attempt; pressing it again changes nothing, and Ready for review, Done or an open attempt return `invalid_state`. `claimKanbanCard({ cardId, leaseSeconds? })` needs `kanban.claim` (orchestrator), a pending play (`play_required` otherwise) and no open attempt (`already_claimed` otherwise). It consumes the play, creates attempt n+1 with a claim secret, a lease (900 seconds by default) and this machine's id, moves the card to In progress, and returns a `KanbanPacket`: the card content, the `<attemptId>.<secret>` claim token (null on an idempotent replay), the checkout's branch, every earlier kick-back comment in order, reporting text naming `heartbeat_kanban_card`, `submit_kanban_card` and `fail_kanban_card`, and the project's Definition of Done.
- **Reports.** `heartbeatKanbanCard`, `submitKanbanCard` and `failKanbanCard` need `kanban.report` (orchestrator, worker) and the claim token, checked as a plan attempt's is (`verifyClaimToken`: `stale_claim`, `expired_claim`). A heartbeat extends the lease by the length the claim holds and keeps the latest progress note. Submit stores the outputs and evidence (`submitAttempt`'s shapes) and moves the card to Ready for review. Fail leaves the card In progress with no pending play. The token and its bare secret are masked wherever the agent pasted them into a note, outputs, evidence or a reason, and so is any other claim token: a note as a plan attempt's note is (`maskNote`), and a report, which is stored as given, by whole tokens only (`maskWholeClaimTokens`), so an attempt id in a path is kept.
- **Lease expiry** is lazy, as a run's is (`expireKanbanLeases`, run by Play, claims, reports and board reads): an overdue `claimed` or `running` attempt becomes `lease_expired`, and the card stays In progress, where a person can press Play again.
- **Review.** `approveKanbanCard({ cardId })` and `kickBackKanbanCard({ cardId, comment })` need `kanban.review` (human-only) and a card in Ready for review (`invalid_state` otherwise). Approve accepts the attempt and moves the card to Done with `completed_at`, `compacted_at` and its compact summary (`summary_json`: the submission summary on one line, cut to 280 characters; the commits; completedAt; approvedBy). Kick back needs a comment (not blank, at most 20,000 characters), rejects the attempt with it as `review_comment`, and returns the card to In progress with a pending play.
- Each transition appends a `kanban_events` row of its attempt (`played`, `claimed`, `running`, `submitted`, `failed`, `lease_expired`, `approved`, `kicked_back`; the payloads carry the outputs, evidence, reason, comment and summary, never the claim secret) and a workspace event `kanban.<kind>`. A later heartbeat's progress note appends only a workspace event, `kanban.progress`. The event row's time is the time the transition wrote into the card and attempt rows, so a card rebuilt from its events gets the same timestamps.
- **Records** (see [Repository-owned persistence](#repository-owned-persistence)): in `repo` mode every event and every create or edit queues an outbox export in the write's transaction (`kanban_event`, `kanban_card`); in `db` mode the finalizer settles them without a file. An attempt imported from another computer keeps that computer's id; this computer refuses its heartbeat, submit and fail with `card_not_owned` (checked before the token) and never expires its lease, which only the claiming computer can extend.

### Sprint learning cards

The post-sprint codification loop, end to end. Storage and authority are enforced by the services named here; the shipped guides (`skills/orchestrator.md` loop step 4, facts `orchestrator.advance-sprint` and `orchestrator.learning-card`, `skills/worker.md`, `skills/reviewer.md`, `skills/sprint-reporter.md`) tell agents the same timing and limits.

- **Timing.** Every successful checkpoint advance, the final one too, writes one generated card inside the advancing transaction (`src/core/services/sprintLearningCards.ts`, DM-937): a `sprint_learning_cards` row (unique per run and sprint) links it to the epic, run, sprint, report, pinned revision, checkpoint, the immutable evidence snapshot (`learningEvidence.ts`: rejected, failed and reconciled attempts, failed row and acceptance checks, the retro's went-poorly items and actions) and the completed increment of each affected repository. The card is queued with a pending Play for the run's orchestrator and the advance result and run view carry it as `learningCard`. A replay or an alternate advance path returns the same card. It never gates the next sprint: the run is already running the next sprint, and the orchestrator claims the card before its ordinary `get_ready_tickets` polling, as one worker job, then continues the loop while it runs.
- **Packet and branches** (`src/core/services/kanban/learningCards.ts`, `learningBranches.ts`, DM-938). `claim_kanban_card` on a linked card adds `learning`: the stored snapshot and bases (nothing is collected again) and one isolated branch per base, `learnings/<cardKey>/<repo|root>`, with a `git worktree add` instruction rooted at the recorded increment. The same branch is named on a retry, a replayed claim and a reclaim after a lost token (`fail_kanban_card` without `claimToken` releases a live claim and requeues the card; reclaim with a new idempotency key). Claim packets also carry the published learnings that apply (DM-936, `selectLearnings` within `DEFAULT_LEARNING_BUDGET`, separate from the facts' budget) as text and provenance only: a learning grants no capability and never changes fact precedence.
- **Submission.** `submit_kanban_card` requires a `learning` block on a learning card and refuses one on an ordinary card: exactly one disposition with a reason per snapshot item (`learning`, `duplicate`, `not_reusable`), drafts (`learningDraftSchema`: bounded title, rule, check, applicability over roles, events and safe repository-relative paths, cited evidence) that cite only `learning` items and cite all of them, staged by `stageLearningDrafts`, and one manifest per base that `verifyLearningManifests` proved read-only against Git (recorded base, isolated branch, commit exists, descends from the base, is the branch tip). The verified manifests and `draftsHash` are stored in `evidence.learning`; nothing is merged, and the card stops at Ready for review.
- **Authority.** Only a person activates learnings. The desktop's single approval (`window.dm.approveLearningCard`, `src/main/kanban/approveLearningCard.ts` around `src/core/services/learningApproval.ts`, DM-950/952/956) approves the exact card, attempt and staged drafts hash: it prepares one integration this machine owns (`learning_integrations`: `prepared` → `integrating` → `integrated` → `published`, or `conflicted` / `aborted` with `failure_json`), integrates every affected repository with each receipt recorded before the next starts, and only then approves the card to Done, publishes the drafts and marks the integration published in one transaction. No MCP tool approves, publishes, retires or replaces a learning; agents read them with `list_learnings` and `get_learning`.
- **Multi-repository recovery.** The native plan, which names absolute checkouts, is kept machine-locally (`meta` `learning_integration_plan:<li>`, never exported) and every core step rechecks this machine's authority. Startup recovery continues only operations this machine owns that stored a plan, from that plan and Git's actual heads, never starting a second operation or publishing twice. A conflict records the failure, posts a card message and leaves the card in Ready for review with its isolated branches untouched and nothing published; the person resolves it and approves again. Portable records (`learnings/records/<lr>.json`, `learnings/integrations/<li>.json`, DM-935) import strictly per file, and an imported manifest never activates a learning.
- **Lifecycle management** (DM-933/946). Published learnings appear in **Knowledge → Learnings** with their source run, sprint, card and attempt and their append-only history. Only the person (`learning.manage`) retires one with a reason or replaces it with new content at the revision they read; retired and replaced learnings leave packet selection at once.

### Agent mail

As-built design, trust model and recovery: [`design/skitarii-messaging.md`](design/skitarii-messaging.md); current real-app [verification procedure](design/skitarii-messaging.md#verification).

- **Generated guidance** (`skitariiMailGuidance` in `src/main/agents/cliInstructions.ts`): `writeTerminalFiles` appends it after the collaboration policy, and before any run, transfer or card guidance, to the instructions of every OMP chat start (`skitariiMail`, set from the connected agent's kind). It is constant text written before the grant is issued, so it names the native tools and CLI commands, says how to check whether this launch has a mailbox, and treats peer text as task data; it never holds the grant, an endpoint id or peer text, and the instructions file stays `0600`.
- **Store** (`src/core/services/agentMailStore.ts`, schema v15): endpoints, bindings, messages and body-free send receipts, local-only (see [Storage decision](#storage-decision)). It takes explicit endpoint ids and infers no caller authority.
- **Authority** (`src/core/services/agentMail.ts`). Six agent commands (`getAgentIdentity`, `listAgentPeers`, `sendAgentMessage`, `readAgentInbox`, `acknowledgeAgentMessages`, `getAgentMailStatus`) need `mail.use`, which the planner, orchestrator, worker and reviewer hold. It is necessary, never sufficient: the caller's mailbox is derived from the session's persisted `sessions.grant_id` (set only for a `dm` CLI session that redeemed a grant), which must be usable now, bound by the desktop to an open endpoint, and bound on this machine in this canonical folder. That check runs inside the same `BEGIN IMMEDIATE` transaction as the send, acknowledgement or snapshot read, before the store reads its clock, so a revocation, expiry or closed binding that commits first is always seen. A reader, an MCP stdio session (whose `grant_id` is null even with an inherited `DM_SESSION_TOKEN`) and an unbound grant get one indistinguishable `unauthorized`. `getCapabilities` reports `mailbox` as `{bound:true, endpointId}` or `{bound:false, reason}` so discovery never promises a mailbox that is not there. No input names the caller's mailbox; schemas are strict. Sends retry on the sender-scoped `clientMessageId` receipt, never `withIdempotency` (whose key has no sender). Nothing logs or emits events, and no error carries a body or a peer's title.
- The mail commands declare `mutates: false`: their writes are local-only, so they skip the portable flush and branch guard and run their own service transactions. The flag authorizes nothing.
- **Desktop management** (`mail.manage`, human-only, desktop-only): provision, bind, rename, suspend, resume, close and delete endpoints; the person's inbox page (`readHumanAgentInbox`), seen cursor (`markHumanAgentMailSeen`, only to a message actually served) and metadata state. A binding needs a current hosted-role grant of this machine; a closed binding never reopens, so rebinding takes a fresh grant.
- **Automatic context delivery** (`agentContextDelivery.ts`, `conversationDeliveries.ts`, native `contextDelivery.ts`/`messaging.ts`): durable exact source/folder/chat/message/body-hash/host-entry proof is separate from acknowledgment and human seen. Peer bodies stay agent-attributed inert JSON; trusted board bodies are saved before scheduling and reach a private outbox bound to the stored endpoint and authenticated own identity. Full pinned batches enter at awaited preparation/tool boundaries or native asides; idle peer+person work starts with a person/user prompt so actual user preparation includes both before request one. Same-chat restart reconciles real host entries before rescheduling; uncertain physical input and unreadable context remain pending/blocking, never fake delivery or endless replay. Historical schema-v16 wake tables remain inert for compatibility, with no active manual-wake service/API.
- **Restricted poll mode** (`OpenWorkspaceOptions.mailPoll`, selected only by the `dm` CLI for status and own identity): needs the `cli` transport and a grant bound here; redeems the grant and maps the binding's one dedicated session (`agent_mail_poll_sessions`, schema v16) under one write lock, so concurrent first polls create one row; skips record reconcile, portable flush, staged-image pruning and local directory creation; refuses every command but those two before parsing its input; touches `last_seen_at` in the poll's transaction and never ends the shared session on close. Migration and the current grant and binding are still checked on every poll. Poll sessions whose grant, binding or endpoint ended are retired in batches of 100 when a new poll session is created and on every desktop mailbox change (deleted when no activity references them, otherwise ended); ordinary sessions are never touched.
- **Chat lifecycle** (`src/main/agents/chatMailboxes.ts`, main process, through each folder's desktop workspace). Only OMP (Skitarii) chats have a mailbox, decided by the stored chat agent id and, at a start, the connected agent's kind; no other CLI's chat and no grant issued outside a chat start is ever bound, and native subagents share their parent's grant and mailbox. The endpoint is keyed by (machine, chat id) in the chat's folder database, its id stored on the chat record (`ChatRecord.endpointId`, written without moving `updatedAt`); a crash between the SQLite commit and that index line finds the same id again, and rename, restart and New session keep it. The trusted chat list provisions every OMP chat (legacy ones too) and resumes one an untrack suspended; `chatGrants.issueChatCli` binds each fresh grant before the CLI is spawned, only while the folder is still tracked with the workspace the grant came from, and revokes a grant whose binding fails; revoking closes the binding first. Deleting a chat records the irreversible deletion (a tombstone even for a chat never provisioned), purges its received mail and leaves its sent mail with a deleted sender before the chat's files and index lines go; if storage cannot record it the chat stays and the delete can be retried. A chat whose mailbox is deleting is never provisioned again: listing leaves it out and finishes it, and startup (`ChatRecords.recoverFolder`) finishes every such deletion and deletes the open mailboxes this installation provisioned (`userData/agents/mailboxes.jsonl`) for chats whose record is gone, never one it did not. Untrack (`TerminalSessions.releaseFolder`) refuses starts in the folder, stops its PTYs and starts, waits for their kills and revokes, suspends its mailboxes and only then forgets the folder; quit and agent removal end grants, never mailboxes.
- **Skitarii native client** (`resources/skitarii/extension/dmClient.ts`, run by OMP's Bun; descriptor in `src/main/terminals/terminalFiles.ts`). After an OMP chat's grant is bound to its mailbox and before the spawn, main writes a private, versioned descriptor for that launch, `userData/agents/omp/<chat id>/dm-client/<generation>.json` (0600; earlier launches' removed; removed again when the launch ends or its start fails; the chat's deletion removes the folder). It pins the absolute runtime (this build's executable, run as Node with `ELECTRON_RUN_AS_NODE=1` on that child only), the absolute `cli.js` with `--repo <folder>`, the folder as working directory, `DARKMECHANICUS_HOME` and the names of the variables the child inherits; never the grant, the naming address or a shell command. Only that launch gets `DM_SKITARII_CLIENT_DESCRIPTOR` (its path); every other launch and sign-in terminal has the variable scrubbed in any letter case. The extension spawns `<runtime> <cli.js> --repo <folder> call <command> -` with `shell: false`, JSON input on stdin and the chat's current `DM_SESSION_TOKEN`. Its mail-specific `call` allowlists the six mail commands and is bounded to 5 s, 2 MiB of stdout and 4 KiB of sanitized stderr. The published general `run` path backs native `dm_call` with `DM_RUN_LIMITS`; command-name validation and the server's existing grant role/authority checks still apply, so it grants no extra powers. Provider keys and runtime-injection variables never pass. An abort or session shutdown cancels in-flight operations and kills their children; cancellation during a private board descriptor/outbox read cannot authorize or spawn afterward. A missing, malformed, other-version or other-chat descriptor is refused, never replaced. The descriptor routes; the grant authorizes.
- **Delivery Standards per model request** (`resources/skitarii/extension/projectStandards.ts`). OMP asks for context before every model request, and the extension injects the project's Delivery Standards from `get_project`. Every context event of a chat shares one in-flight read, and a successful read is reused for 60 s (`STANDARDS_CACHE_MS`). When a refresh fails, a successful read younger than 10 min (`STANDARDS_STALE_MS`) is injected instead of the failure notice. Each read's CLI child has an absolute 30 s lifetime (`STANDARDS_LIFETIME_MS`, `DmRunOptions.lifetimeMs`) that writer contention never renews, so no `get_project` process outlives it.
- **Native naming route.** Only `name_chat` / `nameChat` children additionally receive the launch's `DM_DESKTOP_PIPE`, read from the chat's environment at the call boundary alongside its current grant. The address stays out of the descriptor and every other native command's child environment; the general `DM_*` inheritance ban remains intact. The desktop still authenticates the exact live chat generation and rechecks its grant before publishing metadata.

## Repository-owned persistence

```text
.darkmechanicus/
  .gitignore                          # "local/" — the live database never enters Git
  project.json                        # project id, name, key prefix, format version, optional Definition of Done
  epics/<epicId>/current.json         # saved-revision pointer + content hash + generation
  epics/<epicId>/state.json           # epic status, branch, outcome, ticket statuses (durable)
  epics/<epicId>/snapshots/<revId>.json  # complete immutable plan bundles
  epics/<epicId>/comments/<commentId>.json  # one immutable file per comment
  epics/<epicId>/observations/<observationId>.json  # one immutable file per metric observation
  observations/<observationId>.json  # project-level metric observations (no epic)
  history/<runId>/run.json            # run, attempts, reports, checkpoints, row checks (no leases, tokens, or grants)
  history/<runId>/scorecards/<reportId>.json  # one immutable frozen scorecard per report revision
  profiles/<name>.json                # named capability profiles (darkmechanicus.profile records)
  kanban/<cardId>/card.json           # a Kanban card's definition, key, author and generation (darkmechanicus.kanban-card)
  kanban/<cardId>/events/<eventId>.json  # one immutable file per card transition (darkmechanicus.kanban-event)
  history/<runId>/attachments/<sha256>.<ext>        # evidence images of a run's attempts, with <attachmentId>.json beside each
  kanban/<cardId>/attachments/<sha256>.<ext>        # a card's reference images and its attempts' evidence images, same sidecars
  epics/<epicId>/attachments/<sha256>.<ext>         # images on the epic's comments and plan tickets, same sidecars
  local/                              # Git-ignored: state.sqlite(+wal/shm), machine.json
```

- Files are pretty, key-sorted JSON (`prettyJson`) for reviewable diffs; hashes use canonical JSON (`contentHash`).
- **Image attachments** ([decision 0006](decisions/0006-image-attachments.md)). The `attachments` table (id prefix `im`) holds each PNG or JPEG's bytes in SQLite in both storage modes, with its owner (attempt, kanban attempt, comment, Kanban card or plan ticket), purpose (`evidence` or `reference`), size, hash and who staged it. An agent stages an image with `add_attachment` (a file in an allowed folder) and the app with `uploadAttachment` (bytes from a paste, drop or file picker); the record that names the id claims it, and an unclaimed image is pruned. In `repo` mode the finalizer writes an owner's images before its record, as `<sha256>.<ext>` in the owner's `attachments/` folder, with a sidecar `<attachmentId>.json` (`id`, `sha256`, `createdBy`, `createdAt`) recording who staged it. Records list their images as `attachments` (id, hash, mime, size, label, purpose) and omit the key when there are none, so records without images keep their bytes and hashes. Import checks every file (size, image type and dimensions, hash against the record, sidecar against the file name) and restores the bytes and who staged them; a missing or invalid file leaves the reference with `missing: true`. The app shows images through the `dm-attachment:` protocol, served from SQLite.
- A run's `rowChecks` list is optional and has no default: a run without row checks exports without the key, so history written before row checks existed still imports and re-exports byte for byte. Each entry carries its id, number, sprint, row, commit, entries, who recorded it and when; the importer stores them in `row_checks` and refuses a run that lists a check another run already owns.
- **Finalizer** (flush, `src/core/repo/finalizer.ts`): processes `outbox` entries in id order, in passes (bounded) that pick up entries the flush itself queued. In `repo` mode each entry is exported in two steps, so the write lock is held only to rename and record:
  1. **Staging, outside the lock.** The export runs in a read transaction and collects its file changes. A save builds the state its hook will leave from the read-only `previewSavedRevision`. Image bytes are loaded and SHA-256-checked here, and listing queries do not select the blob. Each new file is written to a temp file under `local/staging/` (named with the entry id, a counter and the process id), fsynced and read back. Staging writes nothing to the database.
  2. **Commit, one short `BEGIN IMMEDIATE`.** It runs the save hook (`completeSavedRevision`) once and checks that the entry still waits and that the tracked records may be written over (below). It then collects the entry's changes again from the rows as they are now, reusing the snapshot record staging built, and requires each change to be staged with identical content. Only then are the temps renamed into place, in order with the pointer last, the export recorded and the entry completed. A previous snapshot is never rewritten in place, and an image already in place is checked by its file stamp.
  - A failed rename or completion puts the replaced tracked files back inside the transaction, before `ROLLBACK` releases the lock; only a failing `COMMIT` restores them after the lock is released. The last good pointer and every earlier snapshot stay intact, and the entry stays pending for an idempotent retry. A process that dies between staging and its commit leaves temps, which the next `repo` flush removes once that process is no longer running.
  - When the commit finds content that a concurrent write changed, it rolls back, stages just those files and commits again, at most twice more (`MAX_RESTAGES`). After that the entry waits for the next flush, with no error, and holds back the later entries of its records.
  - **Backoff** (schema v30, `outbox.next_attempt_at`): a failed entry waits 15 s, doubling to at most 5 min, and its failures keep counting past the five-attempt `failed` state, so it reaches the cap. A scheduled flush (the one after a mutation, and after open) skips it, together with the later entries of the same epic, run or keyed record, until then. An explicit flush (`flush_portable_state`, the desktop Flush) retries it at once. A reconcile's closing transaction clears the wait (`releaseBackoff`) for entries whose epic, run, comment, profile or card it imported, and for every entry when it acknowledges a branch change. Records it found unchanged keep their backoff. A failed entry blocks only the later entries of its own records; other records continue.
  - In `db` mode an entry is settled in one transaction, with no file. The filesystem is injected so tests can fail each write boundary.
- **Unimported epic records are never overwritten.** Before it writes an epic's `state.json` and `current.json` (and before a save's snapshot), the finalizer checks the Linear transfer hold first (unchanged), then hashes the files on disk (`trackedEpicHash`) and requires the hash to be the `exported_hash` or `imported_hash` of the epic's `sync_state` row, or one its export intent names: what this machine last wrote or read. The export intent (`local/exports/<epicId>.json`, machine-local) lists the hashes an export may leave on disk (new state over the old pointer, both new, new pointer over the old state) and is written before anything is replaced, so a process that dies before its row commits does not lock itself out; a failed write also puts both files back. It covers only that uncommitted export: it is removed once the entry commits, and it counts only while the epic's `sync_state` row is still the one it was written against, so after a branch round trip or a stash and pop that reconciled other records, this machine's earlier export is not trusted. A checkout without the files has nothing to lose; files with any other hash, or with no row and no intent, were written elsewhere and not imported here, so the entry fails with `conflict` and waits. Reconcile reports the epic's pending-export conflict; storage status marks it `resolvable` while the condition still holds. Only the person settles it: `resolveEpicConflict` (desktop only, human-only capability `repo.resolve_conflict`, no MCP tool; the Storage card's **Keep tracked records** and **Write local**). Keeping the tracked records first flushes the epic's waiting run histories, then, in one transaction that writes no file, drops the epic's waiting state export and any waiting save (revision marked `failed`, draft kept) and imports the tracked records, or changes nothing. Writing local commits the choice (exactly the found hash as `imported_hash`), then flushes only that epic; a failed write is reported and retried by every flush; its attempt count stops at five. No file is written inside a transaction that can still roll back. One consequence: a change that waits while the checkout holds this machine's export from another branch (switch branches, an agent accepts work, then reconcile) now asks the person to choose instead of being written silently.
- **Initialize** is explicit and repeatable: creates the layout, `project.json`, `.darkmechanicus/.gitignore`, and `local/machine.json`; never commits.
- **Reconcile / import** (`src/core/repo/importer.ts`; open, clone, pull, branch change): every tracked file is untrusted — size limits, merge-marker rejection, zod schemas, stable-id checks, snapshot hash verification, full graph validation, and path containment. A rejected record is reported and leaves its last good state and drafts untouched. An `epics/`, `history/`, or `profiles` that is a link, resolves outside `.darkmechanicus/`, or is not a directory is rejected and reported and read as empty, so opening a repository (which reconciles) never fails on hostile layout. An epic whose tracked state changed while it also has unexported local changes is a **conflict** (surfaced, not overwritten). A branch change pauses active runs until reconciled. Unchanged records are not re-read on every heartbeat: an epic whose pointer and state match the last sync skips its snapshots, and each workspace remembers the stamp (size, modification and change times, inode; `FsAdapter.fileStamp`, which never follows a link) and hash of every comment and profile file it read, so a file keeping its stamp with a synced hash costs one `lstat` (`src/core/repo/fileHashes.ts`). A changed stamp, a link, or a hash that is not synced means a full read with every check. A reconcile runs in three phases, so SQLite's writer lock is held only to write:
  1. **Prepare, outside the lock.** In one read snapshot (`db.tx(fn, 'read')`) it decides which records to read (see Git-targeted reconcile), reads and validates them through an observing filesystem (`observeRepository`, `src/core/repo/reconcilePreparation.ts`, which remembers each stat, listing and body it saw and marks a file that changed while it was read), plans the import, and stamps each planned record's database state (`src/core/repo/recordGuard.ts`: its `sync_state` hashes, generation and conflict, its exports still waiting, and for an epic its open Linear transfer and pending plan revisions). Observation folders, recovered archives and attachment images are read and verified in the same snapshot.
  2. **No-op check, still without the lock.** In a read snapshot it asks whether applying would write anything: a record to stage, a conflict to store or clear, an observation, archive or image to apply, a problems digest, validated-cache proof, checkout branch, attachment registration or marker (head and importer version) that is not current, or a fingerprint that would change (`ReconcileGate.stale`). If nothing would be written, the reconcile returns its result and takes **no write transaction**. `last_reconcile_at` then stays as the last write left it, so the next reconcile's exports-since window only grows.
  3. **Apply, one short transaction per record.** Each changed epic (snapshots, state, ticket statuses and its tickets' attachments), run (with its evidence attachments), comment, profile and Kanban card (definition, events and rebuild) is applied in its own depth-0 `BEGIN IMMEDIATE`, epics before runs and comments. That transaction first checks that HEAD and the checkout are as prepared (`project.json` by its stamp: no body is read under the lock), that the record's own files still read as prepared (`unchangedUnder`), and that its stamp holds. A record that moved writes nothing and is prepared again, alone and outside the lock, at most twice (`OUTSIDE_PREPARES`). A run or comment of a stale epic waits with its epic, and a HEAD or checkout move prepares everything again. What still moves after that is left unsettled in the marker for the next reconcile, with no error to the caller. Observations, recovered archives and attachment images then apply in their own short transactions, each rechecking its row. A last short transaction stores conflicts, pauses runs on a branch change, and records **one** `repository.reconciled` event listing every changed epic. The event is recorded when the reconcile imported something, saw the branch change, repaired attachments, or reports conflicts or rejections other than the previous reconcile's (a digest in `meta`), so a file that stays rejected adds no event on every heartbeat. The same transaction advances the checkout branch, `last_reconcile_at` and the marker, releases export backoff (see Finalizer) and records or clears the fingerprint.
  - **Consistency contract: each record is all-old or all-new.** A record whose apply fails rolls back alone and is reported as rejected; the others stay applied. A reader may see some records of one reconcile before others (an epic already imported while its run is still being applied), never part of a record. A reconcile called inside a caller's transaction applies everything there, as prepared, because nothing else can commit in between.
  - Database-only (`db` mode) projects have nothing to reconcile.
- **Reconcile fingerprint** (`src/core/repo/reconcileFingerprint.ts`, meta key `reconcile_fingerprint`): the automatic reconcile on open and on heartbeat is skipped while its inputs are those of the last clean reconcile, so a one-shot `dm` process on a large project neither scans every tracked file nor holds the writer for it. The fingerprint covers the format and schema version, storage mode, the real checkout root and Git HEAD (branch, commit, detached), every entry under `.darkmechanicus/` except `local/` (path, kind, and a regular file's size, mtime and ctime in nanoseconds, device and inode), and the machine-local state an apply reads (open outbox entries, `sync_state` count, latest update and conflicts, pending plan revisions, open Linear transfers, epic count, attachment rows owned, without bytes or missing, the last attachment row, the attachment registration backfill and the recorded checkout branch). It is checked in a read snapshot before any scan and again in the read snapshot that decides whether the prepared reconcile would write anything (for inputs another session reconciled meanwhile); only a clean reconcile (no conflict or rejection) whose tracked inputs did not move while it ran records one, and anything else clears it, so a project with a standing rejection reconciles in full each time. An explicit reconcile is ungated; what it reads is described under Git-targeted reconcile. The branch guard is unchanged (a moved branch is never reconciled automatically), and the outbox is still flushed after every open. A rewrite that keeps a file's size, mtime, ctime and inode cannot be told apart, which is the same stamp the per-file hash cache already trusts.
- **Git-targeted reconcile** (`src/core/repo/gitChanges.ts`, `src/core/repo/reconcileScope.ts`; meta keys `reconcile_base_commit`, `reconcile_importer_version`, `reconcile_dirty_paths`). When the fingerprint gate misses, an automatic reconcile reads only the records that git reports as changed since the last reconcile. It runs `git status --porcelain=v2 -z --branch --no-renames -uall --ignored=matching` once in `.darkmechanicus/`, which gives HEAD's commit, the branch and the paths. Only when HEAD has moved from the marker's commit does it also run `git merge-base --is-ancestor` and `git diff --name-status -z --no-renames` between the two. A fresh git adapter first runs `git rev-parse` to find the repository, so a reconcile on one spawns two git processes, or four. The diff, the status and the marker's dirty paths map to records by layout: `epics/<id>`, `history/<runId>`, `kanban/<cardId>`, `profiles/<name>.json`, and the whole `observations/` and `recovered-attachments/` folders; `local/`, `knowledge/` and `.gitignore` are ignored. To these it adds `recheck`: every record holding a stored conflict (epic, run, comment, profile, Kanban card or event), and every record whose outbox export completed at or after `last_reconcile_at` (an export written and reverted in between leaves git nothing to report). Observation folders are read for the targeted epics and the project level. `recovered-attachments/` is read when git names it or an attachment row is missing its bytes. The scanners still list and bound each folder, then read only the targeted ids. The result has the same shape, and its `unchanged` lists only the records that were read.
  - **Fallbacks to a full read** (internal reasons, never errors): `no_marker` (none stored, malformed, or its path list was over the cap), `importer_version` (stored by another `IMPORTER_VERSION`, now 1, bumped whenever import semantics change), `not_ancestor` (a force-push, rebase or rewrite), `branch_changed` (the branch differs from the recorded one, or none was recorded), `unborn_head`, `not_work_tree`, `git_failed` (git missing or failing, or its answer missing), `project_record` (`project.json` changed), `unknown_path` (a path outside the layout, or with an invalid id or name), `ignored_path` (git ignores a record path, so it cannot report that path's changes), `requested` (the caller asked for a full read) and `record_deleted` (an `epic.deleted` or `kanban.deleted` event since the last reconcile: the deletion removed the rows and sync records, so a restored folder would leave git nothing to report).
  - **The marker** is written in the closing transaction. It holds the status's HEAD commit, this `IMPORTER_VERSION`, and the dirty-path list. That list holds the status paths (without ignored, `local/` and `knowledge/` ones) plus the paths of records left unsettled: rejected, in conflict, waiting on another record (a run whose epic was refused, a comment whose epic is not here yet), or still moving after the re-prepares. A rejected path that names no record is kept as shown, so full reads repeat until it settles. Over 5,000 paths (`RECONCILE_DIRTY_PATHS_LIMIT`) no list is stored and the next reconcile is full. Without a status (git failed, unborn HEAD) the marker is removed. A reconcile that throws leaves the previous marker. A no-op reconcile writes none: the marker advances only when a write happens anyway.
  - **Who reads everything.** Every explicit reconcile reads every record: `Workspace.reconcile()` passes `{ full: true }` for one, which covers the `reconcile_repository` command through the CLI and MCP, and the desktop routes its `reconcileRepository` command (the Reconcile button and the Forge World's `validateSource`) to the sync lane as an `explicit` reconcile, which is ungated and passes `{ full: true }` (`syncLaneCore.ts`). A storage migration imports into a fresh database, which has no marker, so it reads everything.
  - `GitAdapter.statusPaths`, `diffPaths` and `isAncestorSync` are synchronous, because reconcile runs inside synchronous opens and transactions; the adapter caches the work-tree prefix.
- **Desktop sync lane** (`src/main/desktop/workspacePool.ts`, `syncLane.ts`, `syncLaneCore.ts`, `syncLaneWorker.ts`): the desktop never reconciles on the connection that serves the screen. Each project utility opens its workspace without reconciling (`autoReconcile: false`, `deferOpenReconcile: true`), and runs every reconcile on a `worker_threads` Worker (`openWorkerLane`) with its own connection: WAL, `synchronous=FULL`, the same storage-epoch and Forge binding guard, and the owner's session and machine (it registers no session of its own). Reads and writes keep being served while one imports, and SQLite's writer lock still orders each of the import's short transactions against a write. `inThreadLane` keeps the lane's contract (own connection, admission, release, close), but not its concurrency, for in-process hosts and tests. A reconcile has one of three modes (`SyncMode`): `heartbeat` (the open-time reconcile and the 15-second heartbeat, `bootstrap.ts`: fingerprint-gated, and skipped after a branch change), `member` (a Forge member's import: gated, and it runs after a branch change) and `explicit` (the `reconcileRepository` command: ungated and full, reading every record, with its result shape unchanged). The owner checks the binding before and after, then flushes.
  - **Coalescing.** The pool keeps at most one running and one pending reconcile per project. Requests join the pending one, which takes the strongest mode (`explicit` over `member` over `heartbeat`) and any Forge transfer reservation a joiner carries. A heartbeat with nothing to join is skipped while a reconcile runs and within 15 s of the last one. Work that moves or replaces the store (initialize, storage switch, Forge export and retirement) waits for the lane and releases its connection; the next reconcile reopens it.
  - **Owner protection.** The pool serves the screen with up to two owner processes (`OWNER_LIMIT`), and at most three in all (`PROCESS_LIMIT`). The screen's explicit reconcile is admitted as foreground work; heartbeat and member reconciles and background jobs are background work. Background work never retires an owner the screen used in the last 60 s (`PROTECTED_MS`). When only that protection stands in the way, it opens the one process beyond the screen's slots instead of waiting; past that, it waits. An idle owner closes after 60 s.
- **Server identity** (`src/core/packageInfo.ts`, `src/core/installedApp.ts`): every session carries `serverInfo { name, version, packaged }`, and `get_capabilities` reports it as `server`. The MCP (`darkmechanicus`) and CLI (`darkmechanicus-cli`) entries read `version` from the package.json two folders above their script and set `packaged` when the script path has an `app.asar` segment (`isPackagedScript`); the desktop owner (`darkmechanicus-desktop`) passes Electron's `app.getVersion()` and `app.isPackaged`, which reach its utility process as the `packaged`/`unpackaged` argument. A missing `packaged` reads as false, so a dev build never stands for the installed app. That path test is the recording process's own claim, not a security boundary: an agent can run a script from any folder named `app.asar`. The desktop therefore also records its own observation, the machine-local `meta` key `installed_app` (`{ version, packaged, machineId, observedAt }`), whenever its owner opens an initialized project or initializes or moves one; no command writes it. `readInstalledApp` returns it for the current machine (null when absent or malformed), for delivery verification to prefer over the recording session's `serverInfo`.
- **Profiles** are exported by the finalizer like the other records (`writeFileSafely`, export hash in `sync_state` with `kind = 'profile'`; a failed write blocks later writes of that profile only) and imported by `src/core/repo/profileImport.ts`, each staged profile in its own short reconcile transaction (see Reconcile / import). Dot entries and names not ending in `.json` (such as the temp file of an interrupted export) are ignored, as in `comments/`; a `.json` entry that is not `<valid-name>.json`, a link, a junction resolving outside, a directory, an empty file, a file over 256 KiB, or a record that fails the strict schema or names another profile than its file is rejected and reported without stopping the rest; more than 1,000 entries rejects the directory unread. A `profiles` that is a link, resolves outside, or is not a directory is rejected and reported the same way and read as empty, so the rest of the reconcile goes on and opening the repository (which reconciles) never fails on it. A file whose hash matches the last export or import is unchanged; a changed one is imported (content and dates from the record) unless the local profile has an unexported save. That is a conflict, reported in `profileConflicts` (reconcile result and storage status): the local profile is kept and its next export wins, which clears it, as for epics.
- **Kanban cards** (`repo` mode only) are exported by the finalizer and imported by `src/core/repo/kanbanImport.ts`, each card (definition, events and rebuild) in its own short reconcile transaction (see Reconcile / import). `card.json` (`buildKanbanCardRecord`) holds what an edit can change plus the key, author, creation time, the time of the latest create or edit, and a `generation`; only a create or an edit rewrites it, at a generation past every one this machine exported, imported or saw. It writes only over the record this machine last exported or imported, or one a reconcile reported as a conflict with a local edit (noted as seen with its hash and generation); any other tracked `card.json` makes the entry fail with `conflict` until a reconcile has reported it, so another machine's edit is never dropped silently, and the export after that wins, as a profile's does. Each event file (`buildKanbanEventRecord`) is written once like a comment: an existing file must hold the same record, or the entry fails with `conflict` and the file is left alone; it waits while the card's `card.json` is not in the checkout. Payloads are strict per kind and never carry a claim secret: the services mask reports, and the builder masks every secret of the card's attempts and any whole claim token again. Entries of one card share the blocking key `kanban:<cardId>`, so a failed one holds back only that card's later records; an epic-scoped flush never writes Kanban entries, and they never count as an epic's pending changes or as epic conflicts. On import, a `kanban` that is a link, resolves outside or is not a directory is rejected and read as empty; a card folder is read only when named by a card id, and a card without `card.json`, or with any event file that is a link, too large, or fails the strict schema or names another card or event than its path, is rejected whole, so its stream never has a gap. A changed `card.json` is imported unless a local edit waits to be exported: that is a conflict, and the local card is kept. An event already held with other content is a conflict, never an overwrite. New events are inserted and the card's lane, attempts (state, outputs, evidence, kick-back comment, timestamps), pending Play and Done summary are rebuilt from its whole event stream, ordered by time and then by transition. A Play is pending before the first claim when one was pressed, after a kick-back, or when one was pressed once the latest attempt failed or lapsed; Plays pressed on two computers before they synced count once, and a claim consumes it. An attempt held here keeps its claim secret, progress note and, while still leased, the lease and heartbeat this computer gave it; a new one gets a secret no token was ever made for. Progress notes, later heartbeats and lease extensions are machine-local, like a plan attempt's lease: another computer's import shows the claim's lease and the first heartbeat. A stream that names an attempt with no `claimed` event or gives an attempt two numbers, a card whose key a different card holds here (two computers that each created a card before syncing take the same next key), or a database constraint (two open attempts) rejects the card. Card and event conflicts are reported in `kanbanConflicts` (reconcile result and storage status) and never among the epic conflicts.
- Owned file operations use app-generated relative paths from validated ids and verify the resolved real path stays inside `.darkmechanicus/` (symlinks/junctions included); failures are `unsafe_path`. Imported references are inert strings.
- Machine-local state (leases, claim secrets, approval grants, auto-continue authorizations, sessions, absolute paths) is never exported.

## MCP server (`src/mcp`)

`node out/main/mcp.js --repo <path> [--role orchestrator|planner|worker|reviewer] [--allow-save] [--label <name>]` (packaged: the app executable with `ELECTRON_RUN_AS_NODE=1`). Diagnostics go to stderr. Tool results are JSON (`{ ok: true, data }` or `{ ok: false, error: { code, message, details } }`) in both `content` text and `structuredContent`, with `isError` on failures; arguments that fail a tool's input schema are `invalid_input`. A session lists only the tools its role may call. Skills are exposed as MCP prompts.

## Hosted agents

**Proposed extension (2026-11-10):** [agent-desktop integration notes](design/agent-desktop-integration.md) map optional computer use onto the terminal launch, environment, instruction, and lifecycle paths below. agent-desktop is a tool used by a hosted agent, not an agent provider. The desktop hosts four built-in agent CLIs, `claude` (Claude Code), `codex`, `cursor` and `autonomous` (`a8s`), and custom CLIs: it connects them, installs the downloadable ones, asks each built-in whether it is signed in, runs each chat as the agent's own CLI in a terminal in the app's window and starts them as a run's orchestrator (design: [`design/chat-shells.md`](design/chat-shells.md)). The renderer names only an agent id or kind, a folder, a chat, a model, a role or a title, and for a custom CLI its name and arguments. Rules the connection code keeps:

- **No shell for a path someone chose.** On macOS the executable is one argv entry. On Windows an `.exe` or `.com` is run directly; a `.cmd` or `.bat` shim goes through the shared shim launcher (`src/main/agents/shimLaunch.ts`): exactly one `cmd.exe /d /v:off /s /c` parse with the path in one pair of quotes, so `&`, `^`, `(` and spaces in it are literal. There is no `start`, no nested `cmd.exe` and no shell option anywhere. A path or an argument holding `"`, `%` or a control character (or an argument ending in a backslash) is refused (`unsafe_path`), never escaped. Any other Windows extension is refused as not runnable. Every argument after the path is a constant, or a model id checked by `isSafeModelId` (`src/shared/agents/models.ts`); the launcher quotes an argument only where it needs it. Stopping a process uses `killProcessTree` (`src/main/agents/processTree.ts`), which resolves once the process and what it started are gone, so what a shim started goes with it. A Claude `.cmd` shim is not launched at all: a chat terminal follows the shim to the program it runs (`terminalLaunchSpec.ts`).
- **The installer runs without a shell string.** PowerShell is given the downloaded script with `-File` (and `-NoProfile -NonInteractive -ExecutionPolicy Bypass`); on macOS the script is the argument of `/bin/bash` or `/bin/sh`. The confirmation is a native message box that shows the source, the command, the install folders and how the download is checked. Cancel is the default; only a click on the first button installs. The renderer cannot answer it.
- **The app never touches a credential.** Sign in runs the CLI's own login (`claude auth login`, `codex login`, `agent login`, `a8s init`) in a sign-in terminal in the app's window; the vendor's own page does the signing in. The status command's output is classified and dropped, never stored or returned.

### Chats: records, store, terminals

A chat is a record and a live owner on its stored `surface`. A `terminal` chat runs the agent's own CLI in a PTY in the app's window, with its own approvals, model picker, sign-in prompts and subagents. A `gui` chat (Claude Code or Skitarii only, `GUI_PROTOCOL_KINDS` in `src/shared/agents/agentChat.ts`) runs the same CLI in its own structured mode and the app renders it (see [GUI chats](#gui-chats-srcmainagentchat)). `createChat` (`chatRecords.ts`) stores `surface: 'gui'` for a GUI-capable agent and `terminal` otherwise, and always `terminal` for a Forge setup chat; a record with no `surface` is a terminal chat. **Skitarii mail in the renderer.** `useAgentMail` (`src/renderer/src/agents/useAgentMail.ts`, called once by `useShell`, shared through `AgentMailContext`) holds every OMP chat's `ChatMailState` of the active folders, keyed by folder and chat id: `chats.mail.snapshot` catches a folder up when it becomes active, after a `chats_changed` for it and after a reload; pushes are kept only for active folders and only when newer (`version`) than what is known; a folder that stops being active is dropped with what is in flight for it. The sidebar `ChatRow` shows the person's unseen count (stopped chats too); a Skitarii `TerminalPane` puts **Messages** in its `ChatHeader` (`AgentInbox.tsx`), counting unseen-by-you and unacknowledged-by-its-agent apart, and opens an accessible inbox `Dialog` over the live terminal without remounting, focusing, typing into or restarting it. The inbox reads pages (`useInboxPages.ts`, late answers dropped) and shows bodies and sender names as inert plain text, each sender's stable id, time, reply target and seen/acknowledged state; a sender that is a chat of the folder opens only on click. **Mark shown messages seen** moves only the person's cursor. Read-only `DeliveryStatus.tsx` shows actual automatic full-body insertion counts/blockers and the model-token cost warning; it grants no manual credit and never treats queue acceptance as delivery. Board conversation labels also distinguish pending/unverified from delivered.

**Roles and the chat's `dm` grant.** Before the agent starts, `issueChatCli` (`src/main/agents/chatGrants.ts`) issues a grant in the chat folder's workspace with the chat's role, `allowSave` only when it is set and the role is `planner` or `orchestrator` (`canSavePlans`), the label `"<Agent> · <chat title>"` and a fixed lifetime, and adds its token as `DM_SESSION_TOKEN` to the `dm` invocation `buildCliConfig` (`src/main/desktop/cliConfig.ts`) pins to the folder. The grant is revoked through the same workspace when the session ends. The role is fixed for the chat's life. `chats:create` takes the role and `allowSave` from the person; `chats:startOrchestrator` takes neither (see below).

**The chat store.** `userData/agents/chats/<folder key>/index.jsonl` holds one line per change of a chat record (the last line for an id wins), and `<chat id>.jsonl` the transcript a chat stored before chats became terminals, one `ChatItem` per line; nothing writes a transcript any more. The folder key is the first 24 hex characters of the SHA-256 of the folder's canonical real path, so every spelling of a folder finds the same chats and untracking a folder leaves them. The index is appended to; a truncated last line is repaired on the next append and skipped on read, as is a line of a kind a newer build wrote. Deleting a chat is the one rewrite: its transcript file is removed and the index is replaced atomically without any line of that chat. A record is masked for claim tokens before it is written.

**Activity bindings.** A terminal chat is linked to the attempts and runs it acts on by grant: `chats:boundTerminal` (`grantBindings.ts`) finds the chat whose grant the claiming (or starting) session used, and the Activity tab and orchestrator feed offer **Open terminal** to it. Item-based links live in `userData/agents/activity-bindings.jsonl` (chat id, thread id or null for the main thread, folder, run or attempt id, and `orchestrator` or `worker`): old chats keep the ones they stored, and a GUI orchestrator chat adds a worker attempt binding only for a verified claim token (see [GUI chats](#gui-chats-srcmainagentchat)); deleting a chat removes its own. `chats:boundThreads` answers them (`boundThreads.ts`), limited to the chats of the folder that was asked about. The renderer's Activity tab (`src/renderer/src/ticket/ActivityTab.tsx`) and orchestrator feed (`src/renderer/src/epic/OrchestratorFeed.tsx`) show such a thread through `useThreadStream`: the chat is read once with `chats:read`, nothing is pushed or polled, and its approvals are records with the decision stored for each. A thread can have served several attempts of a ticket, so an attempt's tab clips the rows to that attempt's own window (`attemptWindow`: its claim to its end, or to now while it is open).

**The chat's folder.** Every start of a chat's terminal checks its folder on disk first (`resolveLaunchFolder`, `src/main/agents/launchFolder.ts`): the stored path must still exist, be a directory, be its own real path (a symlink swapped in leads elsewhere) and be tracked. The checked path is the one the grant and the `dm` command are issued for (`--repo`), the terminal's working directory and a custom CLI's `{folder}`. A folder that fails is refused with a `not_found` error naming it and the reason, before a grant is issued.

**Sign-in.** Before a chat's terminal starts, the agent's own status command is asked (`agents:status`); a signed-out agent starts nothing and the pane offers Sign in, which runs the CLI's login in a sign-in terminal (`loginTerminals.ts`). A login the CLI stops accepting mid-chat is the CLI's own to report in its terminal. When an orchestrator chat's CLI exits on its own and its status command then says `signed_out`, the chat's `running` or `paused` run is paused with the reason `signed_out` through the folder's own desktop Workspace, the only session that holds `run.pause_signed_out` (see [Runs, readiness, and attempts](#runs-readiness-and-attempts)). Nothing is resent and no run is resumed by the app itself. An old chat whose turn a lost sign-in cut short (`cutShortMessageId`) is flagged in the sidebar while its agent is signed out; the status is asked again when the window regains focus.

**Starting an orchestrator.** `chats:startOrchestrator` (`startOrchestratorRun`) takes only a folder, an epic, an agent and a model. In main it reads the epic, queues the run through the desktop's own `queueRun`, creates the chat as `orchestrator` with `allowSave` off, titled `Orchestrator · <epic title>`, records the run's id and the epic's id on the chat (`runId`, `epicId`), and starts the chat on its stored `surface` before it answers (`startChatOnSurface`, `src/main/agents/chatSurfaceStart.ts`): a `gui` chat (a Claude Code or Skitarii agent) through the one GUI session manager, `AgentChatSessions.start` with the kickoff as its first user message; any other chat in its terminal (`TerminalSessions.start`) with the kickoff. The renderer then opens the chat. The chat's instructions file holds the orchestrator and worker guidance after the `dm` instructions: the steps, the guides in marked sections read with `skillBody` from the same text the server serves as prompts, and a step that says how each worker subagent is started: it is given its whole execution packet and the worker guidance, runs in the orchestrator's session, and heartbeats and submits for itself, while the orchestrator reviews and decides. The claim token reaches the worker only through that packet. The kickoff is only fixed text and the run lines (epic, branch, run id, the first step; in a folder of repositories, also one `repository → branch` line per repository the epic branch is bound in, with the reminder to work in a worktree of each repository), built from ids, the epic's title and its branch names, never from anything that grants access, and it goes only with the chat's first start (`kickoffSent` on the record), never with a resume: Claude Code takes it as its positional prompt (`kickoffSent` stored before the spawn); every other CLI, and any `.cmd` shim, has it written as one bracketed paste and Enter once its first screen has taken no output for a second (`pasteFirst`, which also carries the instructions of a CLI with no instructions flag). A failure before the run is queued is an error and nothing exists. After it, the run stays queued and the result's `problem` says why no agent is running it (the chat could not be created, or its agent did not start: a folder refused, the agent not connected or signed out, a spawn that failed; the chat is then removed again, or kept and returned when it cannot be removed). A CLI that starts and then exits leaves its chat to read and start again. The agent then calls `start_run`, which picks up the queued run.

**Starting a transfer chat.** `chats:startTransferChat` (`startTransferChat`, `transferStart.ts`) takes the same four fields. In main it reads the epic and its transfer through the desktop's own `getEpic` and `getTransfer`, and refuses, with nothing created, unless the person authorized the transfer (`queued`) or an agent already started it (`in_progress`). It then creates the chat as `orchestrator` with `allowSave` off, titled `transferTitle(epic title)` (`Linear transfer · <epic title>`), records the epic's id on the chat (`transferEpicId` and `epicId`), and starts it on its surface (`startChatOnSurface`: a GUI chat through `AgentChatSessions.start`, any other through `TerminalSessions.start`) with `transferKickoff` as the kickoff before it answers: the same text Copy prompt and `dm transfer linear` print, the Linear transfer guide included. The kickoff goes with the chat's first start only, as an orchestrator's does (a GUI chat's first user message, Claude Code's positional prompt, every other CLI's first paste). Because a later start may be on a new session, the chat's instructions file also carries `transferGuidance` (`src/mcp/transferKickoff.ts`) on every start, after the `dm` instructions, for any chat with a `transferEpicId`: the epic id, the start_transfer step and the guide, built from the epic id alone (on a first start the guide therefore reaches the agent twice). The chat gets the grant and `DM_SESSION_TOKEN` of any orchestrator chat: Dark Mechanicus attaches no Linear server, so the agent uses the one configured in its own CLI. The record keeps `transferEpicId` and the role, so `chats:findTransferChat` finds the chat again after an app restart and its terminal starts again as an orchestrator's, never with the kickoff again. Whether that start resumes the CLI's session follows the launch spec below: Claude Code once its session file exists, Autonomous once the chat was typed into, Codex and Cursor only with a stored session id, a custom CLI never. A CLI that starts on a new session has only the guidance: Codex and Cursor get the instructions as their first paste and so start on the transfer by themselves; Claude Code and Autonomous have them in their system prompt and wait for the person; a custom CLI has them only through `{instructions}`. A failure once the chat is asked for leaves the transfer authorized and is reported in `problem`, as for an orchestrator (an agent that does not start removes the chat again, or keeps it when it cannot be removed). `chats:transferPrompt` answers the kickoff for an agent the person starts elsewhere.

**Starting a planner.** `chats:startPlanner` (`startPlannerChat`, `plannerStart.ts`) takes only a folder and an epic. In main it reads the epic (an unknown epic is refused, nothing created), then picks the agent with `pickChatAgent` over the connected agents and their sign-in state as main checks it (a custom CLI is `unchecked`, so never picked); with nobody signed in it is refused with `no_agent` and nothing is created. It creates a `planner` chat with `allowSave` on, titled `Planner · <epic title>`, recording `epicId`, and starts it on its surface with a kickoff that names the epic and points at the planner guide (the `darkmechanicus-planner` prompt). An agent that does not start removes the chat again, and `problem` says why.

**Board messages to a GUI chat.** `chats:sendConversationMessage` stores the person's message first and resolves the chat as before (`resolveConversationChat`). A chat on the `gui` surface gets the `boardMessage` text as a user turn (`AgentChatSessions.send`, which starts it when it is stopped), never a paste; a fresh epic or card conversation chat on the GUI surface starts with the board kickoff as its first message. A fresh epic conversation chat records `epicId` as well as `conversation`; a card one records only `conversation.cardId`. The delivery ledger records the outcome (`delivered`, or `failed` with the reason) as it does for terminal chats.

**Starting a Kanban card.** `chats:startKanbanCard` (`startKanbanCard`, `src/main/kanban/startKanbanCard.ts`) takes a folder, a card, an agent and a model. In main it plays the card (`playKanbanCard`, which marks a pending play; a card that cannot be played is an error and nothing is created), creates the chat as `orchestrator` with `allowSave` off, titled `kanbanTitle` (`Kanban · <key> <title>`), records the card's id on the chat (`cardId`, no `epicId`), and starts it on its surface (`startChatOnSurface`: a GUI chat through `AgentChatSessions.start`, any other through `TerminalSessions.start`) with `kanbanKickoff` as the kickoff before it answers. The kickoff is short (the card's id, key and title, the checked-out branch, and the first step: `get_capabilities`, then `claim_kanban_card`) and goes with the chat's first start only, as an orchestrator's does (a GUI chat's first user message, Claude Code's positional prompt, every other CLI's first paste). The steps and the orchestrator and worker guides are `kanbanGuidance`, in the chat's instructions file on every start for any chat with a `cardId` (beside a transfer chat's `transferGuidance`), so a card chat started again, even on a new session, keeps its task. Neither carries a claim token: the agent gets one only when it claims. When the chat cannot be created or its agent does not start, the chat is removed again (or kept and returned when it cannot be removed) and `problem` says why; the pending play stays, and pressing Play again starts a new chat. `chats:kickBackKanbanCard` (`kickBackKanbanCard`) records the person's comment through core `kickBackKanbanCard` (the card returns to In progress with a pending play), then finds the card's newest chat by `cardId` and `createdAt` and gives it `<key> was kicked back by a person: <comment>. Claim it again with claim_kanban_card (cardId <id>) and address the comment.`, the comment's claim tokens masked: a GUI card chat as a user turn (`AgentChatSessions.send`, which starts it when it is stopped), any other pasted into its terminal (`TerminalSessions.paste`). A running PTY gets the paste and Enter as a first paste does; a chat with no PTY is started first like an attach (a resume when the CLI has a session, never with the kickoff). A card with no chat answers `chatId: null`; a send or paste that is refused or fails leaves the kick-back recorded and `problem` says the comment could not reach its chat. There is no activity binding for a card: its chat is found by the `cardId` on the chat record.

**Transfer to Linear in the epic workspace.** The header offers **Transfer to Linear** beside Start run for an epic with a saved plan, no active run, no open transfer, no unsaved draft changes, and not completed; Start run hides while a transfer is queued or in progress (the workspace reads `getTransfer` with the epic). Both choices of the dialog call `queueTransfer` first: **Transfer with agent** then calls `chats:startTransferChat` and, once the folder's chats are listed again, opens the chat's terminal, **Copy prompt** then copies `chats:transferPrompt`. If the queue succeeds but the chat cannot be started (or the prompt copied), the transfer stays authorized, as main leaves it: the banner says why (a chat that could not be removed is listed, but the workspace stays on the reason), and the transfer strip under the header, shown while the transfer is open, recovers it. The strip shows the status, how many packet items are recorded ("n of m created") and the last read-back's mismatches by DM key and field, with **Resume** (`chats:findTransferChat`, or the dialog again to start a new transfer chat without queueing), **Copy prompt** and **Cancel transfer** (`cancelTransfer`, after a confirmation). A completed epic whose outcome records a transfer shows **Transferred to Linear** above its plan, from the epic alone, with the project link opened through `openExternal`. The renderer calls only the desktop commands `getTransfer`, `queueTransfer` and `cancelTransfer`; everything else in a transfer is the agent's.

### GUI chats (`src/main/agentChat`)

A `gui` chat runs the agent's CLI in its own structured mode, with no vendor SDK and no per-vendor adapter: Claude Code as `-p --input-format stream-json --output-format stream-json --verbose --include-partial-messages --forward-subagent-text --permission-prompt-tool stdio`, Skitarii as `--mode rpc-ui` (`agentChatLaunch.ts`). `--forward-subagent-text` makes Claude forward each subagent's text with its parent tool id, which is how a worker's thread is told apart. The launch shares the terminal's start files, settings file (memory guard included), environment and Windows shim resolution; main never takes an executable, argument, cwd, environment or confirmation from the renderer. Design decision: [`design/chat-shells.md`](design/chat-shells.md#superseded-in-part-2026-11-20).

**Thread-attempt bindings.** When an orchestrator GUI chat with a `runId` spawns a subagent, the protocol reads the raw spawn prompt in main before masking and emits `thread_claim` with any claim token it holds. `AgentChatSessions` asks the project (`verifyAttemptClaim`, the desktop workspace's `claimedAttempt`) whether the token is that run's live, latest claim of the attempt; only then does it store `{ chatId, folder, threadId, kind: 'attempt', attemptId, role: 'worker' }` in `userData/agents/activity-bindings.jsonl` (`activityBindings.ts`). The bound attempt's ticket key is looked up once (`ticketKeyOfAttempt`) and stamped as the thread's `Acolyte:<key>` callsign with `ticketVerified: true`: the binding wins over the label the model gave the subagent.

**Surfaces.** `agentChat:setSurface` (`AgentChatSessions.setSurface`) is the one switch. It is refused `busy` while a GUI turn runs, a message is queued, a prompt waits, another switch awaits confirmation, or the terminal is starting or still stopping; `unsupported` for an agent outside `GUI_PROTOCOL_KINDS`, a Forge setup or a tooling repair chat. GUI to terminal stops the GUI process. Terminal to GUI with a live terminal needs `nativeTerminalStopConfirmation`: a warning dialog modal to the requesting window, **Stop terminal and switch** or **Cancel**, where Cancel is the default and the Escape answer. Its text says the agent's current work may be interrupted and the same session is kept. Cancel, Escape, a closed dialog, a gone window or a failed dialog answer `cancelled` with nothing stopped. The app never infers that a terminal is idle: a live terminal always needs the confirmation, and the renderer cannot supply it. A terminal whose owner changed while the dialog was open is refused `busy`. After the confirmed terminal generation has stopped and released the chat, the record's `surface` changes and `chats_changed` is pushed; the GUI then resumes the same CLI session.

**Restart resume.** `restartMarkerHook` runs on **Restart now** (`setBeforeInstall` in `autoUpdate.ts`) and writes `restart-resume.json` beside the chat store, listing every live run-bound orchestrator chat. On the next start `resumeAfterRestart` takes the marker (read and deleted before use) and honours it only when it is under 15 minutes old, dated no more than 1 minute in the future, and the app's version went up. Each listed chat that still qualifies gets one message on its same session: `[App restarted after an update from v<from> to v<to>: resume your run from get_run]`. A legacy terminal chat is switched to the GUI first; that switch never stops a live terminal.

**The Magos arbiter** (`src/main/magos/`). `arbitrationRules.ts` decides which prompts are never arbitrated, failing closed: arbitration disabled, not a Start-run orchestrator chat (`not_magos_chat`), a project-less chat, an unsupported kind, a question, an always-ask entry, no tool input, a control file, a path outside the folder and its registered worktrees (`worktreeRoots.ts`, `git worktree list --porcelain`, cached 60 s), a path too long to check (`path_too_long`: a word with a component over 255 UTF-8 bytes, or a name the disk refuses with ENAMETOOLONG, on every platform; a real outside path or control file in the same input outranks it), and the built-in never-arbitrate list. It scans path keys (`file_path`, `notebook_path`, `path`, ...) and free text such as a Bash command, but never the written text of a file-editing tool (`content` of Write, `old_string`/`new_string` of Edit, `edits` of MultiEdit, `new_source` of NotebookEdit), so `$HOME`, `//` or `*` in a file's content reaches the arbiter. `arbiterContext.ts` reads the epic intent and, for a bound worker thread, the attempt's ticket. `arbiterPrompt.ts` holds the fixed system prompt and the masked request on stdin, and parses the one-line verdict `allow_once`, `deny` or `escalate`. `arbiterLaunch.ts` builds the tool-less launch (Claude `-p --output-format json --no-session-persistence --tools "" --strict-mcp-config --safe-mode`) in a fresh temp folder with no grant. `arbiterRunner.ts` runs it: invalid output, a timeout, an error or a cancel escalates. Arbiter folders live under `<userData>/agents/arbiter` and are swept at startup. A verdict the gate applies is recorded on the approval decision as `decidedBy: 'magos'` with its reason (`src/shared/agents/chat.ts`).

**Notifications** (`src/main/notify/`). `notifier.ts` raises OS notifications for `approval_needed`, `question`, `checkpoint_ready`, `run_failed` and `run_stalled`, each gated by its setting and by `whenFocused`, shown once per key per 10 minutes, its text stripped of control characters, masked and clipped. A click restores and focuses the window and pushes the `NavigateTarget` (a chat with an optional thread and prompt id, an epic's checkpoint, or an epic) on `notifications:navigate`. The renderer routes it in `src/renderer/src/app/notificationNavigate.ts`: an epic-bound chat opens on its epic's Agent tab with the owning chat selected and no thread (`EpicAgentLanding`, `landing.ts`), since a worker's card lives in its owning chat; any other folder chat opens in its folder, at the thread when one is named; a project-less chat opens on its own; a checkpoint target opens the epic's checkpoint and an epic target the epic. The prompt id is not used for landing. `notifyIpc.ts` serves `notifications:raise`: the renderer may ask only for `checkpoint_ready` or `run_failed`, by folder, epic and run ids; main reads the titles itself. Prompt and stall events come from `notifiedAttention` in `agentChatWiring.ts`; a prompt's dedupe key is scoped to its chat ref (folder and chat id) as well as its prompt id, so the same prompt id waiting in two chats notifies in each. Every dedupe (the notifier's and the renderer's `useEventFeed` once-per-key set, where report revisions of one sprint share `checkpoint_ready:<runId>:<sprintId>`) lives in memory only: after a restart, revisions submitted before it are history and stay silent, and the first new report revision of an already-notified sprint notifies once more.

**Renderer.** `src/renderer/src/agentChat/` (see [Processes and modules](#processes-and-modules)) renders GUI chats: `AgentChat` (which docks `PendingPromptCard` and then `TodoCard`, the chat's own to-do list, above its composer), `TurnActivityLine` (`turnActivity.ts`: a 30-second stall warning, never while a tool runs or a prompt waits), `AgentChangesCard` (`agentChanges.ts`: completed file-tool writes and edits only), `ChatAgentsRail` (the GUI chat's **Agents** toggle, remembered per chat) and `useNeedsYou` (the folder's prompts waiting on the person or the Magos, from `agentChat:attention`). The epic's **Agent** tab is `src/renderer/src/epic/EpicAgentPanel.tsx` over `epicAgentsView.ts`: the selected chat in the centre (a GUI chat's `AgentChat` with its `TodoCard`, a terminal chat's `SurfaceActions` with **Open terminal** and **Switch to GUI**, or a subagent thread) and a right rail whose **Agents** tab holds the named agent tree (`src/renderer/src/agentTree/`, each row with a closed/total to-dos label) and `AgentChangesCard`. A subagent thread is shown read-only; its composer sends `relayMessage(threadId, text)` to the chat that owns the thread: `[Message from the person for your worker subagent, thread <id>]`, the text, and `Pass this to that worker now and post its answer.`

### Terminals: PTY host, sessions, attach and port, launch spec

**The PTY host.** `src/main/terminals/ptyHost.ts` is the only module that loads `node-pty`, in the main process (`createNodePtyHost`, composed in `bootstrap.ts`); everything else starts PTYs through its `PtyHost` interface (tests use `__mocks__/fakePtyHost.ts`). A spawn takes an absolute program, an argv (on Windows a command line the app quoted itself, `windowsCommandLine.ts`), a canonical cwd, the whole environment (nothing is inherited) and a size. On macOS `ptyHelperCheck.ts` first checks that node-pty's `spawn-helper` is executable and names the file when it is not. A PTY's whole tree is ended with `killPtyTree` (`processTree.ts`); node-pty's own kill reaches only the program.

**Terminal sessions.** `TerminalSessions` (`terminalSessions.ts`) keeps one PTY per chat, with its screen in main: an `@xterm/headless` terminal fed the PTY's output (`terminalScreen.ts`), whose serialized snapshot paints any pane that attaches (a chat switch, a reload, a second window). A start resolves the folder (`resolveLaunchFolder`), checks sign-in (`getAgentAuthStatus`; `signed_out` starts nothing), writes the start files (`terminalFiles.ts`: the instructions and, on macOS, the chat's `dm` launcher; `claudeSettingsFile.ts` for Claude), issues the grant, builds the launch spec and spawns. The grant is revoked when the PTY exits for any reason. While it runs, the folder is checked every minute and on each attach, and a PTY with no input and no output for 10 minutes is stopped (a chat that carries a run or a Kanban card is kept while a lease of it is held); exit, Start again, resume, New session, quit disposal and the signed-out run pause are in the module table above.

**`terminals:attach` and the message port.** The renderer starts a chat's CLI only through `terminals:attach { folder, chatId, newSession? }`, a strict object through `guardIpc`; the other starts are main's own: `TerminalSessions.start`, which `chats:startOrchestrator`, `chats:startTransferChat`, `chats:startPlanner` and `chats:startKanbanCard` call for a terminal-surface chat they have just created, with its kickoff, before they answer (it subscribes no one; a GUI-surface chat starts through `AgentChatSessions.start` instead), and `TerminalSessions.paste`, which `chats:kickBackKanbanCard` calls for a terminal-surface card chat and which starts a chat that has no PTY. Main loads the chat from its own store, refuses a folder that is not the chat's own, and attaches to the running PTY or starts one. An attach that finds the sign-in check under way waits for the start to end and then answers (`running` with an empty snapshot, since its listener heard everything since the spawn) rather than answering `checking`. A `running` answer carries the snapshot, and main posts one end of a `MessageChannelMain` to the asking frame on `terminals:port`, named by an id the preload uses to claim it (`src/preload/terminals.ts`). On that port main takes only `{ type: 'input', data }` (at most 64 KiB) and `{ type: 'resize', cols, rows }` (clamped); it sends the chat's output and its exit, then closes the port. `agents:signIn` answers the same way for an agent's sign-in terminal (`loginTerminals.ts`).

**The launch spec.** `terminalLaunchSpec.ts` is pure: from the chat record, the agent row, the resolved folder, the chat's `dm` invocation and the start files it returns the program, arguments, cwd and environment (`terminalEnv.ts`), plus `pasteFirst` and the values it dropped. Per kind:

| Kind | Arguments main builds |
|------|-----------------------|
| Claude Code | `--append-system-prompt-file <instructions>`, `--settings <file>`, `--model <id>` when set, `--session-id <uuid>` or, once `claudeSession.ts` finds the session file, `--resume <uuid>`; on a first start of an orchestrator chat (a run's, a transfer's or a card's) the kickoff as the positional prompt. On Windows a `claude.cmd` is followed to the program it runs (`resolveClaudeExecutable`) |
| Autonomous | `start <folder>` (or `resume` once the chat was typed into), `--append-system-prompt <text>` (not through a `.cmd`), `--approval-mode always-ask`, `--model <id>` when set |
| Codex | `-C <folder>` or `resume <id>`, `-m <model>` when set (inferred in the design; not checked against a real Codex) |
| Cursor | `--resume <id>` when resuming, `-m <model>` when set (inferred, as Codex) |
| Custom CLI | The confirmed arguments only, whole-argument `{folder}` and `{instructions}` replaced; no app flag |

What cannot go on the command line (the kickoff for every CLI but Claude Code, and the instructions for Codex, Cursor and an Autonomous `.cmd`) is `pasteFirst`: once the CLI has turned bracketed paste on and its screen has then taken no output for a second, main writes it as one bracketed paste with every control character but tab removed, then Enter half a second later as typed input; a kickoff sent so sets `kickoffSent` once its Enter has gone. A later paste (`TerminalSessions.paste`, Kick back's message) goes the same way, queued on the PTY behind any waiting paste; a PTY being stopped or just exited is waited out and started again once, and a PTY that exits or stops before the paste goes drops it. A model that fails `isSafeModelId` and a Claude session id that is not a UUID are dropped and reported.

**What the renderer can and cannot make main start** (condensed from [`design/chat-shells.md`](design/chat-shells.md#what-a-compromised-renderer-can-make-main-start-through-a-terminal)):

| | What main starts | What the renderer can choose |
|-|------------------|------------------------------|
| Program | The chat's agent row in `app.sqlite`, set by Find, Download or Add a custom CLI through native dialogs | Nothing: it names a chat; main reads the agent from its own record |
| Arguments | The per-kind preset or the confirmed custom arguments, plus paths and ids main makes | Only the chat's model, set at creation, which is dropped unless it passes `isSafeModelId` |
| cwd | `resolveLaunchFolder` on the chat's stored folder | Nothing: the request's folder is only compared with the chat's |
| Environment | `terminalEnv.ts`: main's own without `ELECTRON_*` and `NODE_OPTIONS`, `TERM` and `COLORTERM`, the grant and `DARKMECHANICUS_HOME`, the macOS launcher folder first on `PATH` (on Windows, packaged, `ELECTRON_RUN_AS_NODE=1` stays) | Nothing |
| Sign-in terminal | A connected built-in's executable with its constant `LOGIN_ARGS`, in the home folder, with no grant | An agent id only; a custom CLI is refused |
| After the start | Input bytes and sizes on the port | It cannot start a second process, change the program, arguments, folder or environment, or keep a process past a quit, a deleted chat, a removed agent or a moved folder |

What stays possible: keystrokes drive the CLI, so a compromised renderer can make it do whatever it does in that folder at the chat's grant (type a prompt, answer its permission prompts, use its shell escape). The boundary stays the grant's role and Allow save.

## Bridge hardening

Defense in depth on both bridges (desktop IPC and MCP); the command layer's authorization stays the real boundary.

- **IPC sender check** (`src/main/ipcGuard.ts`). `index.ts` wraps `ipcMain` once with `guardIpc` and passes the result to every registrar (`dm:*`, `agents:*`, `chats:*`, `agentChat:*`, `terminals:*`, `settings:*`, `notifications:*` (`notifications:raise`; `notifications:navigate` is a push), `git:*`, `github:*`, auto-update, app version); nothing else touches `ipcMain`, and a test scans `src/main` to keep it that way. A call runs only when `event.senderFrame` is live, attached, top-level, and shows the app's own page: `isAppUrl` (shared with the navigation guard) compares the dev server's origin in development, and in production the packaged `index.html` by parsed protocol, host, and resolved path (query and hash ignored, never a prefix). Anything else gets `{ ok: false, error: { code: 'unauthorized' } }`, the handler never runs, and main logs the refusal. A chat terminal's message port is posted only to the frame of an attach that passed this check, so the port needs no `ipcMain.on` channel of its own.
- **Tools per role** (`src/mcp/tools/define.ts`). Each tool adapts one command (its camel-cased name, or an explicit `command` the compiler requires otherwise). `createMcpServer` grants the server the session's capabilities (`capabilitiesForRole(role, { allowSave })`), and `registerTools` registers a tool only when that set holds `COMMAND_CAPABILITIES[command]`. Read-only tools need `read`, which every role has; `save_plan` needs `plan.save`, which only `--allow-save` adds for planner and orchestrator. A withheld tool is still known to the server: calling it answers `unauthorized` without running anything.
- **Structured validation errors.** The SDK validates tool arguments before the tool callback and answers failures as plain text. The server replaces the SDK's `tools/call` handler with one that parses each tool's zod shape itself and answers failures with `invalid_input` (`details.issues`: path and message per field). `tools/list` stays the SDK's, so advertised JSON schemas are unchanged; a test pins each one to its fingerprint from before the change.

## Verification tooling

- `npm run smoke:mcp` launches the built `out/main/mcp.js` over real stdio (set `MCP_SMOKE_COMMAND` to Electron's binary to use its runtime) and plans, saves, and runs a ticket end to end.
- `npm run spike:claims` races claims on one ticket from 8 processes (exactly one winner per round).
- `src/integration/` exercises the real Workspace through the command table, MCP tools (in-memory transport), and desktop IPC handlers.
- `src/integration-ui/` holds the tests that run main-process code into a renderer model (GUI chat sessions and the Claude and OMP translators feeding `agentChatModel`). They live in their own `tsconfig.integration-ui.json`, the fourth project `npm run typecheck` checks. That keeps main imports out of the web program and renderer imports out of the node program, so `npm run deadcode` (ts-prune over `tsconfig.node.json` and `tsconfig.web.json`) sees each export's real consumers only. Vitest, coverage and oxlint still cover them through `src/**`.
- `preview/` holds the standalone Vite pages the capture harnesses screenshot (`scripts/capture-agent-chat.mjs`). They mount real renderer components over the renderer's test fixtures, so those fixtures stay browser-safe: nothing they reach imports `node:*` (the sample Linear packet takes a fixed hash instead of `contentHash`). `tsconfig.preview.json`, the fifth project `npm run typecheck` checks, and `npm run lint` cover them.
- Fireguard scopes mutants to the graded tests that import the mutated module and bounds each test run with `testTimeoutMs`, so milestone-sized branches grade in hours, not days, and an infinite-loop mutant counts as killed.

## Decisions taken during implementation

The product plan's open decisions were settled as follows (all revisitable):

- **Git tracks portable records**, not SQLite snapshots: JSON records under `.darkmechanicus/` plus a Git-ignored working database, rebuilt on clone.
- **First host:** any stdio MCP host; a Claude Code skill wrapper ships (`installSkills`) and the six skills are also plain MCP prompts, so no host-specific API is assumed.
- **Sprint advancement defaults to a human checkpoint** (`checkpoint.mode = human`); `auto` needs per-run authorization in the desktop.
- **Deletion stays deferred**, as the plan requires: no delete UI or tools ship (mockup 06 is not implemented).
- **The desktop hosts agent CLIs, and drives each through the CLI itself, never a vendor SDK or adapter layer:** a terminal chat runs the agent's own CLI in a terminal (`docs/design/chat-shells.md`); a GUI chat (Claude Code, Skitarii) runs the same CLI in its own structured mode (`src/main/agentChat`, superseding the terminal-only decision in part on 2026-11-20, see [the design note](design/chat-shells.md#superseded-in-part-2026-11-20)), with a Terminal toggle per chat. What differs per CLI is its launch preset (`terminalLaunchSpec.ts`, `agentChatLaunch.ts`) and, for GUI chats, its wire translator; the per-kind connection data (install recipes, version match, status command) sits beside the registry in `src/main/desktop`, and plans, tickets and profiles never name a vendor at all. Connected agents and chats are machine-local `userData` files, not portable records (see [Hosted agents](#hosted-agents)).
- **Named profiles are records like the others:** `format: darkmechanicus.profile`, `formatVersion: 1`, strict schema, key-sorted pretty JSON, imported on reconcile; tickets copy them rather than reference them, so a profile edit never rewrites plans.
- **A Linear transfer is carried out by an agent, authorized by a person, and checked by a read-back that trusts the agent.** Dark Mechanicus never calls Linear and holds no Linear credential: the orchestrator agent does the Linear work with its own Linear MCP server, following the packet `start_transfer` returns (`src/core/transfer/linearPacket.ts`). Sending a plan out is the person's decision, so queueing and canceling a transfer need `transfer.queue`, which only the desktop holds; an agent's `epic.transfer` only carries out a transfer already queued, and while it is open runs and Save are locked (`transferGuard.ts`). Completion rests on the read-back: the agent reports what it read from Linear, and `compareReadback` (`src/core/transfer/linearReadback.ts`) checks it against the stored packet and the recorded items; only a full match completes the epic. Its trust limit: Dark Mechanicus cannot read Linear, so the check is only as good as the agent's honesty in reading Linear back. It catches mistakes, such as a missing issue, a wrong milestone or a lost marker, not an agent that misreports. The runbook is [Transfer an epic to Linear](runbooks/linear-transfer.md).
- **Person-initiated git writes live in the desktop's main process.** Source control (`src/main/git`, `src/main/github`, behind `window.git` and `window.github`) commits, syncs, branches and clones when the person asks; core and MCP stay out of it and core's Git adapter stays read-only. GitHub sign-in reuses the machine's GitHub CLI login. See [0005](decisions/0005-source-control-in-main.md) and [Source control](#source-control).

## Testing conventions

- TDD with Vitest. Core tests use `createTestCtx()` (`src/test/testContext.ts`): in-memory migrated DB, fixed clock, sequential ids. Repository tests use temp directories. Renderer component tests use `// @vitest-environment jsdom` + Testing Library.
- Fireguard grades changed tests: keep mocks rare (fakes over `vi.fn`), assert on outputs/state rather than `toHaveBeenCalled*`, no empty tests, deterministic (100 isolated runs), and kill ≥ 75 % of mutants in changed modules (operators `+ - * / < > <= >= === !==`, `if` inversion, boolean/number returns).

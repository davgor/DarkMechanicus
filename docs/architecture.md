# Dark Mechanicus — implementation architecture

This is the build contract for the product described in [`product-plan.md`](product-plan.md). Where the plan says "proposed", this document records the choice that was implemented. Exact types live in code; this file explains the rules those types carry.

## Processes and modules

```text
External agent host ──stdio──> out/main/mcp.js  (src/mcp)   ─┐
                                                             ├─> src/core  (Workspace: command layer) ─> SQLite + .darkmechanicus/ files
Electron renderer ─> preload (window.dm) ─> main IPC (src/main/desktop) ─┘
```

| Path | Runs in | Responsibility |
|------|---------|----------------|
| `src/shared/domain` | everywhere (renderer-safe) | Vocabulary and contracts: statuses, plan bundle types, error codes, read-model views, the `CommandApi` interface |
| `src/core` | Node (Electron main and the MCP process) | The only place business rules live: database, migrations, services, portable records, import, finalizer, authorization |
| `src/mcp` | Node child process launched by an agent host | Stdio MCP server; each tool validates input and calls one `CommandApi` method |
| `src/main` | Electron main | Window, auto-update, folder registry, native dialogs, IPC handlers that call `CommandApi`, and the agent registry, installer and sign-in (the `agent*` modules in `src/main/desktop`; see [Hosted agents](#hosted-agents)) |
| `src/main/agents` | Electron main | Hosted agents: chat records and their store, the chats' `dm` grants and instructions, old chats' activity bindings and the orchestrator start; chat terminals are `src/main/terminals` (see [Hosted agents](#hosted-agents)) |
| `src/shared/agents` | everywhere (renderer-safe) | The provider-neutral chat contract, the `chats:*` bridge types and the `terminals:*` ones (`terminalApi.ts`) |
| `src/preload` | Electron preload (sandboxed) | Narrow typed bridge `window.dm` |
| `src/renderer` | Chromium renderer | React UI; never touches the database or filesystem |
| `skills/` | shipped as text | Provider-neutral agent instructions, exposed as MCP prompts |

No renderer database access and no duplicated business rules: MCP handlers and IPC handlers are adapters only.

## Storage decision

SQLite through the built-in **`node:sqlite`** module (`DatabaseSync`). It ships inside Electron 42's Node 24 runtime and in system Node ≥ 22.13, so the desktop and the headless MCP process open the same database with no native `.node` binary to rebuild per ABI. See [`docs/decisions/0001-sqlite-driver.md`](decisions/0001-sqlite-driver.md).

- Database: `<repo>/.darkmechanicus/local/state.sqlite` (Git-ignored). WAL, `foreign_keys=ON`, `busy_timeout=5000`, `synchronous=FULL`.
- Every write runs in `db.tx()` = `BEGIN IMMEDIATE` (nested calls use savepoints). Concurrent processes serialize on the write lock.
- `PRAGMA user_version` is the schema version. `migrate()` runs under the write lock; a database newer than the build is refused with `incompatible_schema`, never downgraded.
- Backups use `VACUUM INTO` (a consistent snapshot), never a raw file copy.

## The command layer (`src/core`)

A **Workspace** is opened per project root (one repository, or a folder of repositories) and implements `CommandApi` (`src/shared/domain/api.ts`). Each public command follows the same sequence:

1. **Validate** the untrusted input with the zod schemas in `src/core/schemas.ts` (`parseInput`). Limits (`LIMITS`) bound string sizes, list lengths, and graph sizes.
2. **Authorize** with `requireCapability(ctx.session, capability)`. Capabilities come from the session's role, fixed when the session registered (desktop launch, or the MCP process's launch flags). A caller-supplied name is never authority. The capability each command requires is declared once in `COMMAND_CAPABILITIES` (`src/core/commands/capabilities.ts`, exhaustive over `CommandName`); a test proves the services enforce exactly that table for every role.
3. **Branch guard** — commands that save, export, or dispatch work call `ctx.assertBranch()`; it throws `branch_changed` if the coordinating checkout's branch differs from the one recorded at the last reconcile. Flushing portable records is guarded the same way (pending exports belong to the recorded branch), and a Workspace opened after a branch switch does not reconcile automatically: the person (or agent) reconciles explicitly, which pauses active runs and records the new branch.
4. **Transact** — the whole mutation runs in one transaction, optionally wrapped by `withIdempotency` (same key + same request ⇒ original response; same key + different request ⇒ `idempotency_mismatch`). The stored response never holds a secret: `withIdempotency` is the only place a response is stored, and it stores what `storableJson` (`src/core/storedSecrets.ts`) makes of the response (the v10 migration rewrites stored rows through the same redaction, and deleting an epic deletes its rows). A listed secret field (`claimToken`, `token`, `claimSecret`) and any other field whose name ends in a secret word (`…Token(s)`, `…Secret`, `…Password`, `…Credentials`, `…ApiKey`; `fencingToken` and the token counts are listed as public) are stored as null, and whole claim tokens (attempt id, `.`, 16 or more secret characters) and grant tokens in any string or key are masked; stored text is never cut, so a bare attempt id at the end of a text is kept. The keys of `refMap` are a planner's refs, data rather than field names, so they are masked but not judged by name. A replay passes the stored row through the same redaction again, so a plaintext row written by an older build still running against the database is never handed out. So a replay returns a secret as null; the first caller alone receives it. Schema v10 put the responses stored before this through the same redaction.
5. **Record** — append an event (`appendEvent`) and enqueue portable-record work (`enqueueOutbox`) inside that same transaction.
6. **Flush** — after commit, the Workspace runs the finalizer to write portable records. Flush failure never rolls back the command; it leaves the outbox entry `pending/failed` and storage status shows it.

Service functions take a `Ctx` (`src/core/context.ts`: db, clock, ids, session, machineId, projectId, assertBranch) and never read globals, so tests drive time and ids deterministically.

Errors are `DomainError(code, message, details)` with codes from `src/shared/domain/errors.ts`; adapters convert them with `toErrorShape`.

## Domain rules

### Statuses

Epics and tickets have exactly three statuses: `backlog`, `in_progress`, `completed`. Paused/failed/awaiting review are run or attempt conditions, never statuses.

- Starting work (a claim, or a run starting) moves the ticket and its epic to `in_progress`.
- A ticket becomes `completed` only through an accepted attempt (or explicit carry-forward) — `setTicketStatus(completed)` succeeds only if that evidence exists in the epic's active or latest run.
- An epic becomes `completed` when its final sprint checkpoint advances (all required tickets accepted, the final sprint report carries an epic outcome whose success criteria are all met, and the checkpoint policy's authorization is present), or when a verified Linear transfer completes it: the read-back of the transfer the person authorized matches its stored packet, and the epic's outcome records the transfer. `setEpicStatus(completed)` never completes an epic.
- `completed` is terminal for epics: no status change, no draft, no save, no new run. Tickets of a completed epic are read-only.
- `in_progress` → `backlog` is allowed for an epic without an active run, and for a ticket without an open attempt.

### Drafts and saved revisions

- An epic has at most one draft (`drafts` table) with a `draft_revision` counter for optimistic concurrency and a `base_revision_id`.
- `createEpic` creates the epic (`backlog`) plus an initial draft (one empty sprint). Until the first Save the epic has no saved revision.
- `openDraft` creates a draft from the current saved bundle if none exists. `updatePlanDraft` also creates it implicitly.
- `updatePlanDraft(ops, expectedDraftRevision)` applies `DraftOp`s through `applyDraftOps` (`src/core/plan/draftOps.ts`): all-or-nothing, and every rejected op returns a concrete reason (e.g. "Dependency not added. DM-203 is in Sprint 2 and can't require DM-301 in Sprint 3…"). A stale `expectedDraftRevision` fails with `conflict`. Client-local refs map to stable ids in `refMap`.
- `savePlan(expectedDraftRevision)` validates the whole bundle (`validatePlan`; errors ⇒ `invalid_plan`), rejects a draft whose base is no longer current (`stale_draft`), then records a **pending** revision + outbox entry in one transaction. The finalizer writes the snapshot and pointer; only then is the revision `saved`, the epic's `current_revision_id` advanced, `ticket_status` rows created for new tickets, the draft removed, and the result `saved`. If the finalizer fails the result is `pending`, the draft stays, and the next flush retries. Saving a draft identical to the current revision returns `unchanged`.
- Execution reads only saved revisions. A pending revision is never executable.
- `discardPlanDraft` deletes the draft (for a never-saved epic it resets to the initial bundle).
- Revision ids are collision-resistant stable ids; `number` is display-only (max + 1 per epic).

### Plan validity (`src/core/plan/graph.ts`)

Errors (block Save): duplicate ids, empty titles, no sprints, non-contiguous sprint ordinals, a ticket in zero or several sprints, unknown ticket in a sprint, edges to unknown tickets, self-edges, duplicate edges, **a prerequisite in a later sprint**, cycles (reported as a path), bad relations, duplicate criterion ids, invalid policies, and the acceptance-node errors below. Warnings: isolated tickets, empty sprints, missing acceptance/success criteria, required ticket depending on an optional one, the acceptance-node warnings below, and, **while a run is active** (it has started a sprint), the run-aware warnings: `edits_passed_sprint` (the draft, or a newer saved revision, changes a sprint the run has already passed: a ticket edited, added, removed, moved out or given other prerequisites, or the sprint's own settings; one warning per sprint, measured against the revision the run is pinned to, ignoring the automatic title an acceptance node takes from its sprint's number) and `sprint_before_active` (a sprint the run's plan did not have sits before the active one, so the run never reaches it). They come from `src/core/plan/runWarnings.ts`, are added by `validatePlan` and by every draft edit's result, and never change `valid`.

An edge `{from: A, to: B}` means **B requires A's accepted result**. Relations (`related_to`, `duplicate_of`) are never execution edges. Layout is not stored; the desktop derives positions.

### Sprint acceptance nodes

- Every sprint ends in one ticket of `kind: 'acceptance'` (`src/core/plan/acceptance.ts`; `work` is the default and is never stored, so plans saved before the kind existed keep their content hash). The draft creates it with the sprint (`createEpic`, `add_sprint`): titled `Sprint N acceptance`, a testing ticket with no criteria yet, always last in its sprint. It cannot move to another sprint, its automatic title follows a renumbered sprint, and it goes with its sprint when the sprint is otherwise empty.
- It **implicitly requires every required (non-optional) work ticket of its sprint**. No edge is stored, so tickets move between sprints without rewiring, and `get_run` and `get_ready_tickets` list them as its prerequisites (`get_ticket` shows stored edges only). Until they are all accepted, and while the latest check of any row of its sprint has not passed, it is not ready.
- Its criteria may carry `covers`, the id of the work ticket the criterion verifies (draft operations accept an id, a display key or a client ref; `null` clears it). The plan puts one specific screenshot, measurement or end-to-end check per ticket there, so the combined sprint is verified item by item. A `covers` on a work ticket is ignored.
- Errors: a second acceptance node in a sprint (`duplicate_acceptance`); a ticket of its sprint requiring the node (`acceptance_runs_last`); a criterion covering an unknown ticket (`unknown_covered_ticket`). Warnings: a sprint with work but no node (`missing_acceptance_node`); a required work ticket no criterion covers (`ticket_not_covered`); a criterion covering a ticket outside its sprint (`covers_outside_sprint`); an explicit edge into the node that it already implies (`redundant_acceptance_edge`); `covers` on a work ticket (`covers_on_work_ticket`).
- The checkpoint gates on it (see Sprint checkpoints): its own accepted attempt even when it is optional (`acceptance_accepted`), a verified increment (`increment_merged`), and the project's Definition of Done reported as passed (`definition_of_done`).

### Runs, readiness, and attempts

- One active run per epic (`queued|running|awaiting_checkpoint|paused`), enforced by a partial unique index.
- `queueRun` (desktop) creates a `queued` run pinned to the current saved revision; `startRun` (orchestrator) picks up the queued run or creates one, binds the epic branch (explicit input, else the current checkout branch + HEAD), sets the first sprint active, and moves the epic to `in_progress`.
- A run is pinned to `revision_id`. Saving a new revision never changes an active run; `adoptRevision` switches it only at a checkpoint (or while paused) with no open attempts. Accepted tickets whose content hash is unchanged keep their acceptance; changed tickets need explicit `carryForward` or new work (old attempts get `superseded_at`). A changed ticket in a sprint the run already passed can never be redone in that run, so adoption refuses it unless it is carried forward. **A ticket that moves to a later sprint starts it with a fresh retry budget:** its failed, rejected and abandoned (reconciled `lease_expired`) attempts get `superseded_at`, so readiness no longer counts them and a leftover does not arrive at its retry limit. Sprints are matched by id (a renumbered sprint is the same sprint), accepted and canceled attempts are never touched, the superseded attempts stay in history (and in the tier facts), the next attempt continues the numbering, and the tickets so treated are listed as `freshBudget` in the adoption result and in the `run.revision_adopted` event. The desktop's Saved view shows the revision an active run executes.
- Runs carry `owner_machine_id`. A run imported from another machine rejects execution commands with `run_not_owned` until `takeoverRun`, which marks its leased attempts `lease_expired` (uncertain, needs reconciliation) and pauses the run.
- **Readiness** is computed server-side for the active sprint: a ticket is `ready` when every prerequisite is accepted in this run (or carried forward), it has no open attempt, its last attempt does not need reconciliation, it is under the retry limit, and capacity (sprint cap, plan `maxConcurrency`) allows. Tickets of later sprints are `later_sprint`. Blockers explain why (`prerequisite`, `row_check_failed`, `concurrency`, `retry_limit`, `lease_expired`, `run_state`). Readiness stays per ticket: there are no waves inside a sprint, and rows are not a barrier. Beyond its own prerequisites a ticket is held only by a failed row check on a row it depends on, and a sprint's acceptance node waits for every required work ticket of its sprint (see Sprint acceptance nodes, Rows and Row checks below).
- **Rows** (`groupIntoRows` and `planRows` in `src/core/plan/graph.ts`; the graph view uses the same function and only wraps a wide row at six columns) are the server's layer concept: within a sprint, a ticket's row is one below its deepest same-sprint prerequisite, so row 1 has no same-sprint prerequisites and prerequisites in other sprints do not count. A sprint's acceptance node is in no row (its `row` is null). `get_run` reports each ticket's `row` and, for every row of every sprint, its tickets and latest row check; `get_ready_tickets` reports the same for the active sprint.
- **Row checks** (`recordRowCheck`, MCP `record_row_check`, capability `run.row_check`, orchestrator only; table `row_checks`, schema v5, ids with the `rk` prefix) record `{ runId, sprintId, row, commit, checks[] }` as a run event (`run.row_check_recorded`) and in the run history. `checks` has at least one entry and the check **passes only when every entry has status `passed`**: a failed or skipped entry fails it. A run's checks are numbered in the order they were recorded and the highest number of a row is its latest. While a row's latest check has not passed, every ticket that requires a ticket of that row is `waiting` with a `row_check_failed` blocker (once per row, whichever of its tickets it requires), and a later passing check clears the hold. A sprint's acceptance node is held the same way while the latest check of **any** row of its sprint has not passed (one blocker per failed row). Nothing else is held: readiness stays per ticket, with no barrier between rows, and a ticket already accepted stays accepted.
- **Claim** (`claimTicket`) is transactional: re-computes readiness, creates an attempt (`claimed`) with `fencing_token` = previous claims + 1, a lease, and a secret; returns a claim token (`<attemptId>.<secret>`) and a bounded execution packet (pinned ticket content, acceptance criteria, predecessor outputs, constraints, reporting contract). The partial unique index on open attempts makes duplicate concurrent claims impossible. The token is shown once: a replay of the claim's idempotency key returns the same attempt and packet with `claimToken: null`, and nothing rotates the secret. A caller that lost the token, with no worker holding it, fails the attempt without a token (orchestrator only; it uses a try) and claims again; if a worker may hold it, the lease runs out and the attempt is reconciled. Either way the new claim needs a new idempotency key: the old key keeps replaying the lost claim.
- Heartbeat extends the lease (first heartbeat moves `claimed → running`). Late writes with a superseded or expired token fail with `stale_claim` / `expired_claim`. A heartbeat may carry `progress` `{ note (at most 280 characters), step? (at most 64) }`: it is stored as an `attempt.progress` event (time, sending session, `{ attemptId, note, step }`) in the local events table after any claim token in it is masked, the last 200 per attempt are kept, and it queues no outbox work and is not part of run history, so exports and their hashes do not change. A refused heartbeat stores no note.
- **Activity timelines** (`getAttemptTimeline`, `getRunTimeline`; `src/core/services/activity.ts`, entry shapes in `src/shared/domain/activity.ts`; capability `read`, desktop commands only, no MCP tool) are read models over the events table and the attempt as it stands now; they store nothing. An attempt timeline lists, in time order, the claim (worker label, model, host, effort, rationale), one `alive` span, progress notes, comments on the ticket made while the attempt was open (after its claim, until it closed), the submission, the decision, a failure, a lease expiry (or takeover) and its reconciliation, and the run ending under it. Plain heartbeats write no event, so they are collapsed into the `alive` span: first heartbeat (the `attempt.running` event) to `attempts.heartbeat_at`, with `active` true while the attempt holds a lease. A run timeline lists the run's starts, pauses, resumes and ends, claims, submissions, decisions, failures and lease events, sprint reports and checkpoint approvals and advances, grouped by the session that logged each (groups in order of first activity); notes and heartbeats stay in the attempt timeline. `isLive` is true while the attempt is open (`claimed`, `running`, `submitted`) or the run is active. **Cursor**: `cursor` is an event `seq`; pass it back as `sinceSeq` and a page holds only entries whose event came later (`limit` 1 to 500, default 200; when more remain the cursor stops at the last entry returned). The alive span is the one entry that grows without an event, so it is sent again, same id and a later `until`, on every poll while the attempt holds a lease and on any page that carries another entry (the attempt may have closed since the last poll); the client replaces an entry by id. Each read first expires overdue leases and runs in one transaction, so `isLive` and the entries agree. Every text in an entry is masked for claim-token lookalikes again on the way out, and attempt facts come from `attemptView`, which has no claim secret. The renderer polls with `src/renderer/src/app/activityPoller.ts`.
- Leases expire lazily: commands that read or write execution state first mark overdue `claimed/running` attempts `lease_expired`. Lease expiry is uncertainty, not failure: the ticket needs `reconcileAttempt` (`abandon`, or `resubmit` with outputs) before another claim.
- `submitAttempt` (worker/orchestrator with the claim token) → `submitted`. Submission never unlocks dependents.
- **Sprint increments** (`increment` on `submitAttempt` / MCP `submit_attempt`, acceptance nodes only; column `attempts.increment_json`, schema v6; `incrementVerify.ts`, `increments.ts` in `src/core/services`) check that a sprint reached the epic branch as **one squashed commit**. The acceptance node's submission names `{ branch, commit }`; the command layer asks the Git adapter read-only questions (`isAncestor`, `commitParents`: `git merge-base --is-ancestor`, `git rev-parse --verify`, `git rev-list --parents`, nothing that writes) and `submitAttempt` stores the verdict with the attempt, so gate evaluation stays synchronous SQL and never asks git. The checks, in order: the named branch is the epic's own `branch.name` (the epic's, never the caller's, is what everything else is measured against) · the commit exists · it has exactly one parent · it is reachable from `refs/heads/<epic branch>` · it comes after its base · no commit recorded (`outputs.commits`) by the sprint's accepted, current `work` attempts is reachable from the epic branch (that proves the sprint was squashed and not merged; carry-forward attempts and rejected or superseded ones are not counted). The base is the nearest earlier sprint's verified increment in the run (the new commit must not be reachable from it), else the epic's start commit (the new commit must come strictly after it). **An epic branch without a start commit** (`startCommit: null`) and no earlier increment has no base: the base check is recorded as `skipped` with that reason and the verdict can still pass; likewise the squash check is `skipped` when the sprint's accepted work recorded no commit hash. A skipped check never counts against an increment, a failed one does, and every verdict lists each check with its detail.
  - **A failed verdict is stored, not rejected.** `submit_attempt` still returns the attempt (state `submitted`) with `increment: { passed: false, reasons, checks, ... }`, so the orchestrator reads the reasons straight away, rejects the attempt with them, and the node is resubmitted as a new attempt. Accepting a node whose verdict failed does not help, because the gate reads that accepted attempt, and an accepted ticket cannot be claimed again in the run. A work ticket that names an increment is refused (`invalid_input`); a malformed branch or commit is refused by the input schema; a commit or branch git does not know is a failed check with a reason, never an error. Verification happens once, on submit: `reconcile_attempt` with `resubmit` stores no increment, so that node's gate stays unmet until a submission names one.
  - Read back: `get_run` lists `increments` (each sprint with an acceptance node whose standing attempt, or latest current attempt, named one: sprint, node, attempt and state, verdict), `get_sprint_report` and the checkpoint's `report` carry the sprint's `increment` beside the report (in a folder of repositories `increments` instead, one per repository in name order, and no `increment`; neither is in its content hash, so grants are unaffected), and the run history exports the verdict on the attempt record (`attempts[].increment`, absent when none was named, so history recorded before schema v6 keeps its bytes).
  - The integration target is the epic branch. Merging the epic into the default branch stays a person's step.
- **The sprint cadence** these pieces serve (the orchestrator's side is in `skills/orchestrator.md`; Dark Mechanicus records the commits and verdicts and asks Git read-only questions, but it never merges):
  1. Tickets are light. A worker branches from the sprint integration branch, runs only targeted checks (tests for the files it touched, typecheck when types changed, a screenshot only when a criterion needs one) and submits; the reviewer judges it against its own criteria and that evidence.
  2. The orchestrator merges each accepted ticket into a separate worktree on the sprint integration branch, which leaves the coordinating checkout on the epic branch (switching it raises `branch_changed`). When a row is fully accepted it runs the combined check (typecheck plus the tests touching that row's files) and records it as a row check.
  3. When the acceptance node is ready, the Definition of Done runs on the combined work (a slow check that has its own ticket is taken from that ticket's accepted result), each covered item is verified, and the sprint is squashed into one commit on the epic branch, which the node's submission names as its increment.
  4. The checkpoint gates on the node, the verified increment and the Definition of Done, and then on the person's approval. The full verification therefore runs once per sprint, on the combined work, and the epic branch gets one commit per sprint, never a merge per ticket.
- `acceptAttempt` / `rejectAttempt` (orchestrator/reviewer/desktop) decide a submission. Acceptance completes the ticket and unlocks dependents; rejection leaves the ticket retryable.
- `failAttempt` → `failed`. When a ticket exhausts `retryLimit` (+ user-granted retries), the plan's `onTicketFailure` applies: `continue_independent` (default; dependents stay blocked), `pause_run`, or `fail_run` (terminal; open attempts canceled). A failed dependency is never treated as complete.
- `carryForwardTicket` records a `carry_forward` attempt (state `accepted`) for a ticket already `completed` by an earlier run, with an explicit note.
- `cancelRun` cancels open attempts; `pauseRun` stops new claims (open attempts may still report).
- A run paused with the exact reason `signed_out` (the app's response to an orchestrator chat whose CLI login expired) keeps its open leases: `expireLeases` skips it whatever the lease time, and heartbeats still work. Only the desktop session holds `run.pause_signed_out` (human-only, like checkpoint approval), so `pause_run` with that reason from an MCP session fails with `unauthorized` and changes nothing. The desktop can also switch a run that is already paused for another reason (the ticket-failure policy, a person's pause) to `signed_out`: its overdue leases lapse first, `paused_at` becomes that moment, the open leases are kept, and a `run.paused` event records `from: paused` and the `previousReason`; a run already paused for sign-in is left as it is, so its `paused_at` is not lost. Resuming a run paused for `signed_out` needs the desktop-only `run.resume_signed_out` (human-only too): `resume_run` from an MCP session fails with `unauthorized` and a message that the person resumes it in the desktop app, and changes nothing; a run paused for any other reason is resumed as before. Every pause records `paused_at` (schema v8, local, not exported); `resumeRun` after a `signed_out` pause extends each open lease by the time the run spent paused and records a `run.leases_extended` run event (`pausedAt`, `extendedMs`, each attempt's old and new lease end). Other pause reasons, and `takeoverRun`, expire leases as usual.

### Sprint checkpoints

- `submitSprintReport` stores report revision n+1 (content hash recorded) and moves a `running` run to `awaiting_checkpoint`; no new claims while awaiting a checkpoint.
- Gate conditions (`getCheckpoint`), in this order: report submitted for the active sprint (`report_submitted`) · no open leases in the sprint (`no_active_leases`) · every required ticket accepted (`required_accepted`; the sprint's own acceptance node is left to the next condition) · (sprints with an acceptance node) the node accepted (`acceptance_accepted`) and its increment verified (`increment_merged`: the node's accepted submission, else the one awaiting review, carries a passing increment verdict; a rejected or superseded attempt never counts) · (and, when the project has a Definition of Done) `definition_of_done`: the node's accepted, current attempt reports every named check as passed in its evidence (see below) · (sprints with an acceptance node) the latest report includes a retro with something in it (`retro`; see Sprint retros) · every exit criterion reported met (`exit_criteria`) · (final sprint) epic outcome with all success criteria met (`epic_outcome`) · the run executes the epic's current plan (`plan_current`; see The retro and the redraft loop) · authorization (`approval`).
- Authorization: sprint `checkpoint.mode = human` (default) needs a one-use **approval grant** issued by the desktop (`approveCheckpoint`), bound to project, epic, run, pinned revision, sprint, report id, report hash, and action. `advanceSprint` consumes the exact grant in the same transaction as the transition. A new report revision, an adopted revision, or a consumed grant invalidates it (forged/replayed/stale grants fail). `auto` mode only takes effect when the person enabled `authorizeAutoContinue` on that run; plan edits cannot relax this, and imported runs never carry the authorization.
- `approveAndAdvance` is the desktop's single-click path (issue + consume atomically). `approveWithRedraft` is the desktop's one step for a checkpoint that has a redraft (see The retro and the redraft loop).
- Advancing the final sprint completes the run and the epic (records the outcome). The final gate checks every required ticket of the plan, not only the final sprint's.
- Checkpoint reads and advances first expire overdue leases, so the gate never shows an expired claim as still holding a lease.
- `grantRetry` (desktop) allows one more attempt for a ticket in this run and returns an `awaiting_checkpoint` run to `running`.
- Idempotency keys make repeated advance calls return the original outcome.

### Sprint retros

- A sprint report may carry a `retro` (the sprint review and retrospective): `delivered` (`{ ticket, demo, evidence }`: what to look at and where), `wentWell`, `wentPoorly`, `actions` (process changes for the next sprint), `discoveries` (`{ title, body, ticket? }`: new work found), `leftovers` (`{ ticket, reason }`: required work not accepted) and `tierFit` (`{ ticket, verdict: right_sized | oversized | undersized, note }`). Every list is optional on input. A `ticket` is a ticket id or display key; the server resolves it against the run's pinned plan, stores the stable id, and refuses an unknown ticket with `invalid_input` naming the field (`retro.leftovers[0].ticket`). The retro is part of the report content, so it is in `contentHash`; types are in `src/shared/domain/retro.ts`, resolution and the search text in `src/core/plan/retro.ts`.
- The `retro` gate belongs to a sprint with an acceptance node (plans saved before nodes are unaffected). It is met when the sprint's latest report revision has a retro with at least one entry in some list, so a later revision that leaves the retro out puts it back to unmet and its earlier approval does not carry over. It sits after the node gates and before `exit_criteria`.
- A report read as `SprintReportView` adds `tierFacts`, one entry per ticket of the sprint, computed from the run's attempts on every read (never stored, never in the content hash; `src/core/plan/tierFacts.ts`): `size`, `plannedLevel`, `plannedEffort` (null when the ticket sets none), each work attempt's `modelId`, `effort`, `label` and `fallback`, `attemptCount`, `rejectionCount` (rejected attempts only) and `escalated`. Carry-forward attempts are not counted. `escalated` means some attempt used a higher model tier (cost tier, then highest reasoning level, as `compareTier` orders them, using the run's host catalog) or a higher effort than some earlier attempt. Models are compared only when the catalog lists both and efforts only when both were recorded, so an attempt with no model and no effort (an orchestrator fallback, labelled "Orchestrator (fallback)") is listed, flagged `fallback`, and counted, but never ranked.
- **Redrafting the next sprint** (`redraftNextSprint`, MCP `redraft_next_sprint`, capability `run.redraft`: the orchestrator and the desktop; `src/core/plan/redraft.ts`, `src/core/services/redraft.ts`) turns the retro into the epic draft while the run waits at its checkpoint. It reads the retro of the latest report revision for the run's active sprint (`not_found` without a report, `conflict` for a report with no or an empty retro, `run_not_active` unless the run is awaiting its checkpoint) and rewrites the draft, never the saved plan or the run. Each leftover moves from the active sprint to the sprint after it, ahead of that sprint's acceptance node, together with the tickets of the active sprint that require it (transitively, in sprint order, listed as `dependentsMoved`); a sprint with its own acceptance node is added after the active one only when it is the last and something has to go in it. An explicit dependency of the active sprint's acceptance node on a moved ticket is dropped (`droppedDependencies`), because a node requires every required ticket of its sprint without one; the node itself never moves. Each discovery becomes an unsized ticket in the next sprint, after the moved tickets and ahead of the node, whose `references` hold the source ticket's display key (`{ kind: 'ticket', label: key, location: key }`). A leftover that is an acceptance node, is not in the active sprint, is already in the next one, is not in the draft or was accepted since the report, and a discovery whose title a ticket of the draft already has (ignoring case and spacing) or that has no title, is skipped and listed in `skipped` with a code and a reason, never refused. A second call over the same retro changes nothing (`changed: false`, same draft revision, no event). A change writes one `draft.redrafted` event. The result holds the sprints, `moved`, `dependentsMoved`, `added`, `skipped`, `droppedDependencies`, `changed`, `draftRevision` and the draft's validation (with the run-aware warnings); the orchestrator then sizes and describes the new tickets with `update_plan_draft`, writes the next acceptance node's `covers` criteria and validates the draft, and the person saves and adopts it with the retro's approval (see The retro and the redraft loop).
- Compatibility: a report saved before retros has no `retro` key; it reads with `retro: null` and keeps the content hash it was stored with. A report submitted without a retro stores `retro: null` (as `effort: null` is stored on a worker), so run history that holds one is not readable by an older build, whose strict schema does not know the key. The portable report schema gives `retro` no default (`nullable().optional()`), because a default of null would add the key to every earlier run history and change its bytes and tracked hash; a report written without one parses and re-exports exactly as it was (`legacyRecords.test.ts`). Retro text, with ticket keys, is indexed for search both when a report is submitted and when a run history is imported.

### The retro and the redraft loop

The retro turns what a sprint left over and found into the next sprint's plan, and one approval by the person covers both the retro and the plan change. The pieces are above (the retro, `tierFacts`, the redraft) and below (the gates and the one-step approval); this is how they fit, in order.

1. **Report.** The reporter (`skills/sprint-reporter.md`) writes the retro from evidence: `delivered` with what to look at, an honest `wentWell` and `wentPoorly`, a `tierFit` verdict per ticket taken from the computed `tierFacts` (never from impression), `discoveries` lifted from the workers' structured notes (each has a title and a reason, `skills/worker.md`) and from review notes, `leftovers` with their reasons, and `actions` for the next sprint. The orchestrator submits it with `submit_sprint_report`, and the run waits at its checkpoint.
2. **Redraft.** The orchestrator calls `redraft_next_sprint`. Only the epic's draft changes: leftovers (with the tickets that require them) move into the next sprint, discoveries become unsized tickets there, and a sprint is added after a final one. The orchestrator then refines the draft with `update_plan_draft` or `update_ticket`: it sizes every new ticket, writes the `covers` criteria of the next acceptance node for the moved and the new items, and validates the draft (`validate_plan`). The run-aware warnings (`runAwareWarnings` in `src/core/plan/runWarnings.ts`) flag any change to a sprint the run has passed and any sprint inserted before the active one: the draft changes only future sprints, and a passed sprint is never edited (see the planner skill). This is the one place the orchestrator changes a plan that a run is executing, and it adds tickets only to later sprints. The orchestrator tells the person that the retro and the redraft are ready to approve in one step.
3. **Gate.** Two checks keep the approval honest:
   - `plan_current` (after `epic_outcome` and before `approval`; every sprint, with or without an acceptance node) is unmet while the epic's draft has changes the saved plan lacks (`changedDraftRevision`: a draft that equals the saved plan, as one just opened does, is no change) and while the epic's current saved revision is newer than the run's and not adopted. Its detail says which, and what to do: save the draft and adopt the new revision, discard the draft, or adopt the revision.
   - A report goes stale after an adoption. `report_submitted` is unmet again, with the reason, when the run's revision differs from the one the report was written for (`sprint_reports.revision_id`, a machine-local column) and the sprint's exit criteria changed, a required ticket was added, or a required ticket left by a route other than moving a retro leftover or a ticket that requires one (`sprintScopeChanges`, `src/core/plan/sprintScope.ts`). A new report revision is then due. A report that did not record its revision is never stale. Moving the retro's leftovers out, and adding tickets to later sprints, leave the report current.
4. **Approve retro & redraft.** `approveWithRedraft` (desktop only: capability `checkpoint.approve`, and it also requires `plan.save`, `run.adopt` and `checkpoint.advance`, which no agent role holds, so an agent is refused with `unauthorized` before anything is saved; there is no MCP tool for it, and agents can never approve) takes `{ runId, expectedDraftRevision, reportId? }`, where `reportId`, when given, must still be the sprint's latest report (`conflict` otherwise). In order: (1) **save** the draft (overdue leases are expired first; saving an unchanged draft is fine) and flush the outbox so the revision is saved and current (`save_pending` if it is still pending); (2) **adopt** the saved revision into the run, unless the run already executes it (moved leftovers get a fresh retry budget: `freshBudget`); (3) **recompute** every gate on the adopted revision, so the moved leftovers no longer count; (4) **approve** the report, issuing a grant bound to the adopted revision; (5) **advance**, consuming the grant. The save commits on its own, because a file write cannot be rolled back with a database transaction. Steps 2 to 5 run in one transaction: a refusal at any of them rolls all four back, so the run stays on its old revision with nothing approved or advanced, the saved revision stays saved, and the error names the step (`details.step`, `stepNumber`, `savedRevisionId`, `savedRevisionNumber`, `adoptionNeeded`). The result holds `save`, `adoption`, `approval`, `advance` and the `run`. On the final sprint with the redraft's added sprint, it advances into that sprint instead of completing the epic, because the gates are recomputed on the adopted plan where the active sprint is no longer the last. The desktop's button for it is "Approve retro & redraft"; "Approve & advance" stays for a checkpoint with no redraft.
5. **The acceptance-node limitation.** In a sprint with an acceptance node, a required ticket that is not accepted (a leftover) keeps the node from ever being ready, because the node requires every required work ticket of its sprint (`implicitPrerequisitesOf`, `src/core/plan/acceptance.ts`). The node can therefore never be accepted while the leftover is in the sprint, `acceptance_accepted` stays unmet, and `approveWithRedraft` stops at its recompute step and rolls the adoption back: the moved leftover no longer blocks on the adopted plan, but the node has not run and is not accepted there. The code allows this route instead (the orchestrator's side is in `skills/orchestrator.md`):
   1. Submit the report with the retro, listing the leftovers. `submitSprintReport` accepts it while the run is `running` or `awaiting_checkpoint` whether or not the gates are met.
   2. Redraft, refine and validate the draft as above.
   3. The person saves the draft and adopts the new revision in the desktop app. `adoptRevision` is allowed only at a checkpoint (or while paused) with no open attempts. The leftovers and the tickets that require them leave the sprint, the unchanged accepted tickets keep their acceptance, and the run stays in `awaiting_checkpoint`; the sprint stays the active one because it survives under its id.
   4. The run takes no claims in `awaiting_checkpoint` (readiness reports a `run_state` blocker), so the orchestrator calls `pause_run` (allowed from `awaiting_checkpoint`) and `resume_run`, which returns a started run to `running`, and then runs the acceptance node over what remains like any other: it is ready once every remaining required ticket is accepted and no row check is failing.
   5. The orchestrator submits a new report revision (`submitSprintReport` moves the `running` run back to `awaiting_checkpoint`) with the retro carried again. The gates do not force it, since moving leftovers out does not make the first report stale, but the first report predates the node's acceptance and increment, and a grant is bound to one report's id and hash.
   6. The person approves. The draft was saved and adopted, so `plan_current` is met and no draft remains for `approveWithRedraft` to save: the plain "Approve & advance" applies.

   Where the leftover is in the final sprint, the redraft adds a sprint after it, and once the revision is adopted the active sprint is no longer the last, so `epic_outcome` is no longer asked of it.

### The project's Definition of Done

- A project's Definition of Done is the team's one standard of "done": ordered checks `{ name, command, description }`, stored once in `.darkmechanicus/project.json` (`definitionOfDone`, optional with no default, so a project record written earlier parses and re-serializes unchanged). It is written only by `setDefinitionOfDone` (tool `set_definition_of_done`, capability `project.definition_of_done`, held by the planner and the desktop; the orchestrator reads it through `getProject` but does not hold the capability, because it accepts work against the standard) and through the app's own writer (`src/core/repo/projectConfig.ts`: sorted keys, two-space indent, trailing newline, atomic replace; an empty list removes the key). It is read from the file on every use (`Ctx.definitionOfDone()`), so a change by another session or by hand applies at once; `getProject` returns it as `definitionOfDone`. Names must be unique ignoring case and surrounding spaces, at most 50 checks.
- The execution packet of a sprint acceptance node lists the checks (`definitionOfDone`) and adds a reporting instruction; no other ticket's packet carries them.
- The `definition_of_done` gate belongs to a sprint with an acceptance node, when the project has a Definition of Done (with none, the gate is left out and sprints are gated exactly as before). Dark Mechanicus runs no command: it reads the `evidence.checks` of the node's accepted, non-superseded attempt (not one awaiting review). A check passes when the evidence names it, matching trimmed and ignoring case (never by containment), at least once and every entry under that name has status `passed`; the gate's detail names each check that was not reported, failed, or was skipped.
- In a folder of repositories the project has no list of its own: each repository has its own `definitionOfDone` in its `repositories` entry (written by `setDefinitionOfDone` with `repo`). The acceptance node's packet lists each touched repository with its checks, the node reports them as `<repo>: <check>`, and the gate checks every touched repository's list by those names.

### Comments

- Comments are append-only Markdown notes on an epic (`ticketId` null) or one of its tickets, written by people (desktop) and agents (MCP). There is no edit or delete (deletion stays deferred product-wide). Table `comments` (schema v3), ids with the `cm` prefix.
- `addComment({ epicId, ticketId?, body, idempotencyKey? })` needs capability `comment.write`, which every role holds; `listComments({ epicId, ticketId? })` needs `read` and returns comments oldest first (`created_at`, then id): without `ticketId` every comment of the epic, epic-level and ticket-level; with it only that ticket's.
- The author is the calling session's role and label (the label cut to 200 characters), never input. The body is Markdown, not blank, at most 20,000 characters (`commentBody`). A `ticketId` must be in the epic's current saved plan or its draft (else `not_found`). Completed epics refuse new comments with `completed_epic`; their comments stay readable. The branch guard applies, and an epic holds at most 10,000 comments (`capacity_exceeded`), the most a reconcile reads back.
- Each comment appends a `comment.added` event (payload: comment id and author) and a search document of type `comment` (title "Comment by <label>", body the Markdown), so `search_history` finds comments and labels them.
- Export: one immutable file per comment, `epics/<epicId>/comments/<commentId>.json` (format `darkmechanicus.comment` v1), so writers on different machines never touch the same file. A `comment` outbox entry (epic id, entity id = comment id) is queued in the same transaction; the finalizer writes the file with `writeFileSafely`. An existing file must hold the same comment (else `conflict`, never rewritten). Comment entries never block, or wait for, their epic's plan records. A checkout whose tree lacks the epic's `current.json` (a branch without the epic) gets no comment file, since a folder holding only `comments/` would be rejected by every reconcile: the entry fails with a retryable message and is exported once the epic's records are back (for example, after checking out the epic's branch); the epic's records are never written there for it. Like the epic itself, comments of a never-saved epic stay local: completing the epic's first save queues every comment without an export record, and the finalizer runs up to three passes so entries queued while flushing are written by the same flush.
- Import: for every epic whose own records are not rejected, the importer reads `comments/` as untrusted input: containment and link checks, regular files only, at most 256 KiB per file and 10,000 files per epic, names `<commentId>.json` built from validated ids (dot entries and other names such as temp files are ignored), the strict schema, and an id and epic matching the path. Each bad file is rejected on its own. New comments are inserted, indexed, and recorded in `sync_state` (kind `comment`); an id that already exists with different content is a conflict (reported with its epic, never overwritten) that clears once the file matches again. A comment waiting for export does not count as an unexported epic change.
- Desktop: the ticket panel's Comments tab lists a ticket's comments (author, role, time, body through the safe Markdown renderer) and, for open epics, adds one.

### Named capability profiles

- A named profile is a reusable, provider-neutral `CapabilityProfile` preset (for example `ui-implementation` or `deep-review`) that tickets start from. It names no vendor or model; an exact model stays the `preferences.modelOverride` preference, as on tickets.
- **Names** double as file names (`profiles/<name>.json`), so they are portable on Windows, macOS, and Linux: 1-64 lowercase letters, digits, and hyphens, starting and ending with a letter or digit, and never a Windows device name (`con`, `prn`, `aux`, `nul`, `com0`-`com9`, `lpt0`-`lpt9`). `src/core/profileNames.ts` holds the rule; the owned-path builder, the command schemas, and the record schema all apply it.
- **Commands:** `listProfiles` (sorted by name) and `getProfile` (`not_found` when missing) need `read`. `saveProfile` needs `profile.write` (desktop, planner, orchestrator), honours the branch guard and idempotency keys, and replaces the whole profile: it creates at revision 1 when `expectedRevision` is absent or 0 and replaces only at the current revision; anything else is `conflict`. The description has at most 500 characters (omitted means empty); the capability is complete and validated with the ticket schema, and its skills are normalized like a ticket's. Each save appends `profile.saved` and queues a `profile` outbox entry keyed by name (`outbox.entity_id`).
- **Revision** is the local database's optimistic-concurrency counter and is not tracked: a clone starts at 1 and every import bumps it.
- **Tickets copy profiles.** Applying one (the desktop editor's "Start from profile", or an agent passing a profile's `capability` to `create_ticket`/`update_ticket`) copies the requirements into the ticket; later profile saves never change existing tickets or saved revisions. The desktop writes only on Apply, and "Save as profile…" stores the requirements shown under a name. Apply writes only the requirement groups the person changed since the editor loaded the ticket (through a field or a profile; `context` per field); the others keep the draft's latest values, so it never reverts an agent's concurrent `update_ticket`.
- Deleting profiles is deferred like every other deletion.

## Repository-owned persistence

```text
.darkmechanicus/
  .gitignore                          # "local/" — the live database never enters Git
  project.json                        # project id, name, key prefix, format version, optional Definition of Done
  epics/<epicId>/current.json         # saved-revision pointer + content hash + generation
  epics/<epicId>/state.json           # epic status, branch, outcome, ticket statuses (durable)
  epics/<epicId>/snapshots/<revId>.json  # complete immutable plan bundles
  epics/<epicId>/comments/<commentId>.json  # one immutable file per comment
  history/<runId>/run.json            # run, attempts, reports, checkpoints, row checks (no leases, tokens, or grants)
  profiles/<name>.json                # named capability profiles (darkmechanicus.profile records)
  local/                              # Git-ignored: state.sqlite(+wal/shm), machine.json
```

- Files are pretty, key-sorted JSON (`prettyJson`) for reviewable diffs; hashes use canonical JSON (`contentHash`).
- A run's `rowChecks` list is optional and has no default: a run without row checks exports without the key, so history written before row checks existed still imports and re-exports byte for byte. Each entry carries its id, number, sprint, row, commit, entries, who recorded it and when; the importer stores them in `row_checks` and refuses a run that lists a check another run already owns.
- **Finalizer** (flush): processes `outbox` entries in id order under the database write lock. Snapshot files are written to a temp file, fsynced, renamed, read back and hash-checked; the pointer is replaced by atomic rename last. A previous snapshot is never rewritten in place. Interruption at any boundary leaves the last good pointer intact and the entry pending; a retry is idempotent. The filesystem is injected so tests can fail each write boundary.
- **Unimported epic records are never overwritten.** Before it writes an epic's `state.json` and `current.json` (and before a save's snapshot), the finalizer checks the Linear transfer hold first (unchanged), then hashes the files on disk (`trackedEpicHash`) and requires the hash to be the `exported_hash` or `imported_hash` of the epic's `sync_state` row, or one its export intent names: what this machine last wrote or read. The export intent (`local/exports/<epicId>.json`, machine-local) lists the hashes an export may leave on disk (new state over the old pointer, both new, new pointer over the old state) and is written before anything is replaced, so a process that dies before its row commits does not lock itself out; a failed write also puts both files back. It covers only that uncommitted export: it is removed once the entry commits, and it counts only while the epic's `sync_state` row is still the one it was written against, so after a branch round trip or a stash and pop that reconciled other records, this machine's earlier export is not trusted. A checkout without the files has nothing to lose; files with any other hash, or with no row and no intent, were written elsewhere and not imported here, so the entry fails with `conflict` and waits. Reconcile reports the epic's pending-export conflict; storage status marks it `resolvable` while the condition still holds. Only the person settles it: `resolveEpicConflict` (desktop only, human-only capability `repo.resolve_conflict`, no MCP tool; the Storage card's **Keep tracked records** and **Write local**). Keeping the tracked records first flushes the epic's waiting run histories, then, in one transaction that writes no file, drops the epic's waiting state export and any waiting save (revision marked `failed`, draft kept) and imports the tracked records, or changes nothing. Writing local commits the choice (exactly the found hash as `imported_hash`), then flushes only that epic; a failed write is reported and retried by every flush. No file is written inside a transaction that can still roll back. One consequence: a change that waits while the checkout holds this machine's export from another branch (switch branches, an agent accepts work, then reconcile) now asks the person to choose instead of being written silently.
- **Initialize** is explicit and repeatable: creates the layout, `project.json`, `.darkmechanicus/.gitignore`, and `local/machine.json`; never commits.
- **Reconcile / import** (open, clone, pull, branch change): every tracked file is untrusted — size limits, merge-marker rejection, zod schemas, stable-id checks, snapshot hash verification, full graph validation, and path containment. The whole import is staged and validated before one transactional swap; a failure leaves the last good state and drafts untouched. An `epics/`, `history/`, or `profiles` that is a link, resolves outside `.darkmechanicus/`, or is not a directory is rejected and reported and read as empty, so opening a repository (which reconciles) never fails on hostile layout. An epic whose tracked state changed while it also has unexported local changes is a **conflict** (surfaced, not overwritten). A branch change pauses active runs until reconciled. Unchanged records are not re-read on every heartbeat: an epic whose pointer and state match the last sync skips its snapshots, and each workspace remembers the stamp (size, modification and change times, inode; `FsAdapter.fileStamp`, which never follows a link) and hash of every comment and profile file it read, so a file keeping its stamp with a synced hash costs one `lstat` (`src/core/repo/fileHashes.ts`). A changed stamp, a link, or a hash that is not synced means a full read with every check. A `repository.reconciled` event is recorded when a reconcile imports something, sees the branch change, or reports conflicts or rejections other than the previous reconcile's (a digest in `meta`), so a file that stays rejected adds no event on every heartbeat.
- **Profiles** are exported by the finalizer like the other records (`writeFileSafely`, export hash in `sync_state` with `kind = 'profile'`; a failed write blocks later writes of that profile only) and imported by `src/core/repo/profileImport.ts` inside the same reconcile transaction. Dot entries and names not ending in `.json` (such as the temp file of an interrupted export) are ignored, as in `comments/`; a `.json` entry that is not `<valid-name>.json`, a link, a junction resolving outside, a directory, an empty file, a file over 256 KiB, or a record that fails the strict schema or names another profile than its file is rejected and reported without stopping the rest; more than 1,000 entries rejects the directory unread. A `profiles` that is a link, resolves outside, or is not a directory is rejected and reported the same way and read as empty, so the rest of the reconcile goes on and opening the repository (which reconciles) never fails on it. A file whose hash matches the last export or import is unchanged; a changed one is imported (content and dates from the record) unless the local profile has an unexported save. That is a conflict, reported in `profileConflicts` (reconcile result and storage status): the local profile is kept and its next export wins, which clears it, as for epics.
- Owned file operations use app-generated relative paths from validated ids and verify the resolved real path stays inside `.darkmechanicus/` (symlinks/junctions included); failures are `unsafe_path`. Imported references are inert strings.
- Machine-local state (leases, claim secrets, approval grants, auto-continue authorizations, sessions, absolute paths) is never exported.

## MCP server (`src/mcp`)

`node out/main/mcp.js --repo <path> [--role orchestrator|planner|worker|reviewer] [--allow-save] [--label <name>]` (packaged: the app executable with `ELECTRON_RUN_AS_NODE=1`). Diagnostics go to stderr. Tool results are JSON (`{ ok: true, data }` or `{ ok: false, error: { code, message, details } }`) in both `content` text and `structuredContent`, with `isError` on failures; arguments that fail a tool's input schema are `invalid_input`. A session lists only the tools its role may call. Skills are exposed as MCP prompts.

## Desktop (`src/main`, `src/preload`, `src/renderer`)

- Tracked folders are a machine-local list in `userData/folders.json`, keyed by canonical real path (tracking an existing path selects it instead of duplicating). Stop tracking removes only that entry.
- The main process caches one Workspace (desktop session) per folder. IPC channels `dm:*` validate payloads and call `CommandApi`, and only after the sender check below. The `agents:*` and `chats:*` channels (see [Hosted agents](#hosted-agents)) validate theirs the same way and do not call `CommandApi` themselves. The renderer polls `listEvents` with a cursor (bounded interval) and refetches what changed; unsaved form edits survive refreshes and conflicts.
- Markdown is rendered by a small safe renderer (no raw HTML); links are allow-listed (`http`, `https`, `mailto`) and opened through the main process. Navigation and new windows are denied.

## Hosted agents

The desktop hosts four built-in agent CLIs, `claude` (Claude Code), `codex`, `cursor` and `autonomous` (`a8s`), and custom CLIs: it connects them, installs the downloadable ones, asks each built-in whether it is signed in, runs each chat as the agent's own CLI in a terminal in the app's window and starts them as a run's orchestrator (design: [`design/chat-shells.md`](design/chat-shells.md)). The product decision is in [`product-plan.md`](product-plan.md#agents-hosted-in-the-desktop-app); the user guide is [`runbooks/agents.md`](runbooks/agents.md). None of it is in `src/core`: no business rule lives here. A chat's agent reaches a repository by running the `dm` CLI (`--repo` the chat's folder) with a grant at the chat's role that main issues for the chat and puts in its environment as `DM_SESSION_TOKEN` (`chatGrants.ts`); `cliInstructions.ts` tells it the exact command, in the chat's instructions file (`terminalFiles.ts`). The desktop's own Workspace is used only for the run commands described below. Everything here is machine-local state under `userData`, never a portable record.

The renderer names only an agent id or kind, a folder, a chat, a model, a role or a title, and for a custom CLI its name and arguments. It never supplies an executable path or a download address: the executable comes from a native file dialog in main (Find, Add a custom CLI), from the vendor's installer (Download) or from the registry.

Rules the connection code keeps:

- **No shell for a path someone chose.** On macOS the executable is one argv entry. On Windows an `.exe` or `.com` is run directly; a `.cmd` or `.bat` shim goes through the shared shim launcher (`src/main/agents/shimLaunch.ts`): exactly one `cmd.exe /d /v:off /s /c` parse with the path in one pair of quotes, so `&`, `^`, `(` and spaces in it are literal. There is no `start`, no nested `cmd.exe` and no shell option anywhere. A path or an argument holding `"`, `%` or a control character (or an argument ending in a backslash) is refused (`unsafe_path`), never escaped. Any other Windows extension is refused as not runnable. Every argument after the path is a constant, or a model id checked by `isSafeModelId` (`src/shared/agents/models.ts`); the launcher quotes an argument only where it needs it. Stopping a process uses `killProcessTree` (`src/main/agents/processTree.ts`), which resolves once the process and what it started are gone, so what a shim started goes with it. A Claude `.cmd` shim is not launched at all: a chat terminal follows the shim to the program it runs (`terminalLaunchSpec.ts`).
- **The installer runs without a shell string.** PowerShell is given the downloaded script with `-File` (and `-NoProfile -NonInteractive -ExecutionPolicy Bypass`); on macOS the script is the argument of `/bin/bash` or `/bin/sh`. The confirmation is a native message box that shows the source, the command, the install folders and how the download is checked. Cancel is the default; only a click on the first button installs. The renderer cannot answer it.
- **The app never touches a credential.** Sign in runs the CLI's own login (`claude auth login`, `codex login`, `agent login`, `a8s init`) in a sign-in terminal in the app's window; the vendor's own page does the signing in. The status command's output is classified and dropped, never stored or returned.

### Chats: records, store, terminals

A chat is a record and a terminal: the agent's own CLI runs in a PTY in the app's window, with its own approvals, model picker, sign-in prompts and subagents. The app no longer drives any vendor protocol, stores no new transcript and holds no approval: what a chat stored before chats became terminals stays readable, read-only.

The renderer side is `src/renderer/src/agents/` (the add-agent pane and agent page, `NewChatFields.tsx` (`newChatAgent`, the agent one-click **New chat** uses, and the agent and model choices of Start run), `TerminalPane` with **Earlier conversation** above the terminal, the sign-in view and `SignInTerminal`, the read-only `ChatTranscript` with `ApprovalRecord`, `SignInPrompt`, and the `useAgents`, `useChats` and `useTerminal` hooks), `src/renderer/src/sidebar/AgentsSection.tsx` and `AgentsBlock.tsx`, for runs, `src/renderer/src/epic/StartRunDialog.tsx` (its model choice is `agentModels`, through `useAgentModelChoice`; in a folder of repositories it asks for the epic branch first) and `RunBar.tsx`, and, for Linear transfers, `src/renderer/src/epic/TransferDialog.tsx`, `LinearTransfer.tsx` (the transfer strip and the Transferred to Linear panel) and `transferActions.ts`. **New chat** has no dialog: `startNewChat` (`App.tsx`) creates the chat with the folder's default agent while it is connected (else the first agent that can chat), as an `orchestrator` with `allowSave` on and no model, and opens it; with no agent connected it opens the add-agent pane.

**Roles and the chat's `dm` grant.** Before the agent starts, `issueChatCli` (`src/main/agents/chatGrants.ts`) issues a grant in the chat folder's workspace with the chat's role, `allowSave` only when it is set and the role is `planner` or `orchestrator` (`canSavePlans`), the label `"<Agent> · <chat title>"` and a fixed lifetime, and adds its token as `DM_SESSION_TOKEN` to the `dm` invocation `buildCliConfig` (`src/main/desktop/cliConfig.ts`) pins to the folder. The grant is revoked through the same workspace when the session ends. The role is fixed for the chat's life. `chats:create` takes the role and `allowSave` from the person; `chats:startOrchestrator` takes neither (see below).

**The chat store.** `userData/agents/chats/<folder key>/index.jsonl` holds one line per change of a chat record (the last line for an id wins), and `<chat id>.jsonl` the transcript a chat stored before chats became terminals, one `ChatItem` per line; nothing writes a transcript any more. The folder key is the first 24 hex characters of the SHA-256 of the folder's canonical real path, so every spelling of a folder finds the same chats and untracking a folder leaves them. The index is appended to; a truncated last line is repaired on the next append and skipped on read, as is a line of a kind a newer build wrote. Deleting a chat is the one rewrite: its transcript file is removed and the index is replaced atomically without any line of that chat. A record is masked for claim tokens before it is written.

**Activity bindings.** A terminal chat is linked to the attempts and runs it acts on by grant: `chats:boundTerminal` (`grantBindings.ts`) finds the chat whose grant the claiming (or starting) session used, and the Activity tab and orchestrator feed offer **Open terminal** to it. Old chats keep the item-based links they stored in `userData/agents/activity-bindings.jsonl` (chat id, thread id or null for the main thread, folder, run or attempt id, and `orchestrator` or `worker`); nothing adds to them, and deleting a chat removes its own. `chats:boundThreads` answers them (`boundThreads.ts`), limited to the chats of the folder that was asked about. The renderer's Activity tab (`src/renderer/src/ticket/ActivityTab.tsx`) and orchestrator feed (`src/renderer/src/epic/OrchestratorFeed.tsx`) show such a thread through `useThreadStream`: the chat is read once with `chats:read`, nothing is pushed or polled, and its approvals are records with the decision stored for each. A thread can have served several attempts of a ticket, so an attempt's tab clips the rows to that attempt's own window (`attemptWindow`: its claim to its end, or to now while it is open).

**The chat's folder.** Every start of a chat's terminal checks its folder on disk first (`resolveLaunchFolder`, `src/main/agents/launchFolder.ts`): the stored path must still exist, be a directory, be its own real path (a symlink swapped in leads elsewhere) and be tracked. The checked path is the one the grant and the `dm` command are issued for (`--repo`), the terminal's working directory and a custom CLI's `{folder}`. A folder that fails is refused with a `not_found` error naming it and the reason, before a grant is issued.

**Sign-in.** Before a chat's terminal starts, the agent's own status command is asked (`agents:status`); a signed-out agent starts nothing and the pane offers Sign in, which runs the CLI's login in a sign-in terminal (`loginTerminals.ts`). A login the CLI stops accepting mid-chat is the CLI's own to report in its terminal. When an orchestrator chat's CLI exits on its own and its status command then says `signed_out`, the chat's `running` or `paused` run is paused with the reason `signed_out` through the folder's own desktop Workspace, the only session that holds `run.pause_signed_out` (see [Runs, readiness, and attempts](#runs-readiness-and-attempts)). Nothing is resent and no run is resumed by the app itself. An old chat whose turn a lost sign-in cut short (`cutShortMessageId`) is flagged in the sidebar while its agent is signed out; the status is asked again when the window regains focus.

**Starting an orchestrator.** `chats:startOrchestrator` (`startOrchestratorRun`) takes only a folder, an epic, an agent and a model. In main it reads the epic, queues the run through the desktop's own `queueRun`, creates the chat as `orchestrator` with `allowSave` off, titled `Orchestrator · <epic title>`, records the run's id on the chat (`runId`), and starts the chat's terminal (`TerminalSessions.start`) before it answers; the renderer then opens the chat, so the app shows its terminal. The chat's instructions file holds the orchestrator and worker guidance after the `dm` instructions: the steps, the guides in marked sections read with `skillBody` from the same text the server serves as prompts, and a step that says how each worker subagent is started: it is given its whole execution packet and the worker guidance, runs in the orchestrator's session, and heartbeats and submits for itself, while the orchestrator reviews and decides. The claim token reaches the worker only through that packet. The kickoff is only fixed text and the run lines (epic, branch, run id, the first step; in a folder of repositories, also one `repository → branch` line per repository the epic branch is bound in, with the reminder to work in a worktree of each repository), built from ids, the epic's title and its branch names, never from anything that grants access, and it goes only with the chat's first start (`kickoffSent` on the record), never with a resume: Claude Code takes it as its positional prompt (`kickoffSent` stored before the spawn); every other CLI, and any `.cmd` shim, has it written as one bracketed paste and Enter once its first screen has taken no output for a second (`pasteFirst`, which also carries the instructions of a CLI with no instructions flag). A failure before the run is queued is an error and nothing exists. After it, the run stays queued and the result's `problem` says why no agent is running it (the chat could not be created, or its terminal did not start: a folder refused, the agent not connected or signed out, a spawn that failed; the chat is then removed again, or kept and returned when it cannot be removed). A CLI that starts and then exits leaves its chat to read and start again. The agent then calls `start_run`, which picks up the queued run.

**Starting a transfer chat.** `chats:startTransferChat` (`startTransferChat`, `transferStart.ts`) takes the same four fields. In main it reads the epic and its transfer through the desktop's own `getEpic` and `getTransfer`, and refuses, with nothing created, unless the person authorized the transfer (`queued`) or an agent already started it (`in_progress`). It then creates the chat as `orchestrator` with `allowSave` off, titled `transferTitle(epic title)` (`Linear transfer · <epic title>`), records the epic's id on the chat (`transferEpicId`), and starts its terminal (`TerminalSessions.start`) with `transferKickoff` as the kickoff before it answers: the same text Copy prompt and `dm transfer linear` print, the Linear transfer guide included. The kickoff goes with the chat's first start only, as an orchestrator's does (Claude Code's positional prompt, every other CLI's first paste). Because a later start may be on a new session, the chat's instructions file also carries `transferGuidance` (`src/mcp/transferKickoff.ts`) on every start, after the `dm` instructions, for any chat with a `transferEpicId`: the epic id, the start_transfer step and the guide, built from the epic id alone (on a first start the guide therefore reaches the agent twice). The chat gets the grant and `DM_SESSION_TOKEN` of any orchestrator chat: Dark Mechanicus attaches no Linear server, so the agent uses the one configured in its own CLI. The record keeps `transferEpicId` and the role, so `chats:findTransferChat` finds the chat again after an app restart and its terminal starts again as an orchestrator's, never with the kickoff again. Whether that start resumes the CLI's session follows the launch spec below: Claude Code once its session file exists, Autonomous once the chat was typed into, Codex and Cursor only with a stored session id, a custom CLI never. A CLI that starts on a new session has only the guidance: Codex and Cursor get the instructions as their first paste and so start on the transfer by themselves; Claude Code and Autonomous have them in their system prompt and wait for the person; a custom CLI has them only through `{instructions}`. A failure once the chat is asked for leaves the transfer authorized and is reported in `problem`, as for an orchestrator (a terminal that does not start removes the chat again, or keeps it when it cannot be removed). `chats:transferPrompt` answers the kickoff for an agent the person starts elsewhere.

**Transfer to Linear in the epic workspace.** The header offers **Transfer to Linear** beside Start run for an epic with a saved plan, no active run, no open transfer, no unsaved draft changes, and not completed; Start run hides while a transfer is queued or in progress (the workspace reads `getTransfer` with the epic). Both choices of the dialog call `queueTransfer` first: **Transfer with agent** then calls `chats:startTransferChat` and, once the folder's chats are listed again, opens the chat's terminal, **Copy prompt** then copies `chats:transferPrompt`. If the queue succeeds but the chat cannot be started (or the prompt copied), the transfer stays authorized, as main leaves it: the banner says why (a chat that could not be removed is listed, but the workspace stays on the reason), and the transfer strip under the header, shown while the transfer is open, recovers it. The strip shows the status, how many packet items are recorded ("n of m created") and the last read-back's mismatches by DM key and field, with **Resume** (`chats:findTransferChat`, or the dialog again to start a new transfer chat without queueing), **Copy prompt** and **Cancel transfer** (`cancelTransfer`, after a confirmation). A completed epic whose outcome records a transfer shows **Transferred to Linear** above its plan, from the epic alone, with the project link opened through `openExternal`. The renderer calls only the desktop commands `getTransfer`, `queueTransfer` and `cancelTransfer`; everything else in a transfer is the agent's.

### Terminals: PTY host, sessions, attach and port, launch spec

**The PTY host.** `src/main/terminals/ptyHost.ts` is the only module that loads `node-pty`, in the main process (`createNodePtyHost`, composed in `bootstrap.ts`); everything else starts PTYs through its `PtyHost` interface (tests use `__mocks__/fakePtyHost.ts`). A spawn takes an absolute program, an argv (on Windows a command line the app quoted itself, `windowsCommandLine.ts`), a canonical cwd, the whole environment (nothing is inherited) and a size. On macOS `ptyHelperCheck.ts` first checks that node-pty's `spawn-helper` is executable and names the file when it is not. A PTY's whole tree is ended with `killPtyTree` (`processTree.ts`); node-pty's own kill reaches only the program.

**Terminal sessions.** `TerminalSessions` (`terminalSessions.ts`) keeps one PTY per chat, with its screen in main: an `@xterm/headless` terminal fed the PTY's output (`terminalScreen.ts`), whose serialized snapshot paints any pane that attaches (a chat switch, a reload, a second window). A start resolves the folder (`resolveLaunchFolder`), checks sign-in (`getAgentAuthStatus`; `signed_out` starts nothing), writes the start files (`terminalFiles.ts`: the instructions and, on macOS, the chat's `dm` launcher; `claudeSettingsFile.ts` for Claude), issues the grant, builds the launch spec and spawns. The grant is revoked when the PTY exits for any reason. While it runs, the folder is checked every minute and on each attach, and a PTY with no input and no output for 10 minutes is stopped; exit, Start again, resume, New session, quit disposal and the signed-out run pause are in the module table above.

**`terminals:attach` and the message port.** The renderer starts a chat's CLI only through `terminals:attach { folder, chatId, newSession? }`, a strict object through `guardIpc`; the one other start is main's own `TerminalSessions.start`, which `chats:startOrchestrator` and `chats:startTransferChat` call for the chat they have just created, with its kickoff, before they answer (it subscribes no one). Main loads the chat from its own store, refuses a folder that is not the chat's own, and attaches to the running PTY or starts one. An attach that finds the sign-in check under way waits for the start to end and then answers (`running` with an empty snapshot, since its listener heard everything since the spawn) rather than answering `checking`. A `running` answer carries the snapshot, and main posts one end of a `MessageChannelMain` to the asking frame on `terminals:port`, named by an id the preload uses to claim it (`src/preload/terminals.ts`). On that port main takes only `{ type: 'input', data }` (at most 64 KiB) and `{ type: 'resize', cols, rows }` (clamped); it sends the chat's output and its exit, then closes the port. `agents:signIn` answers the same way for an agent's sign-in terminal (`loginTerminals.ts`).

**The launch spec.** `terminalLaunchSpec.ts` is pure: from the chat record, the agent row, the resolved folder, the chat's `dm` invocation and the start files it returns the program, arguments, cwd and environment (`terminalEnv.ts`), plus `pasteFirst` and the values it dropped. Per kind:

| Kind | Arguments main builds |
|------|-----------------------|
| Claude Code | `--append-system-prompt-file <instructions>`, `--settings <file>`, `--model <id>` when set, `--session-id <uuid>` or, once `claudeSession.ts` finds the session file, `--resume <uuid>`; on a first start of an orchestrator chat the kickoff as the positional prompt. On Windows a `claude.cmd` is followed to the program it runs (`resolveClaudeExecutable`) |
| Autonomous | `start <folder>` (or `resume` once the chat was typed into), `--append-system-prompt <text>` (not through a `.cmd`), `--approval-mode always-ask`, `--model <id>` when set |
| Codex | `-C <folder>` or `resume <id>`, `-m <model>` when set (inferred in the design; not checked against a real Codex) |
| Cursor | `--resume <id>` when resuming, `-m <model>` when set (inferred, as Codex) |
| Custom CLI | The confirmed arguments only, whole-argument `{folder}` and `{instructions}` replaced; no app flag |

What cannot go on the command line (the kickoff for every CLI but Claude Code, and the instructions for Codex, Cursor and an Autonomous `.cmd`) is `pasteFirst`: once the CLI has turned bracketed paste on and its screen has then taken no output for a second, main writes it as one bracketed paste with every control character but tab removed, then Enter half a second later as typed input; a kickoff sent so sets `kickoffSent` once its Enter has gone. A model that fails `isSafeModelId` and a Claude session id that is not a UUID are dropped and reported.

**What the renderer can and cannot make main start** (condensed from [`design/chat-shells.md`](design/chat-shells.md#what-a-compromised-renderer-can-make-main-start-through-a-terminal)):

| | What main starts | What the renderer can choose |
|-|------------------|------------------------------|
| Program | The chat's agent row in `app.sqlite`, set by Find, Download or Add a custom CLI through native dialogs | Nothing: it names a chat; main reads the agent from its own record |
| Arguments | The per-kind preset or the confirmed custom arguments, plus paths and ids main makes | Only the chat's model, set at creation, which is dropped unless it passes `isSafeModelId` |
| cwd | `resolveLaunchFolder` on the chat's stored folder | Nothing: the request's folder is only compared with the chat's |
| Environment | `terminalEnv.ts`: main's own without `ELECTRON_*` and `NODE_OPTIONS`, `TERM` and `COLORTERM`, the grant and `DARKMECHANICUS_HOME`, the macOS launcher folder first on `PATH` (on Windows, packaged, `ELECTRON_RUN_AS_NODE=1` stays) | Nothing |
| Sign-in terminal | A connected built-in's executable with its constant `LOGIN_ARGS`, in the home folder, with no grant | An agent id only; a custom CLI is refused |
| After the start | Input bytes and sizes on the port | It cannot start a second process, change the program, arguments, folder or environment, or keep a process past a quit, a deleted chat, a removed agent or a moved folder |

What stays possible: keystrokes drive the CLI, so a compromised renderer can make it do whatever it does in that folder at the chat's grant (type a prompt, answer its permission prompts, use its shell escape). The boundary stays the grant's role and Allow save.

## Bridge hardening

Defense in depth on both bridges (desktop IPC and MCP); the command layer's authorization stays the real boundary.

- **IPC sender check** (`src/main/ipcGuard.ts`). `index.ts` wraps `ipcMain` once with `guardIpc` and passes the result to every registrar (`dm:*`, `agents:*`, `chats:*`, `terminals:*`, auto-update, app version); nothing else touches `ipcMain`, and a test scans `src/main` to keep it that way. A call runs only when `event.senderFrame` is live, attached, top-level, and shows the app's own page: `isAppUrl` (shared with the navigation guard) compares the dev server's origin in development, and in production the packaged `index.html` by parsed protocol, host, and resolved path (query and hash ignored, never a prefix). Anything else gets `{ ok: false, error: { code: 'unauthorized' } }`, the handler never runs, and main logs the refusal. A chat terminal's message port is posted only to the frame of an attach that passed this check, so the port needs no `ipcMain.on` channel of its own.
- **Tools per role** (`src/mcp/tools/define.ts`). Each tool adapts one command (its camel-cased name, or an explicit `command` the compiler requires otherwise). `createMcpServer` grants the server the session's capabilities (`capabilitiesForRole(role, { allowSave })`), and `registerTools` registers a tool only when that set holds `COMMAND_CAPABILITIES[command]`. Read-only tools need `read`, which every role has; `save_plan` needs `plan.save`, which only `--allow-save` adds for planner and orchestrator. A withheld tool is still known to the server: calling it answers `unauthorized` without running anything.
- **Structured validation errors.** The SDK validates tool arguments before the tool callback and answers failures as plain text. The server replaces the SDK's `tools/call` handler with one that parses each tool's zod shape itself and answers failures with `invalid_input` (`details.issues`: path and message per field). `tools/list` stays the SDK's, so advertised JSON schemas are unchanged; a test pins each one to its fingerprint from before the change.

## Verification tooling

- `npm run smoke:mcp` launches the built `out/main/mcp.js` over real stdio (set `MCP_SMOKE_COMMAND` to Electron's binary to use its runtime) and plans, saves, and runs a ticket end to end.
- `npm run spike:claims` races claims on one ticket from 8 processes (exactly one winner per round).
- `src/integration/` exercises the real Workspace through the command table, MCP tools (in-memory transport), and desktop IPC handlers.
- Fireguard scopes mutants to the graded tests that import the mutated module and bounds each test run with `testTimeoutMs`, so milestone-sized branches grade in hours, not days, and an infinite-loop mutant counts as killed.

## Decisions taken during implementation

The product plan's open decisions were settled as follows (all revisitable):

- **Git tracks portable records**, not SQLite snapshots: JSON records under `.darkmechanicus/` plus a Git-ignored working database, rebuilt on clone.
- **First host:** any stdio MCP host; a Claude Code skill wrapper ships (`installSkills`) and the six skills are also plain MCP prompts, so no host-specific API is assumed.
- **Sprint advancement defaults to a human checkpoint** (`checkpoint.mode = human`); `auto` needs per-run authorization in the desktop.
- **Deletion stays deferred**, as the plan requires: no delete UI or tools ship (mockup 06 is not implemented).
- **The desktop hosts agent CLIs as terminals, and drives no vendor protocol:** each chat runs the agent's own CLI in a terminal (`docs/design/chat-shells.md`); what differs per CLI is its launch preset (`terminalLaunchSpec.ts`), the per-kind connection data (install recipes, version match, status command) sits beside the registry in `src/main/desktop`, and plans, tickets and profiles never name a vendor at all. Connected agents and chats are machine-local `userData` files, not portable records (see [Hosted agents](#hosted-agents)).
- **Named profiles are records like the others:** `format: darkmechanicus.profile`, `formatVersion: 1`, strict schema, key-sorted pretty JSON, imported on reconcile; tickets copy them rather than reference them, so a profile edit never rewrites plans.
- **A Linear transfer is carried out by an agent, authorized by a person, and checked by a read-back that trusts the agent.** Dark Mechanicus never calls Linear and holds no Linear credential: the orchestrator agent does the Linear work with its own Linear MCP server, following the packet `start_transfer` returns (`src/core/transfer/linearPacket.ts`). Sending a plan out is the person's decision, so queueing and canceling a transfer need `transfer.queue`, which only the desktop holds; an agent's `epic.transfer` only carries out a transfer already queued, and while it is open runs and Save are locked (`transferGuard.ts`). Completion rests on the read-back: the agent reports what it read from Linear, and `compareReadback` (`src/core/transfer/linearReadback.ts`) checks it against the stored packet and the recorded items; only a full match completes the epic. Its trust limit: Dark Mechanicus cannot read Linear, so the check is only as good as the agent's honesty in reading Linear back. It catches mistakes, such as a missing issue, a wrong milestone or a lost marker, not an agent that misreports. The runbook is [Transfer an epic to Linear](runbooks/linear-transfer.md).

## Testing conventions

- TDD with Vitest. Core tests use `createTestCtx()` (`src/test/testContext.ts`): in-memory migrated DB, fixed clock, sequential ids. Repository tests use temp directories. Renderer component tests use `// @vitest-environment jsdom` + Testing Library.
- Fireguard grades changed tests: keep mocks rare (fakes over `vi.fn`), assert on outputs/state rather than `toHaveBeenCalled*`, no empty tests, deterministic (100 isolated runs), and kill ≥ 75 % of mutants in changed modules (operators `+ - * / < > <= >= === !==`, `if` inversion, boolean/number returns).
